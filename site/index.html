Every restart is archaeology

You run several coding agents against one repository. An agent dies halfway through a task: a network blip, an OOM kill, or a closed laptop. What survives is work in a terminal scrollback that nobody can read later.

Context dies with the session

Agent A was halfway through rewriting the auth layer. That context lived only in Agent A's prompt window.

Next agent starts from zero

Agent B sees a task titled "fix auth" and starts from scratch, or worse, starts conflicting with A.

Nobody knows what's stale

Which of the three open branches is current? The task list is a TODO file, the reasoning is in an output window, the status is in your head.

Four ideas carry the whole design

Each agent gets a lease on a task, an append-only event log, and a handoff protocol, so a new session starts with the previous session's actual context instead of a task title.

1Ownership is a lease

task claim grants a time-boxed lease. When it expires (crash, kill, or walk-away), the task is automatically reclaimed for the next session.

2The event log is the truth

Every state change is an event. The board is a projection, and rebuild can replay the log and diff it against what's stored.

3Handoffs are written, not generated

A stopping session writes what's done, what's next, what's blocked. resume shows it first. Crash-generated notes explicitly say the previous holder is unreachable.

4Plans are versioned

plan save never overwrites; it supersedes. The full chain, and the reasoning behind any decision, stays queryable.

The board

A web UI with a kanban view, task detail timelines, and live updates over SSE, served locally by the same binary.

Install

One-line install, no runtime required. The binary is self-contained: the Bun runtime, the database schema and the whole web UI are embedded.

curl -fsSL https://raw.githubusercontent.com/ArnoChenFx/agent-kanban/main/install/install.sh | bash

Installs to ~/.local/bin and adds it to your PATH. No sudo. Re-run the same command to upgrade, or use agent-kanban update.

# any shell, including cmd
powershell -NoProfile -ExecutionPolicy Bypass -Command "irm https://raw.githubusercontent.com/ArnoChenFx/agent-kanban/main/install/install.ps1 | iex"

# or, inside an open PowerShell window
irm https://raw.githubusercontent.com/ArnoChenFx/agent-kanban/main/install/install.ps1 | iex

Works from cmd and PowerShell alike. Installs to %LOCALAPPDATA%\Programs\agent-kanban and adds it to your PATH. No administrator rights.

git clone https://github.com/ArnoChenFx/agent-kanban.git
cd agent-kanban
bun install
bun run build:binary      # frontend + embedded assets + compiled binary
./dist/agent-kanban init

Requires Bun ≥ 1.4.2.

Then, in your repository

agent-kanban init                # create a board in the current directory
agent-kanban install-protocol    # teach your agents to use the board
agent-kanban serve               # → http://127.0.0.1:7788/

install-protocol writes the collaboration protocol into the project's AGENTS.md, so agents that read it know to run session start and context before touching code.

Put your agents on the board

Three complementary ways. The skill teaches the workflow, the protocol file enforces the habit, the MCP tools give the agent hands.

1. The protocol file

Writes a managed block into AGENTS.md so any agent that reads it knows to run session start and context first. Supports --check as a CI guard.

2. MCP tools

29 tools over stdio, thin wrappers over the same core the CLI uses. Every tool returns { ok, data, next_actions }, failures carry the same exit-code semantics as the CLI.

3. The agent skill

Teaches the workflow: what to do on exit code 3, that progress renews the lease, why doing → done goes through review.

npx skills add ArnoChenFx/agent-kanban --skill agent-kanban
