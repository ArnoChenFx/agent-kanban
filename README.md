# agent-kanban

[English](README.md) · [中文](README_zh.md) · [For developers](Develop.md) · [开发者文档](Develop_zh.md)

A project-scoped task board that lets multiple AI agent sessions share one source of truth — and pick up each other's work when they crash.

---

## The problem

You are running several coding agents against one repository. Maybe you run a main session plus a few subagents. Maybe an agent dies halfway through a task: a network blip, an OOM kill, a closed laptop, a `SIGKILL` from a supervisor.

What usually survives is work in a terminal scrollback that nobody can read later:

- Agent A was halfway through rewriting the auth layer. That context lived only in Agent A's prompt window.
- Agent B sees a task titled "fix auth" and starts from zero, or worse, starts *conflicting* with A.
- Nobody knows which of the three open branches is stale.
- The task list lives in a TODO file, the reasoning in the agent's output, the status in your head.

Every restart is archaeology.

## What agent-kanban does

It gives each agent a **lease on a task**, an **append-only event log**, and a **handoff protocol** — so a new session can start with the previous session's actual context instead of a task title.

```
┌──────────┐   claim    ┌───────────┐   write     ┌──────────┐
│ session  │ ─────────► │   task    │ ──────────► │ progress │
│    A     │            │ T-0007    │            │ 60%, ... │
└────┬─────┘            └─────┬─────┘            └────┬─────┘
     │                        │                       │
     │  lease expires, or agent crashes              │
     ▼                        ▼                       ▼
┌────────────────────────────────────────────────────────────┐
│  event log  (append-only, the single source of truth)      │
└────────────────────────────────────────────────────────────┘
     │                        │
     │  handoff               │  rebuild
     ▼                        ▼
┌──────────┐            ┌──────────┐
│ handoff  │ ─────────► │ session  │  kanban resume T-0007
│ note     │            │    B     │  → gets the handoff + timeline
└──────────┘            └──────────┘
```

Four ideas carry the whole design:

**1. Task ownership is a lease, with an expiry.**
`kanban task claim T-0007` gives the current session a time-boxed lease (15 min by default). Progress and checklist items are preserved. When the lease runs out, whether the agent crashed, was killed, or just walked away, the server reclaims the task automatically. The next `context` call tells the new session the card is up for grabs. Nobody has to run a cleanup script.

**2. The event log is the source of truth; the board is a projection.**
Every state change is an event: `task_created`, `task_progress`, `handoff_created`, `plan_superseded`. The `tasks` and `plans` tables are derived. That means `kanban rebuild` can recompute the entire board from the log and diff it field by field against what's stored:

```console
$ kanban rebuild
Replaying 412 events...
4 field(s) differ from the stored projection.

$ kanban rebuild --write
Replaying 412 events... 4 drift(s) repaired in a single transaction.
```

If the log and the projection ever disagree, you find out then, rather than six weeks later.

**3. Handoffs are written by the agent, not generated by the system.**
When a session stops, it writes a handoff: what's done, what's next, what's blocked, what open questions remain. `kanban resume` shows that first. Crash-generated handoffs exist as a fallback, and they explicitly say "the previous holder is unreachable", so you never mistake a dead session's guesses for a live one's instructions.

**4. Plans are versioned rather than overwritten.**
`kanban plan save` always creates a new version and marks the old one `superseded`. `kanban plan history` shows the chain; `kanban plan at --ts` shows what was in effect at any moment. When a task is done and someone asks "why did we do it this way?", the answer is still there.

## Quick start

### Option A — single binary (no runtime required)

Download the file for your platform from [Releases](https://github.com/your-org/agent-kanban/releases). The binary embeds the Bun runtime, the database schema, and the entire web UI.

```bash
chmod +x kanban-linux-x64        # macOS: kanban-darwin-arm64 · Windows: kanban-windows-x64.exe
./kanban-linux-x64 init
./kanban-linux-x64 session start --agent my-agent
./kanban-linux-x64 task add "Rewrite the auth layer"
./kanban-linux-x64 serve         # → http://127.0.0.1:7788/
```

### Option B — from source

Requires [Bun](https://bun.sh) ≥ 1.4.2.

```bash
bun install
bun run build:binary            # build frontend, embed assets, compile
./dist/kanban init
./dist/kanban serve
```

### Option C — Docker

```bash
cp .env.example .env
# Set KANBAN_ADMIN_TOKEN — generate one: openssl rand -hex 16
docker compose up -d
```

The image does **not** ship a compiled binary. It runs the TypeScript sources directly on `oven/bun`, so there is no build step in the image and only one copy of the Bun runtime.

By default Compose builds the image locally. To pull a published image instead, set `KANBAN_IMAGE` in `.env`; `KANBAN_BIND` and `KANBAN_PORT` control how far the server is reachable and which host port it binds.

## Daily use

```bash
# 1. Start a session (registers who you are)
kanban session start --agent pi-main --harness pi

# 2. Read the situation — this is the first thing you should do
kanban context
#    → your handoffs, what you're working on, what you could claim

# 3. Claim a task (acquires the lease)
kanban task claim T-0007

# 4. Work, and keep the board honest as you go
kanban task progress T-0007 --pct 60 --note "Storage layer rewritten"
kanban task check T-0007 --item "Add migration test"

# 5. Stuck? Say so, and the lease is released
kanban task block T-0007 --reason "Waiting on API key from ops"

# 6. Stepping away? Leave a real handoff
kanban handoff --task T-0007 \
  --summary "Auth rewrite done, token refresh left" \
  --next "Start from refreshToken(); see plan v2" \
  --blockers "Needs staging API key" \
  --open "Rotate refresh tokens on every use?"

# 7. Done
kanban task done T-0007 --note "Tests green"
kanban session end
```

### Coming back after a crash

```bash
kanban context           # what's mine, what's free, who crashed
kanban resume T-0007     # take over: handoff + full timeline injected
```

You get the previous session's notes, the ordered list of every change made to the task, and the current plan version — not a blank card titled "fix auth".

## The web board

`kanban serve` hosts a real UI on port 7788:

- **7 swimlanes** — Backlog, Todo, Doing, Blocked, In Review, Done, Cancelled
- **Drag and drop** with state-machine validation; an illegal move is rejected with the reason
- **Task drawer** — timeline, handoffs, plan version history
- **Live updates** via SSE, with cursor resume after a reconnect
- **Multi-project switcher**, light/dark mode
- **Shareable links** — `?key=…&project=…`; parameters are stripped from the URL after reading
- **Admin page** at `/admin` — manage projects, issue and revoke tokens

The web UI and the CLI operate on the same data through the same code path. Anything you can do in the browser, an agent can do from its shell.

## Sharing a board across machines

One `kanban serve` process can host many projects. Each project is fully isolated: its own tasks, its own tokens, its own ID space (`T-0001` starts at 1 in every project).

```bash
# On the server machine
kanban serve                                  # prints the admin token once
kanban admin project add my-app
kanban admin token create --project my-app --name "CI runner"
# → k_a1b2c3...

# On a client machine: write <project>/.kanban/config.toml
```

```toml
mode = "remote"

[server]
url   = "https://kanban.example.com"
token = "k_a1b2c3..."

[project]
key = "my-app"
```

```bash
kanban config show     # confirm what resolved and where it came from
kanban task list       # no flags needed from here on
```

Or set it up in one command:

```bash
kanban config init --server https://kanban.example.com --project my-app --key k_a1b2c3
```

## Configuration

Everything lives in `<project>/.kanban/config.toml`.

| Setting | CLI flag | Environment variable | Default |
|---|---|---|---|
| Server URL | `--server` | `KANBAN_SERVER` | derived from the project directory |
| Project key | `--project` | `KANBAN_PROJECT` | derived from the project directory |
| Access token | `--key` | `KANBAN_KEY` | — |
| Mode | — | `KANBAN_MODE` | `remote` if a server is set, else `local` |
| Database path | `--db` | `KANBAN_DB` | `<project>/.kanban/kanban.db` |
| Session ID | `--session` | `KANBAN_SESSION` | `<project>/.kanban/session` |

Two flags affect every command, so they work before or after the subcommand: `--json` for machine-readable output, and `--no-color` to disable ANSI colors. In CI, set `NO_COLOR=1` instead.

Server-side: `KANBAN_HOST`, `KANBAN_PORT`, `KANBAN_WEB_DIR`, `KANBAN_ADMIN_TOKEN`. In Docker, `KANBAN_BIND` controls the *host-side* bind address (`127.0.0.1` or `0.0.0.0`). Note that the container itself always listens on `0.0.0.0`, so this variable is what actually decides how far the server is reachable.

**Precedence:** CLI flags > environment variables > `config.toml` > derived defaults.

> An empty environment variable counts as *unset*, not as an empty value. Otherwise `export KANBAN_SERVER=` would silently shadow a perfectly good `config.toml` and quietly create a new empty local database.

## Security

**`serve` does not terminate TLS, and binds to `127.0.0.1` by default.**

That is deliberate. Most deployments of a tool like this already sit behind an existing HTTPS terminator: a corporate gateway, nginx, a Kubernetes Ingress, or a network reachable only over VPN. Shipping a container that renews certificates introduces a failure mode (expired cert means total outage) that most users do not need.

If you expose it, put it behind a TLS terminator. **Without TLS, tokens travel in plaintext.**

| Token type | Access |
|---|---|
| Project token | Only the projects it is explicitly granted |
| Admin token | Every project, plus project and token management |

`KANBAN_ADMIN_TOKEN` must be `k_` followed by 32 lowercase hex characters. A malformed value fails at startup rather than at first use, because a misconfigured credential that only breaks later is the worst kind.

When it comes from the environment, the token is neither written to `config.toml` nor printed to the log.

## Command reference

| Command | Purpose |
|---|---|
| `kanban init` | Create the local board (`.kanban/`) |
| `kanban session start \| end \| list \| heartbeat` | Session lifecycle |
| `kanban task add \| list \| show \| claim \| progress \| block \| done \| …` | Task operations |
| `kanban board` | Swimlane view in the terminal |
| `kanban context` | Read the situation: board + handoffs + suggested actions |
| `kanban resume <task>` | Take over a task; injects handoff and timeline |
| `kanban handoff` | Write a handoff (summary / next / blockers / open) |
| `kanban plan save \| show \| list \| history \| at \| attach` | Versioned plans |
| `kanban rebuild [--write]` | Replay the event log and verify the projection |
| `kanban doctor [--deep]` | Consistency self-check and repair |
| `kanban config show \| init \| set \| use \| path` | Configuration |
| `kanban project list` | Query projects (local database) |
| `kanban admin project … \| token …` | Project and token management |
| `kanban serve` | Run the HTTP + SSE server |

Run `kanban <command> --help` for the full option list.

### Exit codes

These are a published contract. Agents branch on them, so the meanings never change.

| Code | Name | Meaning | What to do |
|---|---|---|---|
| `0` | OK | Success | — |
| `1` | USAGE | Bad arguments | Read `details.usage` and fix the command |
| `2` | STATE | Task missing, illegal transition, missing required `--reason` | Do not retry as-is |
| `3` | CONFLICT | Task is held by another session with a live lease | Work on something else, or wait. **Do not** reach for `--force` |
| `4` | BUSY | Database is locked | Back off and retry, at most 3 times |
| `5` | NOT_INIT | No `.kanban/` directory, or schema needs migrating | Run `kanban init` |
| `6` | INTERNAL | Bug | Report it, do not retry |
| `7` | AUTH | Missing key, wrong key, or project not found | Fix your credentials |

Agents should branch on the code (or the `error.name` string in `--json` output), never on message text.

## When to reach for this

Good fit:

- More than one agent session working the same repo
- Tasks long enough to span a context window
- Work that gets interrupted (CI, laptop closed, agent restarted)
- A team that wants to *see* what the agents are doing without tailing logs

Poor fit:

- A single agent on a short task. The overhead is not worth it
- Work that must not be shared with a server. Use local mode, no server needed
- Anything needing a real multi-user permissions model. Tokens are project-scoped, not user-scoped
