# 004 — Web 看板与管理页中英文双语

> 状态：已实施（2026-02-19）
> 关联任务：T-0017
> 涉及：`web/src/lib/i18n.tsx`（新增）、`web/src/components/language-toggle.tsx`（新增）、
> `web/src/lib/status.ts`、`web/src/lib/api.ts`、`web/src/components/{board,dialogs,task-card,task-detail,login}.tsx`、
> `web/src/main.tsx`、`web/index.html`、**`src/server/admin-page.ts`**、
> `scripts/snapshot-web.ts`、`scripts/verify-web-ui.ts`

## 1. 要解决的问题

看板的界面文案原本全部硬编码为中文。这在两个场景下会咬人：

- **非中文使用者**：agent 之间的协作界面给人看时，人未必读中文。
- **新增文案的成本**：每加一个按钮就要在 6 个文件里找该改哪，改漏了没人发现——
  中文界面里漏翻看不出来，因为"漏翻"和"没翻译"长得一模一样。

第二点才是关键：双语化在这里不是"多写一份英文"，而是**把文案从代码里抽出来**，
让漏翻变成一件机器能发现的事。

覆盖面包含**两个界面**：`/` 看板（React 应用）与 `/admin` 管理页（服务端内嵌的
自包含 HTML）。两者是同一 origin、同一份语言选择。

## 2. 决策：不引第三方 i18n 库

看板的可翻译面是 190 条文案，其中没有一个需要复数规则、没有一个需要按性别变化、
没有一个需要 RTL。i18next / react-intl 会带来 namespace 解析、fallback 链、
SSR 适配、插件体系——这些在这个项目里全是死重量，而 bundle 是要被内嵌进
单文件二进制的（`src/server/assets.generated.ts`）。

自己写一个约 330 行（含两份词典）的模块，换来：

| 收益 | 说明 |
| --- | --- |
| 键对齐由编译器保证 | `en: Record<MessageKey, string>`，漏一条直接 `tsc` 报错 |
| 零依赖、离线可用 | 不需要拉包，也不进 bundle |
| 可单测 | 词典是纯数据，Provider 薄到没有分支 |
| 看得懂 | 200 行就能读完，不用先读懂 i18next 的心智模型 |

**放弃了什么**：运行时动态加载词典（`fetch("/locales/en.json")`）、按日期/区域
细分文案、复数规则。判断依据是"这些需求在这个项目里是否存在"——现在都不存在。
真要加第三种语言时，加的是一份词典，不是换一套架构。

## 3. 结构

### 3.1 键的来源

`zh` 用 `satisfies Record<string, string>` 声明，`MessageKey = keyof typeof zh`。
`en` 声明成 `const en: Record<MessageKey, string>`。

```
新增一条中文 → MessageKey 多一个 → en 里没写 → tsc 报错
多写一条英文 → Record 里没有这个键 → tsc 报错
```

这比运行时 fallback 强的地方在于：漏翻不会跑到线上。

### 3.2 插值

`{name}` 占位符 + `t(key, params)`。不做 ICU 复数——真要复数的地方
（"还剩 1 项" / "还剩 {n} 项"）拆成两个键，在调用点选：

```tsx
checklistLeft === 1 ? t("card.checklistLeftOne") : t("card.checklistLeft", { n: checklistLeft })
```

英文的 "1 left" 和 "5 left" 语法上完全一样，所以英文只需要一条；
中文需要两条。**代价是两个语言各自的语法问题，不是为了对称而对称。**

缺失的参数保留占位符原样（`进度 {pct}%` 而不是 `进度 undefined%`）——
前者一眼可辨，后者会被当成正常文案读过去。

### 3.3 状态机与时间格式化

`web/src/lib/status.ts` 原来是自包含的（`STATUS_META[to].label`、
`relativeTime(ts)` 直接返回中文字符串）。改造成**接收一个已绑定 locale 的 `t`**：

```ts
canMove(from: TaskStatus, to: TaskStatus, t: Translate): { ok: boolean; reason?: string }
relativeTime(ts: number, t: Translate, now?: number): string
leaseText(expiresAt: number | null, t: Translate, now?: number): string | null
describeEvent(type: string, data: Record<string, unknown>, t: Translate): string
statusLabel(status: TaskStatus, t: Translate): string
```

这样做的取舍：**不引 React**。这个文件不读全局状态、不需要 Provider，
接收 `t` 当参数后仍然能脱离界面直接单测；如果改成在文件里
`useI18n()`，它就变成只能被组件调用、且会隐式依赖 Provider 包在上面的东西。

`STATUS_META` 保留了纯静态的 `colorVar`（渲染热路径上零查表），
把 `label` 换成 `labelKey: MessageKey`——键是编译期常量，代价只有一次对象索引。

### 3.4 语言来源与优先级

```
localStorage["kanban.locale"]  （用户在顶栏的选择，最高优先级）
  ↓ 没有
navigator.language 的前缀      （只认 en 开头；en-US/en-GB 都算 en）
  ↓ 都没有
zh
```

写入失败（隐私模式）静默降级：只影响"下次打开记不住"，不阻断本次切换。

### 3.5 文档级属性

`<html lang>` 决定浏览器的朗读语音与断词位置，`<html>` 上晚改一步就晚一步。
`index.html` 里静态写死 `lang="zh-CN"` 会让英文用户先经历一个中文首帧。

所以抽了 `primeDocumentLocale()`，在 `main.tsx` 的**启动引导**里、
`createRoot` 之前调用——和已有的 `consumeUrlLogin()` 同一个位置、同一类理由
（组件 `useState` 初始值只在首次挂载时求值，render 阶段调用赶不上）。
`document.title` 同样在 render 前写入（`index.html` 里的 title 因此只留产品名）。

## 4. 切换控件

`web/src/components/language-toggle.tsx`：一个 Languages 图标按钮，
tooltip 显示**点完会变成什么**（"切换到 English" / "Switch to 中文"），
`aria-label` 用同一句文案。

**为什么不是两段文字并排**（`中文 | English`）：

- 只有两种语言时，"切到另一种"是唯一确定的动作，不需要用户在两个已知自己语言
  的名字里再挑一次。
- 顶栏横向空间紧张，图标按钮放得下，两段文字放不下。
- 悬停即知结果，不需要额外的"当前选中"高亮去猜状态。

登录页没有顶栏，所以切换按钮挂在登录卡片右上角（用 shadcn 的 `CardAction` 槽位，
`CardHeader` 见到它自动切成两列，标题不会被挤窄）。**否则未登录的用户反而是
唯一改不了语言的一群人。**

## 5. 一个真实的数据泄漏

`SessionsPanel` 原本直接显示后端下发的 `session.fresh` 字段，而那个字段是
后端格式化的**中文串**（`src/core/sessions.ts`：`"刚刚" / "2m 前"`）。
英文界面下它会静静地在会话徽标上露出中文。

修法不是去改后端，而是**改用同一个响应里已有的 `last_seen_at`**（毫秒时间戳，
`src/core/ops.ts` 的 `sessionToJson` 本来就在发），前端自己用
`relativeTime` 格式化。老服务端没带这个字段时才退回 `fresh` 串。

这也回答了"哪些字符串要翻译"的边界问题。

## 6. 边界：翻译 chrome，不翻译内容

| 类别 | 处理 | 例子 |
| --- | --- | --- |
| 界面 chrome | 翻译 | 按钮、页签、toast、状态名、占位符 |
| 用户数据 | 不翻译 | 任务标题、描述、检查项 |
| agent 交接正文 | 不翻译 | handoff `summary` / `next_step` |
| 后端生成的建议 | 不翻译 | `/api/context` 的 `next_actions`（本来就是给 agent 看的 CLI 指引） |
| 后端格式化的时间串 | 绕开，前端自己算 | `session.fresh` → `last_seen_at` |

判据是"这句话是界面在说话，还是用户在说话"。`next_actions` 属于后者——
它本来就是中文的 agent 指令，把它塞进英文界面只会让两边都别扭；
要国际化它，应该改的是后端而不是前端词典。

## 7. 管理页：同一套约定的第二份实现

`/admin` 不是 React 应用，而是 `src/server/admin-page.ts` 里**一个模板字符串**返回的
自包含 HTML（这个页面全部卖点就是"没有外部依赖"），所以它拿不到 `web/` 的
`I18nProvider`，只能内联一份小词典。

约定与看板**完全一致**：点分键（`admin.*` 前缀避免与看板撞名）、`{name}` 插值、
同一个 `localStorage` key `kanban.locale`、同样的优先级
（localStorage → navigator.language → zh）。所以在看板切到英文后打开管理页，
管理页也是英文——同一个 origin 不该有两套语言状态。

静态文案用标记而不是重写模板：

```html
<h2 data-i18n="admin.project.heading"></h2>
<input id="newProjectKey" data-i18n-ph="admin.project.keyPh">
```

启动时 `applyStaticI18n()` 扫一遍 `[data-i18n]` / `[data-i18n-ph]`。
动态文案（表格单元、toast、`confirm()`）走 `t()`。

### 7.1 一个真实的 bug：模板字符串吃掉了正则里的转义

最初的插值实现是：

```ts
// TS 源里写的（注意反斜杠）
if (params) s = s.replace(/\{(\w+)\}/g, (w, n) => ...)
```

这段代码在一个 **TS 模板字符串**里。模板字符串的转义规则先跑一遍：
`\{` → `{`、`\w` → `w`。到浏览器里的正则变成了 `/{(w+)}/g`——要求字面的字母 `w`，
所以一个占位符都替换不掉。表现是管理页顶部显示
`{projects} 个 project · {tokens} 个 token`（而不是 `2 个 project · 1 个 token`）。

两个同类坑，都在同一个文件里：

| 写法 | 模板字符串处理后 | 后果 |
| --- | --- | --- |
| `/\{(\w+)\}/g` | `/{(w+)}/g` | 静默不替换（最难查：没有报错，页面只是"没变"） |
| 注释里写 `` `\\w` `` | 反引号**终止模板字符串** | `tsc` 直接炸 TS1127 |

修法是**彻底不用正则**：

```js
for (const [name, value] of Object.entries(params)) {
  if (value === undefined) continue;   // 缺参数时保留占位符原样
  s = s.split("{" + name + "}").join(String(value));
}
```

零反斜杠、零正则、行为相同。

### 7.2 管理页特有的两处

- **日期格式**跟着 locale 走：`new Date(ts).toLocaleString(HTML_LANG[locale])`。
  原来硬编码 `toLocaleString("zh-CN")`，英文界面下时间是 `2026/9/26 22:51:40`。
- **输入框会溢出**：原来 `min-width: 200px`，英文 placeholder 更长
  （`Name (e.g. CI, contractor team)`）被截断成 `Name (e.g. CI, contractor team`。
  改成 `min-width: 0; flex: 1 1 200px`，同一行控件变多时先压缩而不是溢出。

### 7.3 切语言时表格怎么重画

表格是动态渲染的（`renderProjects` / `renderTokens`），不重跑就还是旧语言的。
但**不该为了换语言再打一次 `/overview`**。所以缓存最近一次响应
（`lastOverview`），切语言时用它重画；登录态下再顺手 `loadAll()` 拉一次，
保证数据是最新的。

### 8.1 回归门禁里钉住默认语言

`verify:web-ui.ts` 原有的一批断言写的是中文文案（`aria-label="卡片操作"`、
页签「交接」/「计划」）。界面语言改成读 `navigator.language` 之后，**在英文系统上
跑这个脚本连第一步"点开卡片"都会失败**。所以浏览器用 `--lang=zh-CN
--accept-lang=zh-CN` 启动，把默认语言钉死；双语行为本身另起一节断言
（自动检测 → 看板切换 → `/admin` 继承 → `/admin` 切回），两种语言都跑。

顺带得到一个断言：管理页**继承**看板的 `localStorage` 选择。

## 9. 踩过的坑

**无头 Chrome 的 localStorage 跨页面导航读不回来。** 已在
`scripts/snapshot-web.ts` 的注释里记过（旧问题）。这次的新坑是它的推论：
**每种语言的截图必须用独立的 `user-data-dir`**——共用 profile 的话，
界面语言会从上一张截图泄进下一张，"截英文"拍出中文。
用 `--lang=en-US --accept-lang=en-US` 传 `navigator.language` 触发自动检测，
不需要真的去点切换按钮。

**`bun run web:build` 会覆盖 `src/server/assets.generated.ts`。** 仓库里提交的是
**空表占位**（`EMBEDDED_ASSETS = {}`），因为 `http.ts` 静态 import 本文件，
而干净 checkout 还没有 `web/dist`——真实清单里全是 `../../web/dist/...` 的字面量
路径，`bun test` 会直接抛 `Cannot find module`。跑过 `web:build` 后
`verify:deploy` 会红，要 `git checkout HEAD -- src/server/assets.generated.ts` 还原。

**`Record<K, V>` 才是穷尽检查，`satisfies` 不是。** 见实施笔记。
