# Agent 看板接口契约

> 配套文档：[001-总体设计.md](./001-总体设计.md)
> 本文件是 CLI / MCP / HTTP 三种接入面的**唯一契约来源**。实现时三者都不得偏离此表。

## 1. 通用约定

### 1.1 数据位置与发现

- 数据根目录：`<project>/.kanban/`，由 `agent-kanban init` 创建
- 环境变量覆盖（按优先级）：`KANBAN_DB` > `--db` > 在 `<project>` 向上逐级查找 `.kanban/kanban.db`
- 向上查找最多 5 层，支持 monorepo 布局

### 1.2 退出码（agent 依赖此做分支判断，必须稳定）

| 码 | 名称 | 含义 | agent 应做什么 |
| --- | --- | --- | --- |
| 0 | OK | 成功 | 继续 |
| 1 | USAGE | 参数/用法错误 | 读 stderr 的 `usage` 字段，修正命令 |
| 2 | STATE | 状态/数据错误（任务不存在、非法转移、缺 reason） | 读 `legal_transitions` 修正；不要重试 |
| 3 | CONFLICT | 冲突（任务被他人持有且租约有效、计划版本冲突） | 读 `holder` 改做别的卡；**不要**用 `--force` |
| 4 | BUSY | 数据库忙/锁等待超时 | 退避 1s 后重试，最多 3 次 |
| 5 | NOT_INIT | 找不到 `.kanban/` 或未迁移 | 跑 `agent-kanban init` |
| 6 | INTERNAL | 内部错误（bug） | 上报，不要重试 |
| 7 | AUTH | 远程认证失败（缺 key / key 错 / project 不存在） | 跑 `agent-kanban remote set` 或找管理员要 key |

`--json` 模式下，**成功时 stdout 只输出一个 JSON 对象**；失败时 stderr 输出 `{"error":{"code":3,"name":"CONFLICT","message":"...","details":{...}}}`，退出码同上。

### 1.3 错误对象

```json
{
  "error": {
    "code": 3,
    "name": "CONFLICT",
    "message": "task T-0007 is being worked on by s-7f3a2b (progress 60%, 12 minute(s) left on the lease)",
    "details": {
      "task_id": "T-0007",
      "holder": { "session_id": "s-7f3a2b", "agent_name": "pi-main",
                  "progress": 60, "last_seen_at": 1771432812345,
                  "lease_expires_at": 1771433712345 },
      "last_event": { "type": "task_progress", "ts": 1771432812345,
                      "data": { "pct": 60, "note": "改完事务层" } },
      "hint": "Someone else is working on this task. Pick a task from `agent-kanban task list --ready` instead; if you really need to take over, have a human confirm and use --force"
    }
  }
}
```

非法状态转移的 `details` 额外含 `"legal_transitions": ["doing","blocked","cancelled"]`，让 agent 自我修正而不是反复试。

### 1.4 会话标识

所有涉及任务归属的命令都接受 `--session <id>`。解析优先级：

1. 显式 `--session`（最可靠，脚本里用这个）
2. 环境变量 `KANBAN_SESSION`
3. `.kanban/session` 文件（`session start` 写入，进程内 cwd 相对）
4. 均无 → 报 USAGE 错误（**不**自动创建，避免误操作产生野会话）

### 1.5 时间与格式

- 所有时间戳为 epoch 毫秒（JSON 输出）；CLI 人类可读输出用 `2h14m` 形式
- `progress` 为 0..100 整数
- 相对时间显示：`<60s` → `just now`，`<60m` → `12m ago`，`<24h` → `5h ago`，否则 `2d ago`

## 2. CLI 契约

```
agent-kanban <group> <command> [args] [options]
```

全局选项：`--json` `--server` `--project` `--key` `--db` `--session` `--no-color`

### 2.0 project 与配置管理（v3：config.toml 取代 remote.json）

连接配置只存在一个地方：`<project>/.kanban/config.toml`。
优先级：**CLI 选项 > 环境变量 > config.toml > 派生默认**。
`remote.json` 与 `agent-kanban remote set/show/clear` 已在 v3 删除（与 config 重复且来源易混乱）。

| 命令 | 说明 | 典型用法 |
| --- | --- | --- |
| `agent-kanban config show [--json]` | 显示生效配置 + **每个字段的来源**（cli/env/config/derived） | `agent-kanban config show` |
| `agent-kanban config path` | 打印配置文件路径 | |
| `agent-kanban config init` | 生成默认配置（`mode = "local"`） | |
| `agent-kanban config set <key> <value>` | 写单个字段（`server.url` / `server.token` / `project.key` / `mode` / `db`） | `agent-kanban config set server.url https://kanban.corp:7788` |
| `agent-kanban config use <profile>` | 切换已保存的 profile | `agent-kanban config use work` |
| `agent-kanban project list` | 列出可见 project | `agent-kanban project list` |
| `agent-kanban project show [key]` | project 详情（key / 名称 / root / 任务计数） | `agent-kanban project show` |
| `agent-kanban admin project add <key> [--name N]` | 创建 project（**server 本机或管理员 token**） | `agent-kanban admin project add agent-kanban` |
| `agent-kanban admin token create --project <key>[,<key>] [--admin]` | 签发 token（明文只显示一次） | `agent-kanban admin token create --project agent-kanban` |

鉴权模型：管理员 token 访问全部 project；项目级 token 按显式 project 白名单授权（一个 token 可授权多个 project）。

### 2.1 生命周期

| 命令 | 作用 | 关键输出 |
| --- | --- | --- |
| `agent-kanban init [--name <项目名>] [--ttl 900] [--grace 600] [--force]` | 创建 `.kanban/`、schema 与 `config.toml`；`--force` **删库重建**（不可逆） | 提示是否检测到可 import 的 journal |
| `agent-kanban session start --agent <name> [--harness pi\|claude-code\|cursor\|human]` | 注册会话，取 session_id | `{"session_id":"s-7f3a2b","agent_name":"pi-main","lease_expires_at":...}` |
| `agent-kanban session heartbeat` | 续期会话 + 其所有持有任务 | `{"renewed_tasks":["T-0007","T-0008"]}` |
| `agent-kanban session end [--summary "..."]` | 正常关闭；持有中任务自动 release 为 todo | `{"released":["T-0007"]}` |
| `agent-kanban session list [--json]` | 列出会话与新鲜度 | 表格：id / agent / status / 持有 / 心跳 |

### 2.2 任务

| 命令 | 说明 | 守卫 / 备注 |
| --- | --- | --- |
| `agent-kanban task add "<标题>" [-d <描述>] [-p 0-4] [--parent T-0003] [--label a,b] [--blocked-by T-0005] [--check "步骤1,步骤2"] [--estimate 2h] [--json]` | 创建任务（默认 `todo`；`--backlog` 进想法池） | `--blocked-by` 全部 done 时自动 unblock |
| `agent-kanban task list [--status doing,blocked] [--mine] [--label x] [--ready] [--parent T-0003] [--sort priority\|created\|updated] [--limit 50] [--json]` | 列表。`--ready` = 依赖满足且无人持有 | `--mine` 需要 session 上下文 |
| `agent-kanban task show T-0007 [--timeline] [--tail 20] [--plan] [--handoffs] [--json]` | 任务详情。描述、checklist 逐项、依赖（id + 标题 + 完成状态）**默认全部输出**；末尾附服务端给的 `next_actions` | `--timeline` 附事件时间线。`--body` 是**兼容参数**（早先描述要靠它才显示，现在已默认输出；传了不报错） |
| `agent-kanban task claim T-0007 [--ttl 900] [--force]` | 抢占为 doing | 失败→退出码 3；`--force` 会记 `task_reclaimed` |
| `agent-kanban task start T-0007` | `claim` 的别名 | |
| `agent-kanban task progress T-0007 --pct 60 [--note "..."] [--check "已完成 X"] [--uncheck "Y"]` | 更新进度/checklist | 隐式续租；`--pct 100` 不自动流转，仍需 `done`/`review` |
| `agent-kanban task note T-0007 "文本"` | 追加笔记（进时间线） | |
| `agent-kanban task block T-0007 --reason "..." [--until T-0009]` | 转 blocked | `reason` 必填 |
| `agent-kanban task unblock T-0007` | 手动转 todo（覆盖自动判定） | |
| `agent-kanban task review T-0007 [--note "..."]` | doing→review | 建议 pct=100 时执行 |
| `agent-kanban task done T-0007 [--note "..."] [--force]` | →done | 非 review 来源需 `--force`；自动触发下游 unblock |
| `agent-kanban task cancel T-0007 --reason "..."` | →cancelled | |
| `agent-kanban task reopen T-0007 --reason "..."` | 终态→todo | `reason` 必填 |
| `agent-kanban task release T-0007 [--reason "..."]` | doing→todo，保留进度 | |
| `agent-kanban task hold T-0007 --for 2h` | 长租约 | |
| `agent-kanban task dep add\|remove T-0007 T-0008` | 依赖维护；会造成环时报错（退出码 2） | |
| `agent-kanban task rm T-0007 [--force]` | 删除（默认仅 cancelled 可删） | |
| `agent-kanban task edit T-0007 [--title] [-d 描述] [--priority] [--estimate]` | 改元信息 | 记 `task_updated` |

### 2.3 计划

| 命令 | 说明 |
| --- | --- |
| `agent-kanban plan save --task T-0007 --file p.md \| --text "..." [--title "..."]` | 存新版本（同任务自动 version+1，旧的转 `superseded`），同时落 `.kanban/plans/PL-T-0007-03.md` |
| `agent-kanban plan new --file project.md [--title "..."]` | 项目级计划（scope=project，`--task` 省略） |
| `agent-kanban plan list [--task T-0007 \| --project] [--json]` | 版本链列表 |
| `agent-kanban plan show PL-0007 [--json]` | 全文输出（agent 恢复上下文主要读这个） |
| `agent-kanban plan diff PL-0007 PL-0009` | 统一 diff（复用 `diff` 算法，纯 TS 实现） |
| `agent-kanban plan attach T-0007 PL-0007` | 把任务当前计划指向某版本 |
| `agent-kanban plan archive [--json]` | 导出全部计划到 `.kanban/plans/` |

#### 2.3.1 计划版本化（v3 语义变更）

计划**从不原地修改**：每次 `save` 都产生一个新版本，旧版本转 `superseded`
并被 `supersedes_id` 串成链。因此“当时为什么那么决定”永远可回溯。

| 命令 | 说明 |
| --- | --- |
| `agent-kanban plan save --title "..." [--task T-0007] (--body-file <路径> \| --body "...") [--no-attach]` | 保存新版本。`--body` 必填（标题只是一句话，正文才是计划）；任务级计划自动挂到任务上 |
| `agent-kanban plan show <计划号> [--raw]` | 读全文（`--raw` 只输出正文，便于管道） |
| `agent-kanban plan list [--task T-0007] [--scope project\|task] [--all]` | 列出计划；默认只显示 `active`，`--all` 含被顶替的 |
| `agent-kanban plan history <计划号>` | 版本链（新 → 旧），回答“这个计划改了几次” |
| `agent-kanban plan at (--task T-0007) --ts <epoch ms>` | 时间旅行：那时生效的是哪版 |
| `agent-kanban plan attach <计划号> --task T-0007` | 把任务指向某个版本（可回滚到旧版） |

ID 规则：项目级 `PL-0001`，任务级 `PL-T-0007-01`（版本号在 2 位以内左补零，超过自然变宽）。

约束：
- 同一 scope 内只能有一个 `active` 版本（保存时自动把旧的转 `superseded`）
- 项目级计划不能挂到任务上（`attach` 会报错）
- 计划只能引用**本 project** 的任务

```json
  ],

    { "code": "read_handoff", "args": { "id": 12, "task": "T-0007", "summary": "完成 WAL 事务层" } },
    { "code": "claim_new", "args": { "commands": ["agent-kanban task claim T-0011"] } }

```

字段语义要点：

- `my_tasks` **只含本会话持有**的卡（依赖 `listTasks` 的 `mine: true` 过滤，详见 `src/core/tasks.ts` 注释）
- `pending_handoffs` **不含本会话自己写的**（不自己提醒自己）
- `consume` 默认为 true：待接手交接会被标记为已读（`consumed_by`），计数在 `consumed_count`；`--no-consume` 只读预览
- `in_progress[].stale_holder` = 持有者会话已失联但卡尚未被回收（需要人接手）
- **`next_actions` 与 `next_action_items` 是同一批建议的两种形态**：
  前者是给 agent 看的英文串（CLI / MCP / `--json` 的读者），后者是
  `{ code, args }`，给界面按自己的语言拼文案。英文串由 items 渲染而来
  （`renderNextAction`），所以顺序、数量、措辞不会各自漂移。
  `code` 是契约：`takeover` / `read_handoff` / `crash_handoffs` / `continue_mine` /
  `blocked_needs_human` / `claim_new` / `claim_after` / `idle`。
  `args` 里 `tasks` 按语言标点列举（前端用 `list.sep`），`commands` 用 `" / "` 分隔
  （两边都是代码，斜杠不随语言变）。老版本前端不认这个字段时退回 `next_actions`。

`resume` 的三条关键规则：

1. **优先展示主动交接**（voluntary）：agent 认真写的信息量远大于系统合成的；crash 交接仅作兜底
2. **交接即让位**：原持有者已留下未消费的 voluntary 交接时，接管不再受租约阻塞（否则会出现“交接写得越认真，越接不了手”）
3. **进度/checklist 完整保留**：接管只换持有者，不丢任何已完成的记录

### 2.5 CLI 脚本友好性

- `KANBAN_SESSION` 环境变量供长驻 shell / hook 使用
- 所有命令支持 `--json`（单行 JSON，便于 `jq`）
- `watch` 输出 JSONL，一行一事件，便于 agent 用 `while read` 或订阅
- 提供 `agent-kanban task list --ready --json | jq -r '.[0].id'` 这类组合的稳定字段命名

## 3. MCP 契约

### 3.1 设计原则

- MCP 工具是 CLI 的**薄封装**，逻辑全在 core（ADR-6）
- 工具返回值统一带 `next_actions`（字符串数组），专门写给 agent 看，指示下一步动作
- 会话上下文不藏在服务端：每个工具显式带 `session_id` 参数（required），避免 agent 忘记维护隐式状态
- 长文本（计划全文、事件时间线）默认**截断并给出行数**，让 agent 用 `kanban_plan_show` 之类工具按需取全文，避免一次性灌爆上下文

## 4. HTTP / SSE 契约

服务默认 `http://127.0.0.1:7788`。

### 4.0 Op 协议（ADR-10，本地与远程一致的关键）

**`POST /api/op`** 是远程模式的核心入口。客户端发一个 `Op`，server 用 `core/ops.executeOp` 执行，
返回与本地 Backend **完全相同**的结构。

请求：
```http
POST /api/op HTTP/1.1
Content-Type: application/json
X-Kanban-Key: k_9f3a...            # per-project key（ADR-11）
X-Kanban-Session: s-7f3a2b        # 可选：会话标识

{
  "project": "agent-kanban",        // 目标 project（决定鉴权与数据隔离）
  "op": { "kind": "task.create", "params": { "title": "实现存储层", "priority": 0 } }
}
```

响应（与 CLI `--json` / MCP 同一包络）：
```json
{ "ok": true, "data": { "id": "T-0007", "title": "实现存储层", "status": "todo", ... },
  "next_actions": ["Claim: agent-kanban task claim T-0007"] }
```

失败：
```json
{ "ok": false,
  "error": { "code": 3, "name": "CONFLICT", "message": "...", "holder": { ... } } }
```

**HTTP 状态码与退出码映射**（让 RemoteBackend 能原样重建退出码）：

| 退出码 | HTTP | 含义 |
| --- | --- | --- |
| 0 | 200 | 成功 |
| 1 | 400 | USAGE |
| 2 | 409 | STATE（状态非法/不存在） |
| 3 | 409 | CONFLICT |
| 4 | 503 | BUSY（可重试，附 `Retry-After: 1`） |
| 5 | 400 | NOT_INIT |
| 6 | 500 | INTERNAL |
| 7 | 401 / 404 | AUTH（缺 key/错 key → 401；project 不存在 → 404） |

`Op.kind` 全集见 `src/core/ops.ts`，是 CLI / MCP / Web 共享的操作集合。
Op 必须是**纯 JSON**（不得携带函数或连接句柄），这是跨进程传输的前提。

#### 4.0.1 崩溃恢复与计划相关 Op（v3 新增）

```json
{ "project": "agent-kanban",
  "op": { "kind": "context.get", "params": { "tail": 20, "consume": true } } }
```

| Op | params | 返回要点 |
| --- | --- | --- |
| `context.get` | `tail?`, `consume?` | `RecoveryContext`（看板计数 / 失联会话 / 待接手交接 / 我的任务 / 建议动作 / `consumed_count`） |
| `handoff.create` | `task_id`, `summary`, `next_step?`, `blockers?`, `open_questions?` | 新交接的 `id` / `kind` / `next_step` |
| `resume.task` | `task_id`, `force?`, `tail?` | 接管结果：进度保留 + 交接全文 + 时间线 + 剩余 checklist + `next_actions` |
| `doctor.check` | `deep?`, `fix?` | `DoctorReport`（issues + stats） |
| `plan.save` | `scope`, `task_id?`, `title`, `body`, `session_id?`, `attach?` | 新版本计划（默认**不含** `body`） |
| `plan.show` | `plan_id` | 计划全文 |
| `plan.list` | `task_id?`, `scope?`, `status?`, `limit?` | 计划摘要列表（不含 body） |
| `plan.history` | `plan_id` | 版本链（新 → 旧，含 body） |
| `plan.at` | `task_id?`, `scope?`, `ts` | 该时刻生效的计划 |
| `plan.attach` | `task_id`, `plan_id`, `session_id?` | 指向后的计划 |
| `rebuild.check` | `from_seq?`, `write?`, `force?` | `RebuildReport`（drift 逐字段差异 / counts / `ok` / `written`） |

约定：
- 计划类 Op 的**列表与保存响应默认不含 `body`**，只给 `body_lines` / `body_chars`，
  避免一次性把几百行计划灌进 agent 上下文；需要正文用 `plan.show`。
- `rebuild.check` 默认 `write=false`（纯只读校验），有漂移时 `next_actions` 给出修复命令。

#### 4.0.2 Web 看板依赖的 Op

`web/` 不在根 `tsc --noEmit` 的编译范围里，也没有前端测试运行器，
所以前后端“形状漂移”只能靠下面这张表 + `test/web-contract.test.ts` 来拦。

| Op | params | 返回要点 |
| --- | --- | --- |
| `task.get` | `task_id`, `timeline?`, `tail?` | **任务本体**（见下方约定）+ `body` / `checklist` 全文 / `dependencies`（TaskDep 对象数组）/ `unfinished_dependencies`（id 数组）/ `dependency_details`（`{id, title, status, done}`，三个接入面共用）；`timeline=true` 时附带 `timeline` |
| `handoff.list` | `task_id`, `limit?` | 该任务**全部**交接（含已被人消费的）数组，字段同 `RecoveryContext.pending_handoffs` 再加 `consumed_by` / `consumed_at` |
| `task.transition` | `task_id`, `to`, `force?`, `reason?`, `note?` | 转移后的任务 + `unblocked`（因它而自动解阻的下游任务） |
| `events.tail` | `task_id`, `tail?` | 该任务最近事件（前端时间线备用数据源） |
| `plan.show` | `plan_id` | 计划全文（详情页“计划”页签） |

**约定：`task.get` 的 `data` 就是任务本体，不带 `{ task: {...} }` 包装。**
CLI（`agent-kanban task show`）与 MCP（`kanban_task_get`）一直按这个形状消费，
Web 早期版本误按包装形状取值，导致点开任务详情时抛
`Cannot read properties of undefined (reading 'plan_id')`。
要改这个形状时，**必须**同时改 `src/commands/task.ts`、`src/mcp/tools.ts`、`web/src/lib/api.ts`
并更新 `test/web-contract.test.ts`。

**依赖的三个字段别混**（都叫 dependency，形状各不相同）：

| 字段 | 形状 | 用途 |
| --- | --- | --- |
| `dependencies` | `[{ taskId, dependsOnId, createdAt }]` | 底层事实。**字段名是 `dependsOnId`** —— 曾有消费方按 `depends_on_id` 读，输出直接变成 `undefined` |
| `unfinished_dependencies` | `["T-0003"]` | 还没做完的依赖 id |
| `dependency_details` | `[{ id, title, status, done }]` | **界面用这个**：id + 标题 + 是否已完成。不让各接入面自己拼，猜错字段名的代价就是静默输出 `undefined` |

#### 4.0.3 事件一律 snake_case，且必须过 `eventToJson`

**所有**返回事件的地方，字段名一律 snake_case，唯一出口是 `rows.ts` 的 `eventToJson`：

| 字段 | 说明 |
| --- | --- |
| `seq` / `ts` | 事件序号 / 时间戳 |
| `session_id` | 谁触发的。**`null` 是合法值**（那次操作没关联会话），前端把它渲染成 `system` 是对的 |
| `type` | 事件类型 |
| `task_id` / `plan_id` / `project_key` | 关联对象 |
| `data` | 事件载荷，普通 JSON，**不做键名转换** |

四个出口，形状必须一致：

| 出口 | 位置 | 消费者 |
| --- | --- | --- |
| `events.list` | `ops.ts` | 外部 / 调试 |
| `events.tail` | `ops.ts` | Web 时间线（无内嵌 timeline 时的兜底） |
| `task.get` 的 `timeline` | `ops.ts` | Web 时间线主路径；MCP `kanban_task_get` 同源 |
| `/api/events` + `/api/stream`(SSE) | `http.ts` | 调试端点 / 看板实时刷新 |

> **曾经的事故**：这四处都把领域对象 `KanbanEvent`（驼峰 `sessionId` / `taskId` / …）
> 直接 `JSON.stringify` 出去——`rows.ts` 只有 `taskToJson` / `sessionToJson`，
> 事件这条路漏了第三处。前端 `task-detail.tsx` 读 `e.session_id` 恒为 `undefined`，
> 每条都走 `?? "system"` 兜底，于是**每张卡的时间线都显示 system**。
> 库里 session_id 是有真值的（`s-xxxxxx`），只是没送到前端。
>
> 难查在于症状与“这些都是系统事件”完全一样：不报错、不空屏、其它页签全正常。
> 守卫在 `test/web-contract.test.ts` 的“事件字段形状” describe 与
> `scripts/verify-web.ts` 的 §4.2 —— 新增事件出口时两处都要跟上。

另外：新增 Op 时除了本节，还要同步
`src/core/ops.ts` 的 switch 与联合类型、`docs/plan/002-接口契约.md` 的 §4.0、
以及（如需给 agent 用）`src/mcp/tools.ts` 的工具映射表。

### 4.1 认证（v3 token 模型）

- 所有 `/api/*`（除 `/api/health`）需 `X-Kanban-Key: k_xxx`
- 服务端查 `tokens` 表：**SHA-256 比对 + 未吊销 + 未过期 + project 白名单校验**（`src/core/tokens.ts`）
- 角色分两种：
  - `admin`：可访问**全部** project，并可调用 `/api/admin/*`（建 project / 签发 / 吊销 token）
  - `project`：只能访问 `projects` 字段里显式列出的 project（一个 token 可授权多个）
- 请求的 `project` 不在白名单内 → 403（区分于 401：“token 有效但无权访问这个 project”）
- SSE 因 EventSource 不能带 header，改用 `?key=` query 参数
- 写接口的 session 身份来自 `X-Kanban-Session`，缺省则由 server 侧从 body 的 `params.session_id` 取
- **本地模式不启用鉴权**（直接用 LocalBackend，不经过 HTTP）
- server 首次启动自动生成管理员 token，**同时**写入 server 的 `config.toml`（运维可见）与 `tokens` 表（运行时鉴权），二者缺一不可

### 4.3 SSE

```
GET /api/stream?project=agent-kanban&after=1042&key=k_xxx

HTTP/1.1 200 OK
Content-Type: text/event-stream
Cache-Control: no-cache
Connection: keep-alive

retry: 3000
id: 1042
event: task_progress
data: {"seq":1042,"ts":1771432812345,"project":"agent-kanban","type":"task_progress","task_id":"T-0007","data":{"pct":60}}

: keepalive

id: 1043
event: task_claimed
data: {...}
```

- **project 隔离**：每个连接只推自己 project 的事件（`events.project_key` 过滤）
- **断线续传**：浏览器 `EventSource` 自动带 `Last-Event-ID`；服务端取 `max(Last-Event-ID, after)` 回放
- **心跳**：每 15s 发 `: keepalive` 注释帧，防中间设备断连
- **事件名**：用事件 `type` 作为 `event:` 字段，前端可按类型增量更新
- **实现**：v1 用 1s 轮询 `events WHERE project_key=? AND seq>?`（跨进程也能工作，零 IPC 复杂度）

### 4.4 静态资源

- `/` → `web/dist/index.html`（Vite + React 19 + Tailwind v4 + shadcn 构建产物）
- `/assets/*` → 带内容哈希的资源，`Cache-Control: public, max-age=31536000, immutable`
- **SPA 回退**：任何非 `/api/` 的未知路径返回 `index.html`（前端用 History API 路由）
- `index.html` 本身用 `Cache-Control: no-cache`——否则发版后用户会拿到旧壳
- **路径穿越防护**：`resolve()` 后校验目标仍在 `web/dist` 内，否则 403
- 未构建时退回内置占位页（页面里直接给出构建命令，而不是 404）
- 构建 `bun run web:build`；开发 `bun run web:dev`（Vite 把 `/api` 代理到本 server）
- 无外部 CDN 依赖，纯离线可用

### 5.1 拖拽与状态机

拖拽只走状态机允许的转移，前端**先预检**，不合法时当场说明原因而不发请求：

| 拖到 | 结果 | 提示 |
| --- | --- | --- |
| 进行中 | ❌ 拒绝 | “「进行中」必须先认领，请用卡片菜单的「认领任务」” |
| 阻塞 / 已取消 | ❌ 拒绝 | “转阻塞需要填原因，请用卡片菜单的「标记阻塞」” |
| 已完成（非从待评审） | ❌ 拒绝 | “只有「待评审」能直接完成” |
| 终态 → 其他 | ❌ 拒绝 | “终态任务需要先「重新打开」” |
| 合法转移 | ✅ 调 `task.transition` | 失败时（被抢占）弹冲突对话框，提供“强行接管” |

### 5.2 主题：shadcn 中性灰阶 + 语义彩色状态

令牌分两层，职责不重叠：

- **中性色**（背景/卡片/边框/文字/主色）：纯灰阶，`chroma` 一律为 0。
  纸面是白的，线条是灰的，界面里不出现任何色偏——彩色状态标签因此跳得最明显。
- **状态色**（`--status-*`）：保持语义彩色，**不中性化**。看板有 7 个状态 ×
  亮暗两套 = 14 个色值，若一并灰阶化，“这条卡在做什么”就只能靠读文字判断了。

每个任务状态**只定义一个颜色**，淡底/边框由 CSS `color-mix()` 派生：

| 令牌 | 亮色 | 暗色 | 语义 |
| --- | --- | --- | --- |
| `--background` | `#FFFFFF` 纯白 | `#252525` 近黑 | 纸面 |
| `--card` | `#FFFFFF` 纯白 | `#333333` | 卡片靠阴影与边框分层，不靠底色 |
| `--foreground` | `#252525` 近黑 | `#FAFAFA` | 正文 |
| `--muted` | `#F5F5F5` | `#444444` | 次要底色 |
| `--border` | `#E5E5E5` | `#444444` | 线条 |
| `--primary` | `#252525` 近黑按钮 | `#FAFAFA` 白按钮 | 主动作 |
| `--status-todo` | 赭石 | 提亮 | 待办 |
| `--status-doing` | 墨绿 | 提亮 | 进行中 |
| `--status-blocked` | 酒红 | 提亮 | 阻塞 |
| `--status-done` | 草绿 | 提亮 | 完成 |
| `--status-review` | 黛紫 | 提亮 | 待评审 |
| `--status-backlog` | 淡藤灰 | 提亮 | 想法池 |
| `--status-stale` | 琥珀 | 提亮 | 会话失联 |

设计规则：

- **`--primary` 刻意不是 `--status-doing`**：主色若也是墨绿，“主按钮”与“进行中”会混同，
  按钮就失去了“这不是状态”的属性
- 暗色**不是反色**：色相不变，状态色整体提明度加彩度（墨绿/酒红在深底会隐进背景）；
  中性色则按标准灰阶重排，不跟亮色做暖度补偿
- 标题用衬线、正文用无衬线，中文回退到系统字体
- 状态色经 `@theme inline` 接入 Tailwind（`text-status-doing`），不写裸色值
- 前端默认跟随 `localStorage` 记忆的偏好，首次跟随系统

### 5.3 约束

- 所有用户输入文本用 `textContent` 渲染，**禁 `innerHTML`**（token 存 localStorage，XSS 可读）
- token 默认存 localStorage（刷新免登录）；一次性登录链接读完后立即 `replaceState` 清理 URL
- 全部写操作走 `POST /api/op`，与 CLI / MCP 同一套语义，前端不自行实现业务规则
- SSE 收到事件后**防抖 400ms** 再重拉（agent 批量写时避免请求风暴）

## 6. 事件 payload 稳定性

前端与 agent 都可能依赖 `data` 字段名，故约定：

- 只**新增**字段，不删除、不改语义；改语义必须新事件 type
- `task_progress.data` 保证含 `pct`、`prev_pct`
- `task_claimed.data` 保证含 `prev_assignee`（可能为 null）、`ttl_ms`
- 所有事件的 `data` 至少是 `{}`（不会是 null），便于 `jq '.data.pct // empty'`

## 7. 兼容性

- `meta.schema_version` 单调递增，`agent-kanban init` / 任何命令启动时自动迁移（幂等）
- 迁移失败 → 退出码 5 并提示 `agent-kanban init --force`（会备份 DB）

### 7.1 schema 版本历史

| 版本 | 变更 | 兼容性影响 |
| --- | --- | --- |
| v1 | 初始 schema | — |
| v2 | 引入 project 层级（ADR-9）：`projects` 表、`project_key` 列、`project_counters` | `tasks.id` 从全局 UNIQUE 改为 `(project_key, id)` |
| v3 | 引入 token 权限模型（ADR-13）：`tokens` 表，废弃 `projects.api_key_hash` 鉴权 | 旧 project key 明文不可恢复，**需重新签发 token** |
| v4 | `task_deps` 补 `project_key`（ADR-9 遗漏），主键改为 `(project_key, task_id, depends_on_id)` | 无需用户操作，自动回填 |

### 7.2 事件 payload 稳定性（rebuild 依赖）

`events` 是唯一事实来源，`tasks/plans/handoffs/task_deps` 都只是它的投影。
`agent-kanban rebuild` 的正确性**完全依赖**每条事件的 `data` 携带了重建所需的全部信息。
因此约定（修改事件 payload 时必须同步）：

| 事件 | `data` 必须包含 |
| --- | --- |
| `task_created` | `title`, `body`, `status`, `priority`, `labels`, `parent_id`, `checklist`（含 `done_at`/`by`）, `estimate_ms` |
| `task_claimed` | `prev_assignee`, `prev_status`, `ttl_ms`（`lease_expires_at` = `ts + ttl_ms`） |
| `task_progress` | `pct`, `prev_pct`；checklist 变更时带**完整快照** `checklist` |
| `task_updated` | `fields` = **新值**映射（`{title: "新标题"}`），不是字段名列表 |
| `task_removed` | `removed_deps`（连带删除的依赖边） |
| `task_blocked` | `reason` |
| `plan_created` / `plan_superseded` | `handoff`→ 完整计划行（`id`/`scope`/`task_id`/`version`/`title`/`body`/`status`/`author_session_id`/`created_at`/`supersedes_id`） |
| `handoff_created` | `handoff` → 完整交接行（含 `session_id`，因为 crash 交接由 system 发出但归属原持有者） |
| `handoff_consumed` | `handoff_id`, `by_session` |

**不参与 rebuild 比较的字段**：`lease_expires_at`、`updated_at`。
理由：它们由心跳/续租前移，而续租不写事件（否则事件量会被心跳淹没），
重建后回到“最后一次有事件时的值”是设计常态，首次 heartbeat 会刷新。
- 事件结构变更走 `event_schema` 版本字段，老事件读取时按版本兼容处理
- **v1 → v2 迁移**（引入 project 层级）：
  1. 建 `projects` 表
  2. 各表新增 `project_key` 列（SQLite 的 `ALTER TABLE ADD COLUMN`）
  3. 回填：按本地目录名 slug 作为默认 project key，存量行统一填该值
  4. 插入默认 project 记录（`api_key_hash = NULL`，即本地模式不鉴权）
  5. 重建相关索引
  迁移后本地项目**零配置继续可用**：不传 `--project` 就是默认 project。
