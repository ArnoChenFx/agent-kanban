# Agent 看板（agent-kanban）总体设计

> 状态：设计定稿；M1–M3 已实现（存储层 / 双模式 project 层级 / 崩溃恢复 / 计划版本化 / 事件重放）
> 决策：TypeScript + Bun · SQLite（WAL） · **本地 / 远程双后端** · **project 层级** · CLI + MCP 双接入 · CLI 泳道视图 + Web 看板（SSE 实时）

## 0. 两种运行模式

看板支持两种部署形态，**上层命令完全一致**，差别只在数据落在哪里：

### 模式 A：本地（默认）

```
$ agent-kanban task add "实现存储层"        # 在项目目录里直接跑
```

- 存储位置：`<项目根>/.kanban/kanban.db`（与目录同生命周期）
- project 层级：**自动单 project**，key 由目录名派生（`agent-kanban`），无需任何配置
- 认证：不需要（已有文件系统权限）
- 适用：单机开发、多会话 agent 共享一份任务

### 模式 B：远程（云端 server）

```
$ kanban --server https://kanban.corp --project agent-kanban \
         --key k_9f3a... task add "实现存储层"
```

- 存储位置：server 端的 SQLite（一个 server 管多个 project）
- project 层级：显式指定，**按 project_key 隔离**（一个 project 的 agent 看不到另一个的卡）
- 认证：**per-project key**（每个 project 一个 key，泄露只影响单个 project）
- 适用：多机器 agent 共享同一份看板、集中看板服务器

两种模式共用同一套 CLI 命令、同一份业务逻辑（core）、同一个前端看板。
区别只在 **Backend 实现**（见 ADR-10）：

```
   kanban CLI（同一份命令代码）
        │
        ├── LocalBackend   ──直接调用──►  core（同一进程）
        │
        └── RemoteBackend  ──HTTP /api/op──►  server ──►  core
```

## 1. 要解决的问题

同一个项目里会同时跑多个 agent 会话（pi、Claude Code 等），另外 agent 可能因为崩溃、被杀、超时而中断。本项目要提供一块**共享的项目级看板**，做到：

| 编号 | 目标 | 落地机制 |
| --- | --- | --- |
| G1 | 不同会话 agent 共享同一份任务列表 | 本地：项目内 `.kanban/kanban.db`；远程：server 端 DB。SQLite WAL 支撑多进程并发 |
| G2 | 任务进度可持久化、可量化 | `tasks.progress`(0-100) + `checklist` + 不可变事件流 |
| G3 | 历史计划可追溯 | `plans` 表按 scope + version 版本化，`supersedes_id` 串成链，可 diff |
| G4 | agent 意外停止后能接上 | 会话租约 + 心跳 + 僵尸自动回收 + handoff 交接事件 + `agent-kanban context`/`resume` |
| G5 | 人与 agent 同屏观察 | `agent-kanban board` 终端泳道视图 + HTTP/SSE Web 看板 |
| G6 | 三种接入行为一致 | CLI / MCP / HTTP 共用同一份 `src/core`，无分叉逻辑 |
| G7 | 本地与远程行为一致 | LocalBackend / RemoteBackend 共用同一 Op 协议与同一 core |
| G8 | 多 project 隔离 | `project_key` 贯穿 tasks/events/plans/handoffs；per-project key 鉴权 |

**非目标（v1 明确不做）**

- 不做 Jira 级权限、审批流、多租户组织架构
- 不做跨 server 的分布式协调（v1 单 server；本地模式单进程）
- 不做自动任务分解（agent 自己用 `agent-kanban task add --parent` 拆子任务即可）
- 不做看板字段自定义工作流引擎（状态机固定，够用且可预测）
- 不做多用户账号体系（用 per-project key 代替，见 ADR-11）

## 2. 架构总览

```
   agent 会话 A (pi)          agent 会话 B (claude)         人类
        │                            │                          │
   kanban CLI                   kanban CLI / MCP            Web 看板
        │                            │                       (127.0.0.1:7788)
        └────────────┬───────────────┴──────────────┬───────────┘
                     │                              │
              ┌──────▼──────────────────────────────▼──────┐
              │            src/core（唯一逻辑实现）        │
              │  tasks / sessions / plans / handoff /      │
              │  context / doctor / events                 │
              └──────┬──────────────────────────────┬──────┘
                     │                              │
              ┌──────▼───────┐              ┌───────▼──────┐
              │  store.ts    │              │  HTTP + SSE  │
              │ BEGIN IMMEDIATE 事务        │  实时推送    │
              └──────┬───────┘              └───────┬──────┘
                     │                              │
              ┌──────▼──────────────────────────────▼──────┐
              │        .kanban/kanban.db（WAL 单文件）      │
              │   tasks / events / sessions / plans /      │
              │   handoffs / deps                           │
              └──────┬──────────────────────────────────────┘
                     │ 导出
       ┌─────────────▼──────────────┐
       │ .kanban/journal/*.jsonl    │  ← 可入 git，人可读、可 diff、可审阅
       │ .kanban/plans/*.md         │  ← 计划归档，人可读
       │ .kanban/snapshots/*.json   │  ← 看板快照，DB 丢失可重建
       └────────────────────────────┘
```

四条设计主线：

1. **事件是真相，任务表是投影**：所有状态变化先写 `events`（只追加），同时在同一事务内更新 `tasks` 投影。事件流可以重放重建全部状态。
2. **租约代替硬锁**：任务归属不是永久的，而是带过期时间的租约。agent 消失后租约过期，卡自动回到可认领状态，**但进度不丢**。
3. **交接是一等公民**：agent 收工前主动写 handoff；崩溃时系统自动合成 handoff。新会话 `context` 时优先读它，不必从时间线里猜发生了什么。
4. **Op 是跨进程的稳定协议**：命令层不直接调 core，而是构造 `Op{kind, params}` 交给 `Backend.execute()`。本地 Backend 直调，远程 Backend 发 HTTP，server 端收到同样的 Op 调同一份 core——所以**两种模式、三种接入的行为必然一致**（ADR-10）。
5. **交接即让位**：持有者留下未消费的主动交接后，接管不再受租约阻塞（否则“交接写得越认真，越接不了手”）。
6. **重建必须无损**：`rebuild` 重建出的投影要与原投影逐字段相等，因此每个事件的 payload
   必须携带重建所需的全部信息（详见 §7.1）。隐式修改投影字段的地方（如 `task done` 隐式把
   progress 提到 100）也必须补发事件，否则事件流就不是完整历史。

## 2.1 双模式与 project 层级的 ADR

### ADR-9 project 层级：`project_key` 贯穿业务表

新增 `projects` 表；`tasks` / `events` / `plans` / `handoffs` / `task_deps` 各增 `project_key` 列，所有查询强制按它过滤。

- 理由：远程 server 要在一个进程里管多个项目；没有这层就必然串项目。
- ⚠️ `task_deps` 是在实现 `rebuild` 时才发现漏掉的（schema v4 补上）。
  漏它的后果在单 project 下完全不可见，但多 project 下：主键 `(task_id, depends_on_id)` 不含 project，
  而 T-编号是 per-project 的 → 两个 project 的同名依赖撞同一条记录，
  且 `INSERT OR IGNORE` 会**静默**丢边。这类“平时不出事、上规模就出错”的遗漏最难查，
  所以凡是声称“`project_key` 贯穿业务表”的地方，都要有对应测试。
- `sessions` 表**不**加 `project_key`：会话是 agent 进程的身份，一个会话完全可以跨项目工作。租约回收因此是全局的。
- 本地模式：打开 `.kanban/` 时自动确保存在一个默认 project（key 取目录名 slug），用户永远不需要传 `--project`。

### ADR-10 Op 执行层：命令层与 core 解耦

命令层从“直接调 core 函数”改为“构造 `Op` 交给 `Backend.execute()`”：

```
命令层 ──构造 Op──► Backend.execute(op)
                     ├─ LocalBackend  ──► core/ops.executeOp(db, op)   （同进程）
                     └─ RemoteBackend ──► POST /api/op ──► server ──► core/ops.executeOp
```

- 理由 1：**行为一致性免费获得**。本地与远程走同一个 switch 分支，不存在“本地能用远程报错”的漂移。
- 理由 2：MCP 与 Web 也能复用同一 Op 层，不需要第三套实现。
- 代价：多一层序列化（远程模式下 Op 是 JSON）。可接受——agent 场景对延迟不敏感。
- 约束：`Op` 必须是**纯数据**（可 JSON 序列化），不得携带函数或数据库句柄。

### ADR-11 认证：per-project key

- 每个 project 一个 key（`k_` + 32 hex），**只在创建时明文显示一次**，库里只存 SHA-256 哈希。
- 请求携带 `X-Kanban-Key` 头（或 SSE 的 `?key=`），服务端按目标 project 校验。
- 本地模式不需要 key（文件系统权限已足够）；远程模式缺 key 或 key 不对 → 退出码 7（新增 AUTH）。
- 不做多用户账号体系：收益有限而复杂度高（密码管理、token 刷新、组织结构），per-project key 已覆盖“多项目共享服务器”的实际需求。
- 已知局限：key 不区分人/agent，审计靠 `sessions.agent_name` 自报。

### ADR-12 双模式的配置来源

| 配置 | 优先级 | 说明 |
| --- | --- | --- |
| server URL | `--server` > `KANBAN_SERVER` > `.kanban/config.toml` > **本地模式** | 一旦有 server URL 即进入远程模式 |
| project key | `--project` > `KANBAN_PROJECT` > 配置文件 > **本地模式自动派生** | 远程模式必填 |
| api token | `--key` > `KANBAN_KEY` > 配置文件 | 本地模式忽略 |

配置存放于**项目级** `<project>/.kanban/config.toml`（不引全局配置）：
一个仓库的 agent 天然知道自己属于哪个 project，配置跟着仓库走最自然；
需要共享同一 server 的多个仓库各自拷一份即可（内容相同，维护成本可接受）。

```toml
mode = "remote"

[server]
url   = "https://kanban.corp:7788"
token = "k_xxx"

[project]
key = "agent-kanban"
```

**关键性质**：配置可以指向远程 server，此时本地**不需要数据库**。
所以“存在 config.toml” ≠ “本地有数据”—— 路径查找必须用宽松版
（`findKanbanDirLoose`：只要 `.kanban/` 存在就算，不要求里面有 `kanban.db`）。

### ADR-13 token 权限模型：项目级 + 管理员

v2 的 `projects.api_key_hash` 只能表达 "1 个 project ↔ 1 个 key"，无法满足：
一个 token 授权多个 project、管理员 token。因此升级为 `tokens` 表：

| 角色 | 权限 | 表达方式 |
| --- | --- | --- |
| `admin` | 管理 project、签发/吊销 token、访问所有 project | `projects = NULL` |
| `project` | 只能访问白名单内的 project | `projects = ["a","b"]` |

- 库里只存 `key_hash`（SHA-256），明文只在签发/轮换时返回一次
- 管理员 token **首次启动自动生成**，写入 server 的 `config.toml`（运维可读）
  **并且注册到 `tokens` 表**（鉴权的唯一依据）—— 两处缺一不可
- 401 vs 403 分工明确：401 = token 无效/已吊销/已过期（该换 token）；
  403 = token 有效但不是 admin（该换权限）
- **不泄漏 project 是否存在**：对不存在的 project 与无权的 project 返回同样的 403
- 支持**预授权**：token 可授权尚不存在的 project，建完 project 即生效
  （运维顺序“先发 token 再建 project”很常见）
- admin API 单独前缀 `/api/admin/*`，要求 admin 角色；Web 管理页在 `/admin`


## 3. 关键技术决策（ADR）

### ADR-1 事件溯源 + 物化视图

`events` 表只追加、永不修改；`tasks`/`sessions`/`plans` 是它的投影。

- 理由：崩溃恢复、审计、"这个任务谁动过"、DB 损坏后重建、跨 agent 交接历史，全部依赖完整时间线；纯状态表会丢失"为什么变成这样"。
- 代价：每次写多一条事件；投影逻辑要保证与事件一致。
- 兜底：`agent-kanban rebuild` 从事件重放重建投影，并有测试断言重放结果与原投影逐字段一致。

### ADR-2 SQLite + WAL + `BEGIN IMMEDIATE` + 条件 UPDATE（乐观并发）

**已实测验证**（Bun 1.4.2 / Windows，探针脚本）：

- `bun:sqlite` 默认 `journal_mode=wal` ✅
- 8 个并发进程 × 25 次 `BEGIN IMMEDIATE` 短事务，**0 次 `SQLITE_BUSY`** ✅
- `UPDATE tasks SET assignee=? WHERE id=? AND assignee IS NULL` 在 8 进程争抢下**恰好 1 个赢家**，其余 200 次正确返回 `changes=0` ✅
- ⚠️ 陷阱：`new Database(path, { create: false })` 直接抛 `SQLITE_MISUSE`，必须写 `{ readwrite: true, create: false }`
- ⚠️ 陷阱：连接必须设 `PRAGMA busy_timeout=5000`，否则瞬时并发直接报 locked

结论：agent 工作负载是**低频写**（一次状态变更一次事务），WAL 串行化写完全够用，不需要引入 Postgres/Redis。

### ADR-3 人可读任务 ID（`T-0007`）而非 UUID

- 理由：agent 在自然语言、提交信息、handoff 里反复引用任务号，`T-0007` 可直接读；UUID 会导致 agent 编造不存在的 ID。
- 生成：`BEGIN IMMEDIATE` 事务内 `SELECT MAX(seq)+1`，天然无碰撞。
- 任务同时保留内部自增 `seq`（SSE 游标/排序用），ID 单独存 `id` 列。

### ADR-4 租约（lease）而非永久 owner

`tasks.lease_expires_at` 默认 15 分钟。任何写操作（progress/note/claim）隐式续期；`agent-kanban heartbeat` 显式续期；`--ttl` 可调；`agent-kanban hold --for 2h` 支持长任务。

- 理由：agent 崩溃是常态（不是异常），不能用"必须先解锁"这种需要清醒agent才能执行的协议。
- `blocked` 状态**不因租约过期而回收**（阻塞是持久事实，不是运行时状态）。

### ADR-5 DB 不入 git，用可导出的 journal 代替

`kanban.db` 是二进制，git diff 无意义且并发写时提交易损坏。策略：

- `.kanban/kanban.db*` → `.gitignore`
- `agent-kanban export` 导出事件为 `.kanban/journal/events-YYYYMMDD.jsonl`（**入 git**，人可读、可 review、冲突可人工按 seq 合并）
- `agent-kanban plan save` 同时落一份 `.kanban/plans/PL-0007.md`（**入 git**，人可读）
- `agent-kanban import` 从 journal 重建 DB → 换机器/新 clone 后 `import` 即恢复全部上下文
- 备用模式 `KANNABAN_SYNC=db`（直接跟踪 db 文件）供单写者团队使用

### ADR-6 单 core 三前端

`src/core/*` 是纯函数式业务层，CLI（`src/commands`）、MCP（`src/mcp`）、HTTP（`src/server`）都只做参数解析与输出格式化。禁止在前端层写业务判断，否则三处行为必然漂移。

### ADR-7 handoff（交接）为一等公民

agent 之间的知识传递不靠"你去翻时间线"，而是显式的 `handoffs` 记录，带 `summary` / `next_step` / `blockers` / `open_questions` 四个结构化字段，并有 `consumed_by` 标记谁已接手。

### ADR-8 进度双表示

`progress`(0-100 整数) 用于看板和粗粒度恢复；`checklist`(JSON 子项) 用于细粒度恢复。两者都写，恢复时优先呈现 checklist 的未完成项——这是新 agent 最需要的"接着做什么"。

## 4. 数据模型

### 4.1 ER 概览

```
sessions 1───┬──* tasks(assignee_session_id)      当前持有者
            ├──* events(session_id)               谁做了什么
            ├──* handoffs(session_id)             谁交接了什么
            └──* plans(author_session_id)         谁写的计划

tasks   1───* plans(task_id, scope='task')        任务级计划版本链
tasks   *───* task_deps                           任务依赖（无序对）
tasks   1───* handoffs(task_id)                   任务交接历史
```

### 4.2 表结构

> 以下为权威定义，与 `src/core/schema.sql` 一一对应。改表先改这里。

```sql
-- ========== 项目级元信息 ==========
CREATE TABLE meta (
  k TEXT PRIMARY KEY,
  v TEXT NOT NULL
);
-- 键：schema_version, project_name, created_at, default_ttl_ms, grace_ms

-- ========== 会话：一次 agent 运行 ==========
CREATE TABLE sessions (
  id             TEXT PRIMARY KEY,          -- s-7f3a2b（base36，6 位）
  agent_name     TEXT NOT NULL,             -- 人可读名，如 pi-main / claude-fix
  harness        TEXT,                      -- pi | claude-code | cursor | human
  cwd            TEXT NOT NULL,
  pid            INTEGER,                   -- 诊断用（进程存活探测），非强约束
  status         TEXT NOT NULL,             -- active | idle | closed | crashed
  started_at     INTEGER NOT NULL,          -- epoch ms
  last_seen_at   INTEGER NOT NULL,          -- 最后心跳（任何写操作刷新）
  lease_expires_at INTEGER,                 -- 会话级租约
  meta           TEXT                       -- JSON：{ model, host, ... }
);
CREATE INDEX idx_sessions_status ON sessions(status, last_seen_at);

-- ========== 任务 ==========
-- 关键：id 是 **per-project 唯一**（UNIQUE(project_key, id)），不是全局唯一。
-- 因为 agent 口语里的 "T-0007" 必须只指向本 project 的卡。
CREATE TABLE tasks (
  seq              INTEGER PRIMARY KEY AUTOINCREMENT,  -- 全局唯一序号（SSE 游标/排序）
  id               TEXT NOT NULL,             -- T-0007（per-project 唯一）
  project_key      TEXT NOT NULL,             -- 所属 project（ADR-9）
  title            TEXT NOT NULL,
  body             TEXT,                      -- markdown 详细描述
  status           TEXT NOT NULL,             -- backlog|todo|doing|blocked|review|done|cancelled
  priority         INTEGER NOT NULL DEFAULT 2,-- 0 最高 … 4 最低
  assignee_session_id TEXT,                   -- 当前租约持有者（可空）
  lease_expires_at INTEGER,                  -- 任务级租约到期时间
  progress         INTEGER NOT NULL DEFAULT 0,-- 0..100
  checklist        TEXT,                      -- JSON：[{text, done, done_at, by}]
  labels           TEXT,                      -- JSON：["backend","urgent"]
  parent_id        TEXT,                      -- 父任务 T-0003
  plan_id          TEXT,                      -- 当前生效的计划版本
  block_reason     TEXT,                      -- 阻塞原因
  created_by       TEXT,                      -- session id
  created_at       INTEGER NOT NULL,
  updated_at       INTEGER NOT NULL,
  started_at       INTEGER,
  finished_at      INTEGER,
  estimate_ms      INTEGER,
  spent_ms         INTEGER
);
-- 看板主查询路径：project + 状态 + 优先级
CREATE UNIQUE INDEX idx_tasks_project_id ON tasks(project_key, id);
CREATE INDEX idx_tasks_status   ON tasks(project_key, status, priority, created_at);
CREATE INDEX idx_tasks_assignee ON tasks(assignee_session_id);
CREATE INDEX idx_tasks_parent   ON tasks(project_key, parent_id);

-- ========== per-project 任务号计数器（保证 ID 永不复用）==========
-- 不用 MAX(id) 的原因：删除任务后 MAX 回退，会把已删除的 ID 重新分配，
-- 而历史事件/交接里仍引用那个 ID → 审计链条断裂。
CREATE TABLE project_counters (
  project_key   TEXT PRIMARY KEY,
  next_task_num INTEGER NOT NULL
);

-- ========== 任务依赖（A 依赖 B，B 完成则 A 可做）==========
-- project_key 不可省（schema v4 补上）：T- 编号是 per-project 的，
-- 没有它两个 project 的同名依赖会撞车，且 INSERT OR IGNORE 会静默丢边
CREATE TABLE task_deps (
  project_key TEXT NOT NULL,
  task_id     TEXT NOT NULL,
  depends_on_id TEXT NOT NULL,
  created_at  INTEGER NOT NULL,
  PRIMARY KEY (project_key, task_id, depends_on_id)
);

-- ========== 事件：不可变，只追加 ==========
CREATE TABLE events (
  seq         INTEGER PRIMARY KEY AUTOINCREMENT,  -- 全局单调 = SSE 游标
  ts          INTEGER NOT NULL,                    -- epoch ms
  session_id  TEXT,                               -- 系统事件为 'system' / NULL
  type        TEXT NOT NULL,                       -- 见事件类型表
  task_id     TEXT,
  plan_id     TEXT,
  project_key TEXT,                               -- 所属 project（ADR-9）
  data        TEXT                                 -- JSON payload
);
CREATE INDEX idx_events_task    ON events(task_id, seq);
CREATE INDEX idx_events_ts      ON events(ts);
CREATE INDEX idx_events_project ON events(project_key, seq);

-- ========== 计划（版本化）==========
CREATE TABLE plans (
  id           TEXT PRIMARY KEY,      -- PL-0007（项目级） / PL-T-0003-02（任务级）
  project_key  TEXT NOT NULL,         -- 所属 project（ADR-9）
  scope        TEXT NOT NULL,         -- project | task
  task_id      TEXT,                  -- scope=task 时有效
  version      INTEGER NOT NULL,      -- 同 scope 内自增，从 1 开始
  title        TEXT NOT NULL,
  body         TEXT NOT NULL,         -- markdown 全文
  status       TEXT NOT NULL,         -- active | superseded | draft
  author_session_id TEXT,
  created_at   INTEGER NOT NULL,
  supersedes_id TEXT
);
CREATE INDEX idx_plans_scope ON plans(project_key, scope, task_id, version);

-- ========== 交接（恢复的核心）==========
CREATE TABLE handoffs (
  id           INTEGER PRIMARY KEY AUTOINCREMENT,
  project_key  TEXT NOT NULL,         -- 所属 project（ADR-9）
  task_id      TEXT NOT NULL,
  session_id   TEXT NOT NULL,         -- 交接发出方
  kind         TEXT NOT NULL,         -- voluntary(主动) | crash(崩溃自动) | reclaim(被接管时附注)
  summary      TEXT NOT NULL,         -- 做了什么
  next_step    TEXT,                  -- 交接里写给接手方的下一步建议
  blockers     TEXT,                  -- JSON 数组
  open_questions TEXT,                -- JSON 数组
  created_at   INTEGER NOT NULL,
  consumed_by  TEXT,                  -- 接手方 session id
  consumed_at  INTEGER
);
CREATE INDEX idx_handoffs_task    ON handoffs(project_key, task_id, id);
CREATE INDEX idx_handoffs_pending ON handoffs(project_key, consumed_by, id);
```

### 4.3 为什么事件表不拆细

一个 agent 任务会产生几十条事件（claim/progress/note/…）。拆成 `task_notes` / `task_progress` 等多表会让"完整时间线"变成 N 路 join，破坏 ADR-1 的重放能力。代价是读时间线要 `json_extract`，在几百条量级完全可接受；用 `data` 存结构化 payload 已足够查询。

## 5. 任务状态机

### 5.1 状态集合

| 状态 | 含义 | 谁可进入 |
| --- | --- | --- |
| `backlog` | 想法池，尚未澄清，不应被随意认领 | 人 / agent 任意 |
| `todo` | 已就绪可做（依赖已满足） | 人 / agent；或 blocked 在依赖满足时自动 |
| `doing` | 有人正在做（有租约） | 通过 `claim`（抢占） |
| `blocked` | 被阻塞，必须带 `reason` | 人 / agent |
| `review` | 产出待评审（人确认） | doing 完成时 |
| `done` | 完成 | review 确认，或 doing `--force` |
| `cancelled` | 取消（终态） | 人 / agent |

### 5.2 转移表

| from | to | 守卫条件 | 产生事件 |
| --- | --- | --- | --- |
| backlog | todo | — | `task_ready` |
| backlog | cancelled | — | `task_cancelled` |
| todo | doing | 抢占成功（`assignee IS NULL` 或原持有者已僵死） | `task_claimed` |
| todo | blocked | 必须 `reason` | `task_blocked` |
| todo | cancelled | — | `task_cancelled` |
| doing | blocked | 必须 `reason` | `task_blocked` |
| doing | todo | `release`，或租约过期（僵尸回收） | `task_released` / `task_reclaimed` |
| doing | review | `progress=100` 或 `--force` | `task_review` |
| doing | done | `--force`（跳过评审） | `task_done` |
| blocked | todo | **自动**：全部依赖 `done` | `task_unblocked` |
| blocked | doing | 先 `unblock` 再 `claim` | `task_claimed` |
| blocked | cancelled | — | `task_cancelled` |
| review | done | 确认通过 | `task_done` |
| review | doing | 评审打回 | `task_reopened` |
| done | todo | `reopen`（必须 `reason`） | `task_reopened` |
| cancelled | todo | `reopen` | `task_reopened` |

非法转移 → 退出码 2，错误信息列出合法后继状态（agent 可据此自我修正）。

### 5.3 自动 unblock

`task_done` 事件写入后，同一事务内查 `task_deps` 反向依赖，若某 `todo`/`blocked` 任务的全部依赖已 `done`，则自动转 `todo` 并写 `task_unblocked` 事件。这样 agent 不需要轮询"我等的任务好了没"。

## 6. 崩溃恢复设计（核心）

四层机制，逐层加固。任何一层失效，下一层仍能兜住。

### L1 租约：归属是带期限的，不是永久的

```
claim T-0007  →  lease_expires_at = now + ttl(默认 15min)
progress/note →  隐式续期（lease_expires_at = now + ttl）
heartbeat     →  显式续期（会话级 + 该会话所有持有任务）
hold --for 2h →  显式长租约（长任务）
```

### L2 心跳与僵尸判定

- 任何 CLI / MCP 调用都会刷新 `sessions.last_seen_at`（对 agent 零心智负担：它本来就在调命令）
- 判定：`now - last_seen_at > grace`（默认 10 分钟）→ `status = crashed`
- 触发者三选一（按成本排序）：
  1. `agent-kanban doctor`（每次 CLI 调用隐式执行，代价 < 1ms）
  2. `agent-kanban serve` 进程内 30s 定时扫描
  3. `agent-kanban session start` 启动时（agent 开工第一件事就是它）
- **回收动作**（单个事务）：
  - `sessions.status = crashed`
  - 其 `doing` 任务：`lease_expires_at = NULL`，`status = doing → todo`，**`progress` 与 `checklist` 原样保留**
  - 写 `task_reclaimed`（`data.holder_crashed=true`）与 `session_crashed` 事件
  - 自动生成一条 `kind=crash` 的 handoff（内容见 L3）
- **`blocked` 任务不回收**：阻塞原因需要人处理，与 agent 是否存活无关
- `pid` 存活探测作为辅助信号，仅在 `agent-kanban doctor --deep` 启用（Windows 下 `process.kill(pid,0)` 不可靠，跨平台方案不统一，所以只做提示不做判据）

### L3 handoff：交接记录

```bash
# 主动交接（agent 收工前）
agent-kanban handoff --task T-0007 \
  --summary "完成 WAL 事务层，store.ts 20 个测试全绿" \
  --next    "接着写 handoff 崩溃合成逻辑，见实施计划 M2" \
  --blockers "无" \
  --open-questions "WAL 文件要不要纳入 git 跟踪？倾向不纳入"
```

崩溃自动合成的 handoff 内容（不需要 agent 参与；这几句是系统生成的文案，CLI / Web 里都按英文显示）：

```
summary: <任务标题>: progress 60%, the holder went silent (14 min without a heartbeat).
         Last actions: claimed the task; progress updated to 60% (改完 BEGIN IMMEDIATE 事务封装)
next:    Continue from 60%. Remaining: handoff 崩溃合成, rebuild 命令
blockers: the previous holder s-7f3a2b went silent (14 min without a heartbeat, the process may have crashed)
open_questions: （继承任务上最近一次 note 中的问号句，启发式）
```

### L4 context / resume：把现场拼回来

```bash
agent-kanban context                      # 项目级：开工包（推荐每个会话开工先跑这个）
agent-kanban context --task T-0007        # 任务级完整档案
agent-kanban resume T-0007                # 接管 + 注入交接 + 写 claimed 事件
```

`agent-kanban context` 输出结构（`--json` 时同构返回）：

1. **看板概览**：各状态计数、正在做的卡（附持有者与心跳新鲜度）、僵尸会话警告
2. **待接手的 handoff**：未被消费的交接（默认标记为 consumed，`--no-consume` 只读预览）
3. **`--task` 详情**：描述、状态、进度、checklist 未完成项、依赖、**当前计划全文**、事件时间线（`--tail N` 截断）、历史 handoff
4. **`--session` 详情**：本会话持有的任务 + 每张卡最近 10 条事件
5. **下一步建议**：可认领的 ready 任务（依赖满足、无人持有/持有者已僵死），按优先级排序；CLI 把它渲染成 `Suggested next steps:` 区块，JSON 模式则是 `next_actions` 字段

`agent-kanban resume T-0007` 一步完成：验证原持有者已僵死或 `--force` → 抢占 → 拉取最近 handoff 与时间线（作为该次调用的返回内容）→ 写 `task_claimed` 事件。**agent 恢复工作只需要这一条命令**。

### L5 事件重放与自证：`rebuild`

`events` 表只追加，因此可以从它把 `tasks` / `plans` / `handoffs` / `task_deps` 全部重建出来。
实现上采用**先算再比、默认不写**（而不是计划里最初写的"清空后重放"）：

```
1. 读事件流 → 2. 内存重放出完整投影 → 3. 与库中投影逐字段比对 → 4. 报告 drift
                                                          └─ 只有 --write 才落库（单事务）
```

理由：清空重放意味着一旦事件历史有缺口，用户辛苦攒的看板就被抹掉。
先算再比让 `rebuild` 成为一条零风险的只读命令（可进 CI），
同时提供 `doctor --deep` 的 `projection_drift` 检查与之联动。

由此得到一条硬约束（ADR-1 的真正含义）：**每个事件 payload 必须携带重建该投影所需的全部信息**。
详见 §7 与契约 §7.2。隐式修改投影字段的地方（如 `task done` 隐式把 progress 提到 100）
必须补发事件；物理删除（`task rm`）必须发 `task_removed`，否则已删任务会被重建“复活”。

不参与比较的字段：`lease_expires_at` / `updated_at`——它们由心跳/续租前移，
而续租不写事件（否则事件量会被心跳淹没），重建后回到“最后一次有事件时的值”是设计常态。

### L6 无 DB 降级：事件 journal

DB 二进制不入 git，`.kanban/journal/*.jsonl` 入 git。`agent-kanban import` 按 `seq` 顺序重放事件重建全部表。因此：

- 换机器 / 新 clone → `agent-kanban init && agent-kanban import .kanban/journal/*.jsonl` 即完全恢复
- DB 损坏 → `mv kanban.db kanban.db.bak && agent-kanban import ... && agent-kanban rebuild`
- 事件冲突（两台机器各写） → 按 `seq` + `ts` + `session_id` 人工裁决，工具提供 `agent-kanban import --dry-run` 输出冲突报告

## 7. 事件类型表

> ⚠️ `data` 里的字段直接决定了 `rebuild` 能不能重建投影。**改事件 payload 时必须同步本表**，
> 否则重放会丢信息。完整约束见 [002-接口契约.md §7.2](./002-接口契约.md)。

| type | 触发 | data 关键字段（重建所需） |
| --- | --- | --- |
| `session_started` | `session start` | `agent_name`, `harness`, `pid` |
| `session_heartbeat` | 任何调用（节流写，≥60s 才落库） | — |
| `session_closed` | `session end` | `summary` |
| `session_crashed` | 僵尸回收 | `grace_ms`, `last_seen_at` |
| `task_created` | `task add` | `title`, **`body`**, `status`, `priority`, `labels`, `parent_id`, **`checklist`**, **`estimate_ms`** |
| `task_updated` | 改描述/标签/预估 | `fields` = **新值**映射（不是字段名列表） |
| `task_ready` | backlog→todo | — |
| `task_claimed` | 抢占成功 | `prev_assignee`, `prev_status`, `ttl_ms`（租约 = `ts + ttl_ms`） |
| `task_released` | 主动 release | `reason` |
| `task_reclaimed` | 租约到期回收 | `holder_crashed`, `prev_progress`, `prev_status`, `forced` |
| `task_progress` | `progress` / 隐式提进度 | `pct`, `prev_pct`, `note`；checklist 变更时带**完整快照** `checklist`（含 `done_at`/`by`） |
| `task_note` | `note` | `text` |
| `task_blocked` | `block` | `reason` |
| `task_unblocked` | 依赖满足自动 | `unblocked_by` |
| `task_review` | doing→review | `note` |
| `task_done` | →done | `note`, `force`, `spent_ms` |
| `task_cancelled` | →cancelled | `reason` |
| `task_reopened` | 重新打开 | `reason`, `from_status` |
| `task_removed` | `task rm` | `title`, `status`, `forced`, **`removed_deps`**（不发这条，已删任务会被 rebuild 复活） |
| `dep_added` / `dep_removed` | 依赖变更 | `depends_on_id` |
| `plan_created` | `plan save` | **完整计划行**（`id`/`scope`/`task_id`/`version`/`title`/`body`/`status`/`author_session_id`/`created_at`/`supersedes_id`） |
| `plan_superseded` | 新版本覆盖 | **完整旧计划行** + `status="superseded"` |
| `handoff_created` | 主动或自动 | **完整交接行**（含 `session_id`——crash 交接由 system 发出但归属原持有者） |
| `handoff_consumed` | 新会话接手 | `handoff_id`, `by_session` |
| `board_exported` | `export`/`snapshot` | `out_path`, `event_count` |

事件体统一形状：

```json
{ "seq": 1042, "ts": 1771432812345, "session_id": "s-7f3a2b",
  "type": "task_progress", "task_id": "T-0007", "plan_id": null,
  "data": { "pct": 60, "prev_pct": 40, "note": "改完 BEGIN IMMEDIATE 封装" } }
```

## 9. 可靠性与一致性

| 关注点 | 机制 |
| --- | --- |
| 状态与日志原子性 | 每次写操作 = 一个 `BEGIN IMMEDIATE` 事务，内含"改投影 + 插事件"，不存在只改一半 |
| 抢锁失败可识别 | 条件 UPDATE 后检查 `changes === 0`，返回冲突错误 + 当前持有者信息 |
| 投影与事件一致 | `agent-kanban rebuild` 重放校验；`doctor --deep` 对比事件折叠结果与 `tasks` 表 |
| 长时间无进展检测 | `doctor` 报告"doing 超过 N 小时无 progress 事件"的卡 |
| 僵尸占用 | 租约 + 自动回收；`review`/`blocked` 不受影响 |
| 事件表膨胀 | 单任务量级 ~50 条；提供 `agent-kanban compact --keep-days 30`（先快照再裁剪） |
| DB 损坏 | 事件 journal 可完整重建；`doctor` 检测 `PRAGMA integrity_check` |
| 并发锁等待 | `busy_timeout=5000`；超时 → 退出码 4（"请重试"），agent 可安全重试 |
| 时钟回拨 | 所有过期判定用 `max(now, last_seen_at)` 兜底，避免时钟回拨导致租约永久有效 |

## 10. 安全

- `serve` 默认绑定 `127.0.0.1`，`--host 0.0.0.0` 需显式指定并建议配 `--token`
- SSE 与写接口在 `--token` 模式下要求 `Authorization: Bearer <token>`（SSE 用 query 参数，因 EventSource 无法带 header）
- 任务标题/描述/笔记一律视为不可信文本：Web 前端用 `textContent` 渲染，禁止 `innerHTML` 拼接
- 不做任何 `eval`/模板注入；SQL 全部参数化
- CLI 不设权限模型（本地开发工具），但所有写操作留事件审计，可事后追责

## 11. 已知风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| agent 忘记心跳 | 卡被误判僵死并回收 | 写操作隐式续期（`progress`/`note` 都刷新）；MCP `bootstrap` 工具主动提示；默认 grace 10 分钟远大于 agent 单次操作间隔 |
| 长任务被误回收 | 进度被重置 | `--ttl` / `hold --for`；`blocked` 态不回收；回收**保留 progress**（这是与常见做法的关键区别） |
| agent 抢占他人正在做的卡 | 重复劳动 | 租约未过期则抢占失败（退出码 3），错误信息附带持有者与最近动作，让 agent 换任务而不是硬抢；`--force` 需人工介入并记 `task_reclaimed` |
| 事件表膨胀 | DB 变大 | 量级可控；提供 compact + snapshot |
| 多个 agent 目标冲突 | 互相覆盖 | 每张卡同一时刻只有一个租约持有者；`review` 状态作为人介入闸门 |
| DB 不入 git 让人以为"没历史" | 新 clone 空看板 | README 与 `agent-kanban init` 输出明确提示 `import` 路径；`init` 后若检测到 journal 存在会主动提示 |
| 忘记更新协议文件 | agent 行为漂移 | `agent-kanban install-protocol` 幂等写入并带 `<!-- agent-kanban:begin -->...<!-- agent-kanban:end -->` 标记；`agent-kanban doctor` 检查 AGENTS.md 片段是否落后于当前 CLI 版本 |
| SQLite 单写者在超高并发下成为瓶颈 | 命令变慢 | agent 写频率极低（分钟级），实测 8 进程 × 200 事务无 busy；如未来成为问题可换 `BEGIN CONCURRENT`/换 PG |

## 12. 与项目约定的集成：agent 协作协议

`agent-kanban install-protocol` 幂等写入 `AGENTS.md` 的受管区块（内容随 CLI 版本演进）：

```markdown
<!-- agent-kanban:begin -->
## Task board (agent-kanban)

This project's task state lives in `.kanban/kanban.db` and is shared by every session.
**Do not work around it.** Changing code without updating the board leaves the board
describing a project that no longer exists.

### Start of every work session

```bash
agent-kanban session start --agent <your-name> --harness pi   # 1. register the session
agent-kanban context                                          # 2. read the situation, do this first
agent-kanban task claim T-0007                                # 3. claim it, you get the lease
```

`agent-kanban context` tells you whether anyone left you a handoff, which cards you already
hold, and what is free to claim right now. **Skipping it means working blind.**

### While working

```bash
agent-kanban task progress T-0007 --pct 60 --note "rewrote the storage layer"   # renews your lease
agent-kanban task check T-0007 --item "add migration test"                      # checklist item
agent-kanban task note T-0007 "found a dependency conflict"                     # quick note
agent-kanban task block T-0007 --reason "waiting on API key"                    # releases the lease
```

Tasks over 30 minutes long: `agent-kanban task claim T-0007 --ttl 7200` extends the lease.

### Before you stop

```bash
agent-kanban handoff --task T-0007 --summary "what got done" --next "where to pick up"
agent-kanban task done T-0007 --note "tests green"                             # only when finished
agent-kanban session end
```

**A handoff is written for whoever picks this up next, not for you.** Name the function,
the file, the test that fails. "The rest is straightforward" costs the next session a
full round trip.

### After a crash

```bash
agent-kanban context              # whose lease expired, which cards are unattended
agent-kanban resume T-0007        # take over: handoff content plus the full timeline
```

No scrolling through chat logs, no asking a human.

### Rules

- Never read or write `kanban.db` directly, and never hand-edit anything under `.kanban/`
- A rejected claim (exit code `3`) means another session holds the lease. The error names
  the holder and their last action. Pick a different card rather than forcing it
- Every command accepts `--json`. Use it in scripts, never parse the coloured output
- Plans are versioned: `agent-kanban plan save` writes a new version and keeps the old one
- `agent-kanban doctor` self-checks consistency, `agent-kanban rebuild` re-derives the board from the event log

### Exit codes

| Code | Meaning | What to do |
| `0` | Success | — |
| `1` | Bad arguments | Read the usage hint, fix the command |
| `2` | State error | Task missing or transition not allowed; do not retry as-is |
| `3` | Conflict | Another session holds the lease; pick a different card |
| `4` | Database busy | Back off and retry, at most 3 times |
| `5` | Not initialised | Run `agent-kanban init` |
| `6` | Internal error | Treat as a bug and report it |
| `7` | Auth failed | Check the token and the project key |

## 13. 已验证的技术假设（探针结论）

| 假设 | 验证方式 | 结论 |

| `bun:sqlite` 默认 WAL | `PRAGMA journal_mode` | ✅ `wal` |
