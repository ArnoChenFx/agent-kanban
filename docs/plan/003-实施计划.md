## 2. M1 存储层与状态机

### 步骤

1. **工程骨架**：`package.json`（`bin: kanban` → `src/cli.ts`）、`tsconfig.json`、`bunfig.toml`、`.gitignore`（忽略 `.kanban/kanban.db*`）、`src/core/errors.ts`（`KanbanError` + 退出码映射表）
2. **`src/core/db.ts` + `schema.sql`**：连接、`PRAGMA journal_mode=WAL` / `busy_timeout=5000` / `foreign_keys=ON`、迁移器（`meta.schema_version` 幂等升级）、`.kanban/` 向上查找
3. **`src/core/tx.ts`**：`withTx(fn)` = `BEGIN IMMEDIATE` → fn → `COMMIT` / `ROLLBACK`；同事务内提供 `emit(event)` 写事件；异常映射到退出码
4. **`src/core/ids.ts`**：`T-0007` / `s-xxxxxx` / `PL-xxxx` / `PL-T-0007-03` 生成（T 序列在写事务内 `MAX+1`）
5. **`src/core/tasks.ts`**：状态机**数据驱动**（转移表是 `const TRANSITIONS: Record<Status, Partial<Record<Status, Guard>>>`，不是散落的 if），实现 create/get/list/update/claim/release/transition、依赖读写、环检测
6. **`src/core/events.ts`**：事件追加、查询（按 task / seq / ts）、心跳节流写（≥60s 才落库）
7. **CLI**：`init` / `task add|list|show|claim|start|progress|note|block|unblock|review|done|cancel|reopen|release|dep` / `board`
8. **看板自举**：`agent-kanban init` 后把本项目自己的 M1-M6 任务导入看板（dogfooding）

### 关键实现约束

- 所有写操作必须在 `withTx` 内；代码评审时把"存在裸 `db.exec('UPDATE ...')` 之外的写路径"当作 bug
- 抢占只用条件 UPDATE + `changes` 判定，不用"先 SELECT 再 UPDATE"
- `progress`/`note` 等写操作同时刷新租约（ADR-4 的隐式续期），这是防误回收的关键
- 列表输出字段名要稳定（契约 §2.5），MCP/Web 都依赖

### 测试

| 用例 | 断言 |
| --- | --- |
| 状态机表驱动 | 对转移表每一项：合法转移成功、非法转移抛 `STATE(2)` 且 `legal_transitions` 正确 |
| 并发抢占 | 8 个 `Bun.spawn` 同时 `claim T-0007`：恰好 1 个 exit 0，其余 exit 3，且 7 个错误里的 `holder.session_id` 等于赢家 |
| 环检测 | `A 依赖 B`、`B 依赖 A` → 退出码 2 |
| 自动 unblock | 完成 B 后，A 从 blocked 自动到 todo，且产出 `task_unblocked` 事件 |
| ID 分配 | 并发 add 10 个任务，ID 无重复且连续 |
| 事件原子性 | 非法转移后检查 `events` 无新行（事务回滚干净） |

## 3. M2 崩溃恢复（核心里程碑）✅ 已完成

> 实施结果见 [2026-02-19-M2-崩溃恢复实施笔记.md](../note/2026-02-19-M2-崩溃恢复实施笔记.md)。
> 实现过程中修正了若干设计缺口（交接不随租约让位、`listTasks` 的 `mine` 门控、`resume` 交接优先级、
> crash 交接的 blockers 为空、`init --force` 不删库），详见笔记第二节。

### 步骤

1. **`src/core/sessions.ts`**：`start` / `heartbeat` / `end` / `list`；`.kanban/session` 便捷文件
2. **租约字段接线**：`claim` 写 `lease_expires_at`；所有写操作隐式续租；`hold --for`；`--ttl` 贯穿 CLI/MCP
3. **僵尸回收 `reapZombies(now)`**：
   - `sessions.last_seen_at < now - grace` → `status=crashed`
   - 其 `doing` 任务 → `status=todo`、`lease_expires_at=NULL`、**保留 progress/checklist**
   - 写 `session_crashed` + `task_reclaimed` 事件
   - 自动生成 `kind=crash` 的 handoff（summary 由最后 N 条事件合成，next 由未完成 checklist 合成）
   - `blocked` / `review` 任务不动
4. **回收触发点**：CLI 每次调用隐式轻量 reap（一条 `UPDATE ... WHERE` 成本可忽略）；`serve` 30s 定时；`session start` 强制 reap
5. **`src/core/handoff.ts`**：主动写交接；`crash` 自动合成；`consume(sessionId)` 标记被谁接手；`--no-consume` 只读
6. **`src/core/context.ts`**：组装看板概览 + 僵尸告警 + 待接手交接 + 进行中 + 阻塞 + ready 建议 + `next_actions`
7. **CLI**：`session start|heartbeat|end|list` / `handoff` / `context` / `resume` / `watch` / `doctor`（doctor 提前到 M2 实现）
8. **`resume` 一步流**：校验（原持有者僵死、**已留下主动交接**、或 `--force`）→ 抢占 → 拉交接 + 时间线 + 剩余检查项 → 写 `task_claimed` → 返回接手指令

### 关键实现约束

- 回收必须**保留 progress**：这是"恢复后不用从头再来"的直接体现
- `crash` handoff 的合成文本只允许使用已有事件数据，不做猜测式推断（`open_questions` 可从最近 note 中启发式抽取问号句，规则写死在代码里并单测）
- 时钟回拨兜底：过期判定用 `now - max(last_seen_at, lease_expires_at/2)` 之类避免负数异常，具体公式单测覆盖
- **交接即让位**：持有者留下 `voluntary` 交接后，接管不再受租约阻塞（否则“交接写得越认真越接不了手”）。**M4 补充**：“留下”包括“已被本会话消费”——否则 MCP 标准流程（`bootstrap` 默认 consume → `resume`）会卡在 CONFLICT，agent 只能 `force`，而 `force` 会把一次正常接手续记成“抢占”。消费回答的是“谁接手了”，不是“能不能接手”
  ⚠ **该判定的两处必须同步**：JS 前置判定与条件 UPDATE 的 SQL 谓词。曾只改前者，表现为“日志说可以接管，紧接着就抛 CONFLICT”
- **人写优先于机器合成**：`resume` 优先展示 `voluntary` 交接，`crash` 仅作兜底
- **crash 交接的 blockers 必须含“原持有者失联”**：这是接手方最该先看到的信息

### 测试（已实现 17 个用例，全部用可注入时钟）

| 用例 | 断言 |
| --- | --- |
| 完整崩溃恢复 | 建卡→claim→progress 40→不心跳→推进时间（注入 clock）→reap→断言：`status=todo`、`progress` 仍 40、生成 crash handoff、summary 含进度与失联时长、next 含未完成 checklist |
| resume 接管 | 崩溃后新 session `resume`：成功接管、返回交接全文、进度/checklist 保留、交接标记已消费 |
| 交接让位 | 持有者写了主动交接且租约仍有效时，resume 成功（无 force） |
| 交接优先级 | 同时存在 voluntary 与 crash 时，resume 返回 voluntary |
| doctor | 健康库 ok；失联租约可发现并 `--fix`；progress/checklist 不一致可发现 |
| 租约未过期时抢占 | exit 3，错误含 holder 的 `progress`/`last_seen_at`/`last_event` |
| 强制抢占 | `--force` 成功且写 `task_reclaimed`（`holder_crashed` 或 `forced=true`） |
| blocked 不被回收 | reap 后 blocked 任务状态与 reason 不变 |
| 心跳续租 | grace 内 heartbeat → 不被判崩；不 heartbeat → 被判崩 |
| handoff 消费语义 | 第二个 session `context --no-consume` 能看到但不被标记；不带参数则标记 consumed（`consumed_by` 正确） |
| 时钟回拨 | `now < last_seen_at` 不产生异常回收 |

## 4. M3 计划与一致性 ✅ 已完成

> 实施结果见 [2026-02-19-M3-计划与重建实施笔记.md](../note/2026-02-19-M3-计划与重建实施笔记.md)。
> 实现过程中修正了三个结构性缺陷（事件 payload 不足以重建投影、`task done` 隐式改 progress 不记事件、
> `removeTask` 不记事件），并发现 ADR-9 漏了 `task_deps` 的 project 隔离（schema v4）。

### 步骤

1. **`src/core/plans.ts`**：任务级 / 项目级计划；`save` 自动 version+1 并把旧版转 `superseded`；同事务写 `plan_created` + `plan_superseded`（**事件携带完整计划行**，供 rebuild 重建） ✅
2. **`plan list|show|history|at|attach`**：版本链回溯（改了几次）、时间旅行（那时的计划） ✅（`diff` 未做）
3. **`src/core/rebuild.ts`**：内存重放 → 逐字段比对 → 默认只校验，`--write` 才落库 ✅
4. **`agent-kanban rebuild`**：⚠️ 实现上改为「**先算再比、默认不写**」而非计划里的「清空后重放」——
   事件历史一有缺口，清空重放会直接抹掉用户攒的看板。现在它是零风险的只读命令 ✅
5. **`src/core/doctor.ts`**：`stale_lease` / `stale_block` / `no_progress` / `progress_mismatch` / `done_with_remaining` / `projection_drift`；`--fix` 自动修可修项 ✅
6. **CLI**：`plan *` / `rebuild` / `doctor` ✅

### 关键实现约束

- **事件 payload 必须携带重建该投影所需的全部信息**。这是 M3 最大的收获：
  `task_created` 缺 body/checklist/estimate、`handoff_created` 缺内容、
  `task_progress` 的 checklist 缺 done_at/by，都会让 rebuild 重建不出正确的投影。
  凡是**隐式修改投影字段**的地方（如 `task done` 隐式把 progress 提到 100），必须留事件痕迹。
- `removeTask` 必须发 `task_removed` 事件，否则已删任务会被 rebuild **复活**。
- 写回必须在**一个事务**里：DELETE 四张表再逐行 INSERT，中途失败不留半写状态。
- **不参与比较的字段**：`lease_expires_at` / `updated_at`（由心跳前移，续租不写事件，属设计常态）。
- **必须能重建的字段**：checklist 的 `done_at` / `by`（重建必须无损，否则 `--write` 跑一次就把"谁勾的"洗没了）。
- schema v4：`task_deps` 补 `project_key`（ADR-9 遗漏，会导致多 project 下依赖静默错乱）

### 测试（已实现 18 个用例，全部用可注入时钟）

| 用例 | 断言 |
| --- | --- |
| **重放一致性（核心）** | 跑遍所有操作后 `rebuild` 零漂移（tasks/plans/handoffs/task_deps 行数与内容全对） |
| 漂移检出 | 绕过 core 直接改库（改标题/状态/错改进度/删依赖）→ rebuild 逐字段报出 |
| `--write` 修复 | 修复后一致，且功能（依赖/计划链/新任务号）正常 |
| 重建幂等 | 反复 `--write`，投影快照逐字节相同 |
| 任务删除不复活 | `removeTask` 后 rebuild 不重建出该任务 |
| project 隔离 | 两个 project 各自 rebuild，互不干扰 |
| lease/updated_at 豁免 | 只改租约不报漂移 |
| 交接消费状态 | `consumed_by` / `consumed_at` 能从事件重建 |
| 计数器不撞号 | 重建后新建任务得到 T-0004 而非 T-0001 |
| doctor 联动 | 漂移被报为 `projection_drift`（error 级，hint 指向 rebuild） |
| 计划版本链 | 连续 save 3 次 → 版本 1/2/3，只有 v3 `active`，链正确 |
| 计划时间旅行 | `planAtTime` 查到当时生效的版本 |

## 5. M4 MCP Server ✅ 已完成

### 步骤

1. `src/mcp/server.ts`：stdio 传输的 MCP server，工具定义由契约 §3.2 的 JSON Schema **单向生成** zod ✅
2. `src/mcp/tools.ts`：每个工具 = 「参数改名 → 构造 Op → 取包络」，**零业务逻辑** ✅
3. 长文本截断策略：`plan_show` 默认 20000 字符，超出截断并在 `next_actions` 提示 ✅
4. `kanban_bootstrap` 作为每会话第一个工具，文案强调“先看交接再动手” ✅
5. 注册示例写进 README（`pi mcp add` / `claude mcp add` 两种配置） ✅
6. **计划内未列、但必须加的**：`kanban_plan_diff`（契约 §3.2 有、M2 未做），配套 LCS 行级 diff ✅

### 关键实现约束

- **MCP 走 Op，不直调 core**。Op 已经是“本地与远程一致”的那层，走它就自动获得与 CLI
  相同的行为，不必在第三个接入面重写状态机（ADR-6 / ADR-10）
- **长驻进程要能换会话身份**。CLI 每次是独立进程，sessionId 从参数读即可；MCP 是长驻进程，
  agent 先 `session_start` 再用返回的 id 调二十个工具。为此给 `Backend` 加了 `withSession()`，
  返回新实例而**不就地改字段**（MCP 允许多路 tools/call，就地改会让在飞中的请求用错身份）
- **stdout 是 JSON-RPC 通道**。任何一行日志写进去都会让客户端解析失败，且报错出现在客户端
  那边，极难定位。诊断一律走 stderr
- **契约 §3.4 的流程必须真能跑通**（`session_start → bootstrap → resume`）。这暴露了
  “bootstrap 默认消费交接会抹掉让位信号”的问题，修法见 M2 笔记的补充

### 测试（`scripts/verify-mcp.ts`，真起 stdio 子进程）

| 用例 | 断言 |
| --- | --- |
| 工具层契约 | 20 个工具均有 description 与 inputSchema |
| 恢复流程 | 真子进程跑完契约 §3.4 七步：接管、进度保留、交接注入、计划版本、diff |
| 通道卫生 | stdout 零非 JSON 行；收到的响应数与请求数一致 |
| 错误包络 | 不存在的任务 → `ok:false` + code/name/message；非法 status 被工具层拦下（不落到 SQL） |
| CLI 等价 | 同一 Op，CLI `--json` 与 MCP `data` 看到同一批卡 |

## 6. M5 Web 看板

6. 安全渲染：全部 `textContent`，无 `innerHTML` 拼用户内容

### 测试

- SSE：连接 → 触发 CLI 侧写入 → 收到事件（端到端，起真实 `serve` 子进程）
- 续传：断线期间产生 N 个事件 → 带旧 `Last-Event-ID` 重连 → 恰好补齐 N 个且顺序正确
- 鉴权：无 token 访问 `/api/board` → 401
- 绑定：默认只监听 127.0.0.1（断言 `netstat`/连接外部地址失败）

## 9. 风险登记（实施期重点关注）
