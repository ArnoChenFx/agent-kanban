# 006 — CLI 文案英文化

> 目标：`agent-kanban` 命令行**输出给人看的文本**全部改成英文；MCP 工具描述、core 抛出的错误
> 文案一并英文化；中文 Web 界面的报错改由词典渲染，因此仍然显示中文。
> 代码注释、任务标题、交接正文、种子数据、JSON 字段名、退出码**一律不动**。

## 一、为什么先定这份文档

这次改造跨 19 个文件、约 650 处文案。多人（多个 agent 会话）并行改同一批文件时，
最贵的浪费不是改错，而是**同一个词在 A 文件译成 `claim`、在 B 文件译成 `take`**。
所以术语对照表必须先落地，且**只此一份**，谁都不许自己造词。

## 二、范围

### 改（英文）

| 位置 | 说明 |

| `src/commands/*.ts` | 各命令的 USAGE 常量、成功日志、下一步建议、参数校验报错 |
| `src/commands/output.ts` | `错误[X]：` / `提示：` / `用法：` / `当前持有者：` 四个模板 |

| `src/mcp/tools.ts`、`src/mcp/server.ts` | 工具描述、工具报错 |

### 不改（保持中文 / 原样）

- **代码注释**：`// 租约 15 分钟` 这类注释全留中文。中文注释是本仓库的既定风格
  （AGENTS.md：「代码注释用中文没问题」），且注释里的中文是理解逻辑的关键线索。
- **数据**：任务标题、描述、checklist 文本、交接 summary/next、计划正文、seed 脚本造的数据。
  用户用中文写标题，输出里就照原样显示中文——这是**回显**，不是文案。
- **JSON 契约**：`ok` / `code` / `name` / `details` 等键名、退出码数值、事件 `type`、
  状态机取值（`todo`/`doing`/…）都不动。`--json` 模式输出的结构完全不变。
- **`next_action_items` 的 `code` 与 `args` 键名**：一个字都不动（`takeover` / `read_handoff` /
  `claim_new` …）。`web/src/lib/next-actions.ts` 靠它们查词典，改了前端就崩。
  注意这与 `next_actions` 文本的处理**方向相反**，见上面「改」一节。
- **脚本自身日志**：`scripts/verify-*.ts` 打印的中文日志保持中文（开发者面向，不是产品输出）。
  只有**断言 CLI 输出的期望值**必须跟着改。
- **Web 界面 chrome**：走词典的界面文案不动（AGENTS.md 已有规则）。

## 四、文风规则

1. **直译，保留结构**。不重新设计排版，不合并行，不改缩进对齐。
2. **保留符号**：`✓` `✗` `⚠` `→` `·` `│` `█` `░` `⛔` `◎` 一律原样。
3. **对齐**：原来是靠中文字符宽度对齐的（`project  ：`、`  租约：`），英文化后
   标签长度变了，**要重新对齐冒号位置**，用空格补齐即可，不要留多余的全角空格。
4. **`KanbanError.usage(msg, usage)` 的第二个参数保留 `Usage: ` 前缀**。
   `output.ts` 会先判断该文本是否已以 `Usage:` 开头，已开头就不再补表头——
   这同时修掉了「用法：」重复两遍的旧问题（USAGE 常量还被 `--help` 直接打印，
   必须自包含）。
4. **反引号内的命令照抄**，不要改写命令，也不要给命令加引号。
5. **句子用祈使句 / 动词开头**（`Claim the task first`），不用礼貌语。
6. **JSON 里的 `next_actions` 保持中文**（见 §二）。
7. **`--json` 模式的任何键名、值结构不变**，只改人读的文本。
8. 翻译后**不得改变控制流**。这是纯文案改动，diff 里出现 `if`/`return`/新增分支即为事故。

## 五、错误文案与 Web 词典（reason slug）

### 问题

core 抛出的 `KanbanError.message` 会同时流向三处：CLI 打印、Web toast 展示、agent 读 JSON。
英文化后，中文 Web 界面的报错会变成英文——除非 Web 不再直接展示 `message`。

### 做法

给每个面向 Web 的错误在 `details` 里加一个**稳定的 slug**：

```ts
// 改前
throw KanbanError.state(`任务 ${taskId} 不存在`, { task_id: taskId });
// 改后
throw KanbanError.state(`task ${taskId} not found`, { reason: "task_not_found", task_id: taskId });
```

Web 侧按 `details.reason` 查词典渲染中文，缺 key 时**回退到 `message`**（英文）。
所以：英文界面 = 直接用后端 message；中文界面 = 词典命中则中文，未命中则英文兜底。

### slug 命名

`snake_case`，动词-名词，按「出了什么事」命名而不是按「哪个函数抛的」：
`task_not_found`、`illegal_transition`、`not_lease_holder`、`project_exists`、
`invalid_duration`、`remote_unreachable`、`sqlite_busy` …
同一个语义**必须复用同一个 slug**（如"任务不存在"在 task.ts / ops.ts / http.ts 都要叫
`task_not_found`），否则词典会出现同义两行、中文界面随机命中其中一个。

`details.hint` 同样会展示在 Web 上，翻译时也放英文，中文提示由词典承担。

## 六、执行者注意事项（人或 agent 都适用）

- **用 `read` 工具或 `rg` 看文件，不要用 PowerShell 的 `Get-Content`。**
  本机 PowerShell 5.1 的 `Get-Content` 默认按 ANSI（GBK）解码，会把仓库里
  正确的 UTF-8 中文显示成乱码（`瑙ｆ瀽绉熺害鏃堕暱` ← `解析租约时长`）。
  照着乱码翻译会把乱码写进文件，是本项目最容易犯又最难发现的错误。
- 中文标点（`：：（）、""`）在英文句子里一律换成半角（`:, ()""`），
  句末用 `.`，不要保留中文句号 `。`。
- 不要顺手重构、不要改控制流、不要动 JSON 键名。diff 里出现非文案改动即为事故。
