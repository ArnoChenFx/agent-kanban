# 2026-09-27 Session 身份分片实施笔记

> 对应方案 [007-Session身份分片](../plan/007-Session身份分片.md)，看板任务 `T-0005`。
> 起因是有人问"同一台机器同一目录跑两个 agent 怎么区分身份"——查完发现它们**根本没在区分**。

## 一、发现的过程

先按协议起了会话（`session start --agent pi-main`），然后去读实现，发现身份只有一个来源：
`.kanban/session` 单文件。这文件是 `session start` 写的，**后写覆盖先写**。

于是同一目录的第二个 agent 一 `session start`，第一个的身份就没了。之后两边所有不带
`--session` 的命令都记到同一个 session 名下。跟同事确认了这不是我看错：
`AGENTS.md` 里"多 agent 协作"那一节默认了身份能分开，实际上并没有任何机制在分开。

顺手做了三件核实工作（都不是凭印象）：

1. **本机环境变量**：`PI_SESSION_ID` 确实存在（`01a0debe-…`，与 `PI_SESSION_FILE` 同名 UUID）
2. **`process.ppid` 可用性**：bun 1.4.2 在 Windows 上有值。实测同一 shell 内稳定（`70712`），
   跨 shell 变（`57976 / 70712 / 31564`）→ **对本项目场景不可用**
3. **其他 harness 有没有**：claude / cursor-agent / codex 本机都装了。
   从二进制里 `rg -o '\b[A-Z][A-Z0-9_]{2,28}_SESSION_ID\b'` 挖字符串：
   - claude-code → `CLAUDE_CODE_SESSION_ID` ✅（还有 `CLAUDE_SESSION_ID` 等变体）
   - cursor-agent → 只有 `CURSOR_AGENT_SOCKET` 这类进程级变量，**没有会话 id** ✅（结论正确）
   - codex → 我当时写的是「全是配置项，没有会话 id」——**这个结论是错的**，
     根因见第七节（截断了清单）

结论：pi 和 claude-code 能自动分流。核实办法写进了 `paths.ts` 的注释，
并明确写"加新 harness 前照这个办法核实，别写听起来像的名字——
写错了不报错，只是那个变量永远不存在"。

## 二、方案定型时改掉的一个决定

一开始想的是"写两处保险"：有 key 就写分片，**同时**也更新旧单文件，理由是同目录里
可能有旧版 CLI 或不带 key 的进程。

写完冒烟脚本跑了一遍，第 9 步直接把这个决定打回来了：

```
### 9. 无 key 的裸 shell
  exit=0
  ✓ Claimed T-0003 ka-three (lease 15m)
  session list → s-1egink (agent-b)  Tasks held: T-0002, T-0003
```

裸 shell 那条**冒充了 agent-b**，顺手指纹多了一张卡。也就是说我留了个后门：
keyful 侧每次 `session start` 都在给 keyless 侧刷新冒充素材。

改成"只写一个地方"：有 key 就只写分片、绝不碰旧单文件。代价是 keyless 侧会明确报错，
提示里写清修复动作。这正是本项目一贯的取舍——**宁可退出码 1，不要静默写错人**
（和 `context` 那个警告、和 `resolveSessionId` 不自动建野会话是同一条线）。

## 三、写测试时撞到的东西

### 3.1 `KANBAN_SESSION=` 是空串，不是未设置

第一版 e2e 测试里，为了"清掉所有可能影响 key 的变量"，我给子进程传
`KANBAN_SESSION: ""`。结果 **"A 去抢 B 的卡"期望退出码 3、实测 0**，`holder` 是空串。

顺着查下去，发现是**先于本次改动就存在**的 bug：

```ts
// openCtx 原本的优先级链
process.env.KANBAN_SESSION ?? readSessionFile(dir) ?? null
```

`??` 只挡 null/undefined。`KANBAN_SESSION=` 这种"赋值空串"是最常见的取消设置写法，
它**不是 nullish**，于是直接胜出 → `sessionId = ""` → 身份文件被忽略 →
两个 agent 都以空身份跑 → A 再 claim B 的卡被认成"自己持有"续租。

而且 README 早就写着：

> An empty environment variable counts as *unset*, not as an empty value.

所以这不是引入新约定，是**把代码兑现到已声明的约定**。修法是抽 `pickSessionId`，
三处都判非空字符串。回归测试就钉在 `test/session-identity.test.ts` 里。

> 这条记在这里是想说明：写"清空环境变量"这种辅助代码时，
> 空串和未设置的区别是会咬人的，而且它咬的是**静默**那一侧。

### 3.2 自己的测试也有两个低级错

- 硬编码任务 ID（`T-0003` / `T-0004`）→ 测试顺序一变就错，实际 `task add` 出来的编号

## 四、其他踩到的

### 4.1 `RegExp` 带 `/g` 时 `test()` 有状态

清洗文件名的正则原本是一个带 `/g` 的常量，既 `.replace()` 又 `.test()`。
`test()` 会记住 `lastIndex`，第二次调用结果就不对了（表现为 key 偶尔"变长"）。
拆成两个常量，注释里写明原因。

### 4.2 调试脚本把自己的 bug 看成实现的 bug

第一次写 PowerShell 冒烟脚本时，为了避开某个占位符问题，我把"空值"写成了
`[char]39`（一个单引号字符）——结果 `CLAUDE_CODE_SESSION_ID` / `KANBAN_SESSION_KEY`
都被设成了 `'`（真值），于是 `resolveSessionKey` 命中 `KANBAN_SESSION_KEY`，
生成 key `custom-_-09g3t8m`，所有命令都以同一个身份跑。

**排查这类"结果不对"时，先确认自己的辅助代码是对的**，否则会去改本来正确的实现。

### 4.3 Windows PowerShell 5.1 按 GBK 读脚本

冒烟脚本带中文注释，`powershell.exe -File` 直接语法报错（`Unexpected token`）。
用 `pwsh` 跑就正常。这与 `AGENTS.md` 里已记录的"看文件用 `read` 工具或 `rg`"是同一个坑的
另一面：写脚本也一样。

## 七、第二轮：扩展其它 harness（grok / oh-my-pi / codex）

### 7.1 我自己写下的一个错误结论，和它的根因

第一轮我在笔记里写「codex 的 `CODEX_*` 全是配置项，没有会话 id」。**这是错的。**
本机 codex 0.157.1 其实有 `CODEX_SESSION_ID`。

根因有两条，都很典型：

1. **用 `Select-Object -First 30` 截断了清单。** `CODEX_*` 一共 28 条，我截到 30 条的时候
   看起来“完整”，但实际上中间有条被 PowerShell 的管道处理掉了，于是我信心十足地
   下了错结论。**教训：列清单给人看之前，先看一眼总数对不对。**
2. **带 `\b` 的正则扫描在二进制上会漏。** Rust 编译出的 rodata 里字符串是紧挨着排的
   （无 NUL 分隔），前一个字符串的末尾字母会让下一个字符串的 `\b` 判定失败。
   实测同一个二进制：`rg -c --fixed-strings 'CODEX_SESSION_ID'` 数出 **1** 处，
   而 `\bCODEX_[A-Z0-9_]{2,40}\b` 的清单里 **完全找不到它**。
   → 扫描顺序应该是：**宽松正则列候选 → `--fixed-strings` 逐个确认 → dump 上下文看语义**。

### 7.2 翻二进制找不到，就去查官方源码

用户给了 [codex PR #10096](https://github.com/openai/codex/pull/10096)，
标题就是答案：**Inject `CODEX_THREAD_ID` into the terminal environment**（2026-02-03 合入 main）。
翻 `codex-rs/core/src/exec_env.rs` 又发现 main 上其实**两个都有**：

```rust
pub use codex_protocol::shell_environment::CODEX_SESSION_ID_ENV_VAR;
pub use codex_protocol::shell_environment::CODEX_THREAD_ID_ENV_VAR;

/// Exposes the shared root-session identity and harness version to shell commands.
pub(crate) fn inject_session_env(env: &mut HashMap<String, String>, session_id: SessionId) {
    env.insert(CODEX_SESSION_ID_ENV_VAR.to_string(), session_id.to_string());
```

本机 0.157.1 只有 `CODEX_SESSION_ID`（没有 `CODEX_THREAD_ID`），与“本地是旧版”一致。
**两条路都要走**：翻二进制快但会漏，官方源码慢但权威。

### 7.3 一个真正的设计判断：codex 该用 session 还是 thread

两个变量都在，选哪个不是随便的。选错了不会报错，但会让一个 agent 变成 N 个：

`CODEX_THREAD_ID` 是**当前 thread**（一个 codex agent 内部可以起并行 thread），
`CODEX_SESSION_ID` 是**root session**（整个 agent 运行）。

按 thread 分片的后果：一个 codex agent 起 3 个并行 thread → 3 个不同身份 →
它们互相抢同一批卡、互相报 CONFLICT，而它们其实是**同一个 agent**。

所以用**更粗的 `CODEX_SESSION_ID`**。这条已经写成测试
（“thread 与 session 同时存在时取 session”）钉住，改错了会红。

> 由此抽出一条通用规则：**身份粒度不能比 agent 本身更细。**
> 分片的目的是区分“不同的 agent”，不是区分“同一个 agent 的内部步骤”。

### 7.4 oh-my-pi 给的是路径，不是 id

`PI_SESSION_FILE` 的值是会话 jsonl 的**路径**。本机真实文件名：

```
~/.omp/agent/sessions/--E--Project-tty7--/2026-08-09T08-33-15-322Z_019fe5a7-....jsonl
                                   ^^^^^^^^^^^^^^^^^^^^ 对同目录并行的每个 agent 都相同
```

目录段是**项目路径**，对同目录并行的 agent 完全一样；只有 basename 里的
时间戳+uuid 有区分度。所以 `HarnessSessionEnv` 加了 `kind: "path"`：
只取最后一段，**并且一律补哈希**（哈希取完整原值含目录，
所以两个目录下的同名文件也不会共用身份）。

这里没用 `node:path` 的 `basename`——那个函数认的是**本机**分隔符，
而处理的是别人写进环境变量的字符串（测试也可能在 Windows 上喂 POSIX 路径）。

### 7.5 加了“按命名约定自动发现”

表是写死的，而符合 `<TOOL>_SESSION_ID` 约定的工具会越来越多。
于是加了一级兜底：表里没有、但环境里有 `<TOOL>_SESSION_ID` 的，直接收编
（key 前缀取自变量名）。claude 的另一个变量名 `CLAUDE_SESSION_ID` 就靠这级生效。

它的代价是**可能选错**（→ 两个 agent 共用一个 key，也就是刚修掉的那个静默 bug），
所以配了三道缓解：

- 排除名单（`TERM_` / `ITERM_` / `OTEL_` / `ANTHROPIC_` / `SERVER_ECHOED_` / `INVALID_`，
  每一条都是扫描时**实际看到**的）
- 多个候选时**按变量名排序**取第一个，不按 env 枚举顺序
  （枚举顺序不保证稳定，那样同一台机器两次调用可能给出不同身份，比选错更糟）
- `session start` 打印 `identity` 行，选错一眼能看见

### 7.6 pi 与 oh-my-pi 共用一个变量名，顺序有讲究

pi 同时设置 `PI_SESSION_ID` **和** `PI_SESSION_FILE`（oh-my-pi 用的那个）。
所以表里 pi 的条目必须排在 oh-my-pi 前面，否则在 pi 里跑会顶着 oh-my-pi 的身份。
已写成测试（“pi 优先于 oh-my-pi”）。这类顺序依赖必须钉住，否则后人“整理”表格时会静默改坏。

### 7.7 DeepSeek Harness：有源码就别用搜索结果

用户问“deepseek harness 能不能读 session id”时，网页搜索摘要给的答案里包含
`DSH_SESSION_JSONL`。用户直接指向了本地 checkout `E:\Project\deepseek-harness`，
源码里的答案是：

```ts
// packages/shell/shell-env/src/index.ts
if (execution.agent !== undefined) {
  values[DSH_SESSION_ID_KEY] = execution.agent.session.header.id
}
```

`DSH_SESSION_ID` 确实存在（值就是会话 id）。而 `DSH_SESSION_JSONL`
**已被移除**——仓库里的决策笔记
（`.agents/notes/archived/simplification/2026-08-27-persistence-export-and-pre-release-trims.md`）
写得很清楚：那个路径只在 `compression: 'none'` 时诚实，而默认产物是 `.jsonl.zstd`，
bash 根本读不了。**搜索摘要在描述一个已经被删掉的变量。**

两条“变量存在 ≠ 一直有”的前提，都得写进注释：

1. **仅 agent 调用注入**（`if (execution.agent !== undefined)`）。人手动敲的 shell 里
   没有它，会退回旧单文件。反过来，源码说 shell 执行器**每次执行都丢弃继承的 `DSH_*`**
   再合并当前快照，理由写得很清楚：让嵌套 harness 与并发的父子 agent 无法泄露陈旧身份。
   这个设计对我们正好。
2. key 前缀取 `deepseek-harness` 而不是 `dsh` / `deepseek`——这一栏会出现在文件名和
   看板标签上，而 `deepseek` 在 agent 生态里更常指**模型/provider**
   （pi 的 `auth.json` 里 `deepseek` 就是一个 provider 键），用全名避免被读成“用的哪个模型”。

> 推广一下：**核实环境变量名的优先序是 本地源码 > 官方仓库源码 > 本机二进制 > 搜索摘要。**
> 我已经在“二进制”和“搜索摘要”这两档上各坑过一次（见 7.1）。
