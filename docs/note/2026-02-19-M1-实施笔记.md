# M1 实施笔记：踩坑与决策记录

> 对应 [001-总体设计](../plan/001-总体设计.md) / [003-实施计划](../plan/003-实施计划.md) 的 M1 阶段。

## 一、工具/语言层面的坑

### 坑 1：`#` 不是合法的注释语法

`seed-board.ts` 开头写成 `# 看板自举脚本`，Bun 报 `Syntax Error at 1:1`。

JS/TS 只有 `//` 与 `/* */` 两种注释（`#!` shebang 除外）。`#` 是类的私有字段语法。

**排查弯路**：先怀疑是编码/BOM/换行符问题，写了逐行二分脚本定位——结果发现是我的**最小复现用例本身就写错了**（用 PowerShell 造的 `"# c\nconsole.log(1)"` 同样失败）。
教训：验证"工具行为异常"时，先确认自己的复现用例是对的，否则会花大量时间排查不存在的环境问题。

**规避**：本项目所有源码注释统一用 `//`，不用 `#`。

### 坑 2：`Bun.argv.slice(2)` 只在带参数时可靠

`bun run x.ts a b` 时 `Bun.argv = [bun.exe, "x.ts", "a", "b"]`，`slice(2)` 正确。
不带参数时 `Bun.argv` 只有 2 个元素，测试脚本里 `slice(2)` 得到 `[]`。
影响：写参数校验时不能假设 `slice(2)` 一定非空（上一轮的探针脚本就在这上面绕了一圈）。

## 二、SQLite / bun:sqlite 的坑

### 坑 3：Windows 高并发 WAL 写入会偶发 `disk I/O error`

8 进程连续写事务（每进程 10 轮）时偶发 `SQLITEError: disk I/O error`，且**不是锁竞争**——`busy_timeout=5000` 对它无效。这是 SQLite 在 Win32 上 `-shm`（共享内存）初始化的竞争问题。

**处理**（两处，缺一不可）：
1. `errors.ts`：把 `SQLITE_IOERR` / `disk I/O error` 归类为 `BUSY(4)` 而非 `INTERNAL(6)`。
   理由：agent 看到 4 会"退避重试"，看到 6 会"这是 bug，别重试"——分类错误会导致真实故障被忽略。
2. `tx.ts`：`withTx` 内置指数退避重试（40ms → 80ms → 160ms，最多 3 次）。

**重试的前提约束**（写进注释了，未来容易踩）：回调内**只能有数据库操作，不能有外部副作用**（网络请求、外部文件写入），因为重试会重跑整个回调。

### 坑 4：`{ create: false }` 触发 SQLITE_MISUSE

见 [2026-02-19-bun-sqlite-并发探针](./2026-02-19-bun-sqlite-并发探针.md)。打开已存在的库必须 `{ readwrite: true, create: false }`。

## 三、代码设计层面的问题（M1 实施中暴露的）

### 问题 5：事务边界必须由最外层统一

`init` 里出现 `cannot start a transaction within a transaction`：`setInitialConfig` 自己开了事务，而调用方已在 `withTx` 内。

**决定**：任何"写一组数据"的函数**不开自己的事务**，事务边界永远在最外层（`withTx`）。这样"建库 + 写配置 + 记事件"是一次原子提交。

### 问题 6：`Db` 包装对象与裸 `Database` 混用导致运行时空指针

`getMeta(db: Db)` 实际用 `db.raw.query`，而调用方传了裸 `Database`（来自 `ctx.db`）。
Bun 报 `db.query is not a function`，堆栈不指向真正的错误点。

**决定**：`getMeta`/`setMeta`/`getConfig`/`setInitialConfig` 的参数类型统一为 `Database`；
只有需要路径信息的 `openDb`/`applySchema`/`migrate` 才用 `Db` 包装。

### 问题 7：init 的幂等分支不自愈

第一次 init 中途失败（用户 Ctrl+C）会留下"库已建、meta 不全"的半成品。原实现看到 `schema_version` 存在就直接返回，项目永远缺 `project_name`。

**决定**：幂等分支也要调 `setInitialConfig` 补齐缺失项（该函数只写不存在的键，不覆盖用户调整）。

### 问题 8：ANSI 转义符被算进表格宽度 → 终端列错乱

`padEndWidth` 用 `.length` 算宽度，彩色文本的 `\x1b[36m` 被计入，导致 holder 列显示成 `s-avu9e3…`。

**决定**：`displayWidth`/`padEndWidth`/`padStartWidth` 内部先 `stripAnsi`。
顺带把中文全角宽度（`displayWidth` 算 2 列）也在这里统一处理。

### 问题 9：抢占他人持有的卡，报错类型错了

原 `claimTask` 前置检查把"别人正在做"归类为"非法转移"（STATE/2），导致 agent 以为是自己的用法错误从而反复重试。
正确语义是 **CONFLICT/3 + holder 详情**，让 agent 改做别的任务。

同时补上了设计里没写清的一条：**租约已过期的 doing 卡可以被接管**（这是崩溃恢复的关键路径，原实现的前置检查会直接拒绝）。

**决定**：`claimTask` 前置分支拆成三类——todo（走条件 UPDATE）/ doing-自己（续租）/ doing-别人（force 或 租约过期 或 CONFLICT）。

### 问题 10：`next_actions` 给错建议比不给更糟

`task add` 原本无条件建议"认领"，但如果任务有未完成依赖，agent 照做后会卡住。

**决定**：`nextActionsForNewTask` 接收 `unfinished` 参数，依赖未满足时改为建议"先做上游"。
board 的"可认领/⏳ 等"标记与 `--ready` 过滤共用同一个 `isClaimable` 判据，避免两处逻辑不一致。

### 问题 11：自动解锁只处理 blocked，漏掉"本来就是 todo"的情况

`T-0002` 依赖 `T-0001`，状态本来就是 `todo`（只是不能认领）。`T-0001` 完成时，
原实现只检查下游是否为 `blocked`，于是**没有发出"现在可以开工了"的信号**。

这是最容易被漏掉的一环：agent 等的是通知，不只是状态。

**决定**：`notifyDependentsReady` 对 `blocked` 改状态、对 `todo` 只发事件，两种都在 `unblocked` 返回列表里，
CLI 输出"依赖它的任务现在可以开工了"。

### 问题 12：`done` 转移被误加 `requireReason`

完成一件事本身不需要理由，`--note` 才是可选的。取消/重开/阻塞才需要说明原因。
实现时给 `done` 也加了 `requireReason`，导致 `task done T-0001 --note "..."` 报"需要 --reason"。

**决定**：转移表的 `requireReason` 只用于 `blocked`/`cancelled`/`reopened`；`done` 去掉。
这与设计文档 §5.2 一致（文档是对的，实现走偏了——提醒：**实现与文档冲突时要先判断谁对**）。
