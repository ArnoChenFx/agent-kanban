# M3 计划版本化与事件重放笔记（2026-02-19）

> 主题：让"事件是唯一事实来源"这句话**可被验证**，而不只是一句口号。
> 结果：新增 `core/plans.ts` / `core/rebuild.ts` / `commands/plan.ts` / `commands/rebuild.ts`，
> schema 升到 v4，测试 77 → 95。

## 一、先写代码还是先验证？

正常顺序是先写功能再补测试。这次反过来：**先假设 rebuild 能work，再去补齐让它 work 的东西**。

结果发现：事件 payload 根本不足以重建投影。缺的不是某个字段，而是**一整类字段**：

| 缺口 | 后果 | 修法 |
| --- | --- | --- |
| `task_created` 缺 body / checklist / estimate_ms | 重建出的任务丢正文与工时 | 事件携带建时完整快照 |
| `task_progress` 的 checklist 只有 `{text, done}` | 重建后 done_at / by 被抹成 null | 快照带完整项 |
| `task_updated` 只有字段名 | 无法还原 edit 的结果 | `fields` 存新值（本来就存的是新值，只需注释说明） |
| `handoff_created` 只有 `handoff_id` + `kind` | 交接内容完全无法重建 | 事件携带完整交接行 |
| `plan_created` / `plan_superseded` 无内容 | 计划无法重建 | 事件携带完整计划行 |

**教训**：事件溯源架构里，"事件是唯一事实来源"这个承诺的强度，
完全取决于**每个事件 payload 是否携带了重建该投影所需的全部信息**。
M1/M2 只关心功能能不能跑，payload 里缺字段不会暴露任何问题——
只有当你去尝试重建时，它才会现形。

## 二、rebuild 的核心设计：先算再比，默认不写

朴素实现是"清空投影表然后重放"。但那意味着**事件历史一有缺口，用户辛苦攒的看板就被抹掉**。

所以这里的顺序是：

1. 读事件流
2. 在**内存**里重放出完整投影（`Projection` 对象）
3. 与库里现有投影**逐字段**比对，产出 drift 列表
4. **默认到此为止**（纯只读，可进 CI）
5. 只有显式 `--write` 才落库，且要求无 drift（或 `--force`）

这样 `agent-kanban rebuild` 变成一条**零风险**的日常命令：
随时可以跑，跑了不会坏任何东西。真正的修复需要用户明确下决心。

写回本身必须**在一个事务里**：DELETE 四张表再逐行 INSERT，
中途失败（约束冲突、磁盘满）如果不在事务里，会留下"表被清空但没填回"的半写状态。
那种状态比漂移严重得多——漂移是数据不对，半写是数据没了。

> 这个 bug 是真的发生过一次：我在加事务保护之前跑了一次 `--write`，
> 当时 `insertDep` 漏了 NOT NULL 的 `created_at`，
> 结果 plans 和 task_deps 被 DELETE 之后 INSERT 失败，**真的丢了数据**。
> 好在事件流还在，`rebuild` 本身就是恢复手段——这算是被自己的工具救了。

## 三、rebuild 抓出来的两个真实 bug

### 1. `task done` 隐式改 progress 却不记事件

`transition` 在 `to === "done" | "review"` 时会 `progress = 100`，
但只发 `task_done` 事件，不发 `task_progress`。
结果事件流里最后一条 progress 还是 60%，rebuild 重算出 60，与库里的 100 不符。

**修法**：progress 变了就补发一条 `task_progress`，并标 `implicit: "transition→done"` 说明来源。
凡是**隐式修改投影字段**的地方，都必须留事件痕迹，否则事件流就不是完整历史。

### 2. `removeTask` 完全不写事件

删任务时只 DELETE 表，不发任何事件。于是事件流里还留着 `task_created`，
rebuild 会把已删任务**复活**。

**修法**：新增 `task_removed` 事件类型（类型表加一个字面量），带 `removed_deps`，
rebuild 遇到它就删掉对应的投影行和依赖边。

这也说明 rebuild 的价值是**双向**的：不只是验证写入路径有没有 bug，
也能发现"该写事件的地方没写"这类结构性遗漏。

## 四、顺带发现的 project 隔离漏洞（schema v4）

实现 rebuild 时 `compareDeps` 报 `no such column: project_key`，
顺藤摸瓜发现 **ADR-9 漏了 `task_deps` 这张表**：

- 主键是 `(task_id, depends_on_id)`，不含 project
- 而 T-编号是 per-project 的 → project A 和 project B 的 "T-0001 依赖 T-0002" 撞同一条记录
- `INSERT OR IGNORE` 会**静默**丢弃后者的依赖（当成重复）
- `getDependencies` / `getUnfinishedDeps` / 环检测全都不带 project 过滤

单 project 场景（本地模式、迁移前的库）完全不会暴露这个 bug，
但它会让"一个 server 管多个 project"在**有依赖关系时静默出错**。

**修法**：schema v4 迁移重建 `task_deps` 表，PK 改为 `(project_key, task_id, depends_on_id)`，
回填靠 `tasks` 表反查 project_key（匹配不到时退化为最早创建的 project）。
全部 8 处 SQL 补上 project 过滤，`findCyclePath` / `wouldCreateCycle` 也要传 projectKey。

## 五、不参与比较的两个字段

`lease_expires_at` 与 `updated_at` 被**有意排除**在比较之外：

- 租约每次心跳/续租都会前移
- 而续租**不写事件**（否则事件量会被心跳淹没，一个活跃项目一天能写几十万条）
- 所以 rebuild 后这两个字段会回到"最后一次有事件时的值"

这是设计上的正常现象，不是漂移。文件头与 CLI 帮助里都写明了这一点。
首次 heartbeat 会立刻刷新它们。

对比之下，**checklist 的 `done_at` / `by` 必须参与**并能重建：
它们不是高频易变字段，且一旦重建丢成 null 就破坏了幂等性
（`--write` 跑一次就把"谁勾的"洗没了）。取舍标准是：**重建必须无损**。

## 六、计划版本化

`plan save` 每次产生新版本，旧版本转 `superseded` 并被 `supersedes_id` 串成链。

- 项目级 `PL-0001` / 任务级 `PL-T-0007-01`
- 保存后自动挂到任务的 `plan_id` 上（`agent resume` 时能读到"当时怎么打算的"）
- `plan history <id>` 回溯版本链，"这个计划改了几次"
- `plan at --task T-0007 --ts <ms>` 时间旅行，"一小时前生效的是哪版"

实现时踩的一个坑：`getActivePlan` 的 SQL 里用了字面量 `'task'` / `'project'`，
却仍然多传了一个 `planScope` 绑定值，bun:sqlite 严格校验参数个数 →
`SQLite query expected 2 values, received 3`。
现在 `planScope` 只用于入参校验（task 作用域必须有 taskId，反之亦然），
不再传给 SQL。

## 七、顺带修掉的一个配置 bug（空环境变量屏蔽配置文件）

更新 `verify-remote.ts` 第十步时发现：即使把 `KANBAN_SERVER` 显式置空，
仅靠 `config.toml` 仍读不到远程任务。原因是：

```ts
const serverRaw = cli.server ?? env.KANBAN_SERVER ?? fileConfig.server;
```

`??` **不跳过空字符串**。`export KANBAN_SERVER=`（或 CI 里
`env: { KANBAN_SERVER: undefined }` 被序列化成 `""`）会让 server 变成空字符串
→ `Boolean(cfg.server)` 为 false → 判为本地模式 → 静默在本地新建空库，
**没有任何报错**，只是“数据不见了”。

**修法**：所有来自 env/CLI/file 的值先过 `nonEmpty()`（trim 后非空），
空串与 `undefined` 同等对待。已补两个回归测试（空串、纯空白），
并顺手把 token hint 里已删除的 `agent-kanban remote show` 改成 `agent-kanban config show`。

> 教训：配置合并里 `??` 与 `||` 的区别不是风格问题。
> 凡是从"用户可控制的外部输入"取值，都必须显式处理空值语义。
