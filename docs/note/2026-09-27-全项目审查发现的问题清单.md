#0、会话心跳从未被刷新（已修）

## 症状

一个**完全正常**的 agent——连续工作 30 分钟、每 3 分钟调一次 `task progress`——
在第 12 分钟被系统判成失联（crashed），自己那张进行中的卡被回收回 `todo`，
还被凭空合成了一条 **造假的** crash 交接，内容是
「the holder went silent (12 min without a heartbeat)」。实测：

```
t+ 9min  session=active    task=doing  assignee=sW  progress=30%
t+12min  session=crashed   task=todo   assignee=null progress=40%  ← 被判失联并回收了！
...
[crash] 要做的卡: progress 40%, the holder went silent (12 min without a heartbeat).
```

## 根因

失联判据是 `sessions.last_seen_at`（ADR-4 L1），而设计上它必须由**普通调用**刷新——
`sessions.ts` 与 `schema.sql` 的注释都写着「**任何 CLI/MCP 调用都会刷新 last_seen_at**
（agent 本来就在调命令，零额外心智负担）」。

实际实现里 `touchSession` **零调用点**，而 `events.recordHeartbeat` / `lastHeartbeatTs`
同样零调用点（整段心跳事件节流机制从未接线）。于是 `last_seen_at` 只在
`session start` 与显式 `agent-kanban session heartbeat` 时更新。

## 为什么它特别难被发现

1. **触发门槛就是最普通的用法**：默认 grace 10 分钟，只要干活超过 10 分钟就中招。
2. **全程不报错**：`task progress` 照常成功。回收后 `assignee_session_id` 变 NULL，
   而 `updateProgress` 只在「非 NULL 且不是我」时才抛冲突——所以 agent 毫无察觉地
   继续在一张已经被系统判定为「无主」的卡上写进度。
3. **agent 用来证明自己活着的命令正是杀死它的命令**：`reapZombies` 是在
   **每条命令开头**无条件跑的（`openLocalCtx`）。
4. **它制造出项目要防的那个后果**：新会话跑 `context` 会看到「有 crash 交接等你接手」，
   于是另一个 agent 去抢一张**此刻正有人在做**的卡——重复劳动。
5. **单 project 本地模式就会触发**（下面 #1 那条要开第二个 project 才会）。

## 修法

1. `touchSession` 自带节流（`TOUCH_THROTTLE_MS = 60s`）并返回是否真写了。
   不节流的话，「每条命令算心跳」等于「每条命令一次写」，会把写锁抢成常态。
2. `ops.ts` 的 `executeOp` 里接入：远程模式下 client 没有数据库，**只有 server 端能刷**，
   而 ADR-10 要求两端同源，所以刷新点必须在 core 而不是命令层。
3. `commands/context.ts` 的 `openLocalCtx` 里**在 `reapZombies` 之前**接入。
   顺序是硬要求：先回收后刷新的话，被回收的正是执行这条命令的自己。
4. 顺手修掉 #15：`reapZombies` 先做一次只读探测，确认真有僵尸才开写事务。
   原来每条只读命令（`task list` / `board` / `context`）都要抢一次全库写锁。
   事务内会用同一判据重查，所以探测只是优化，不引入竞态。

## 守卫

`test/session-heartbeat.test.ts`（10 条），三层：

- **行为**：连续工作 30 分钟仍 active 且持有卡；真失联仍会被回收且进度保留；
  只失联一个 session 不影响另一个。
- **节流与边界**：窗口内不重复写、会话行不存在返回 false、时钟回拨视为新鲜、
  无僵尸时不开写事务。
- **接线**（防重构回退）：`executeOp` 里的调用点存在；`openLocalCtx` 里
  `touchSession` 的位置在 `reapZombies` **之前**；节流常量不被删。

接线层不是凑数：上层行为测试全靠「executeOp 会刷新」这个前提，
真被摘掉时它们会以「心跳没刷新」的方式集体变红，但**报出来的错指向 reapZombies**，
查不到真正原因。

已验证：临时把 `executeOp` 里的刷新改成 `if (false)` 后，两条关键行为测试确实变红；
临时删掉只读快路径后，「没有僵尸时不开写事务」确实变红。真实 CLI 端到端也确认
（静默 65 秒后跑一条 `task list`，`last_seen_at` 变成 0.1s 前）。

顺带记录一条待清理：`events.recordHeartbeat` / `events.lastHeartbeatTs` 至今仍是死代码
（`session_heartbeat` 事件类型从未被写入过）。`buildConflictError` 与
`buildCrashSummary` 里对 `session_heartbeat` 的过滤也因此是空转。这次没动，
因为接通它只会增加事件量而无功能收益；按设计意图，`last_seen_at` 才是承重的那一套。

# 验收脚本污染真实看板（本轮新发现，已修）

**这不是上面清单里的条目，是修 #2 的时候当场踩到的。**

## 症状

修完 #2 准备把卡片标完成，发现看板被冲掉了：真卡只剩一张 `实现崩溃恢复`
（p0、60%、holder 是某个不认识的 session）——而那正是 `scripts/verify-rebuild.ts` 的夹具数据。

## 根因

`scripts/verify-rebuild.ts` 与 `scripts/verify-recovery.ts` 用 `cwd: ROOT` spawn CLI，
**并且开头就 `init --force`**：

```ts
await run(["init", "--force", "--name", "agent-kanban"]);   // cwd: ROOT
```

也就是说：**每次有人跑这两个验收脚本，开发者自己的看板就被重置 + 灌夹具卡。**
verify-rebuild 更狠，中途还要**故意改坏投影**再修复：

```ts
db.query("UPDATE tasks SET title = '被偷偷改过的标题', status = 'doing' WHERE id = 'T-0002'").run();
db.query("UPDATE tasks SET progress = 99 WHERE id = 'T-0003'").run();
db.query("DELETE FROM task_deps WHERE project_key = ? AND task_id = 'T-0003'").run(projectKey);
```

verify-recovery 也要直接改库（把心跳改旧来模拟崩溃）。

## 为什么之前没人发现

`AGENTS.md` 早就记过这个坑：

> **别让验收脚本的 CLI 跑在仓库根**：`session start` 会把身份写进 `<cwd>/.kanban/sessions/<key>`，
> cwd 是仓库根就会**覆盖开发者自己的身份文件**。`scripts/verify-web-ui.ts` 因此把 `run()` 的
> cwd 换成临时目录。

问题是**只修了 `verify-web-ui.ts` 一个**。另外三个（`verify-web.ts` / `verify-remote.ts` /
`snapshot-web.ts`）碰巧都传了 `--db`，所以库没被动（cwd 只影响身份文件）；而
`verify-rebuild.ts` / `verify-recovery.ts` 既没传 `--db` 也没换 cwd，于是双重命中。

## 修法

- 两个脚本照搬 `verify-web-ui.ts` 的做法：`mkdtempSync` 建临时目录 → `cwd: dir` +
  显式 `--db` → 收尾 `rmSync`。
- **加静态守卫**（`test/write-project-isolation.test.ts`）：
  spawn CLI 时若 `cwd` 可能是仓库根，而全文没有 `--db` / `KANBAN_DB` → 判失败。
  判在**文件级**而不是 spawn 块级——`--db` 通常写在传给包装函数的参数数组里，
  块级扫描会误报（第一版就是这么写的，一开始报出 5 个假警报）。
- 特意**不**要求「所有碰 CLI 的脚本都建临时目录」：`seed-demo` / `dogfood` 本来就该
  操作仓库里那个库（它们是工具，不是回归）。守卫只管「不要**隐式**用 cwd 定位库」。

## 已实测

```
BEFORE tasks= 19 events= 78
verify-rebuild exit=0 / verify-recovery exit=0 / verify-remote exit=0 / verify-web exit=0
AFTER  tasks= 19 events= 78
```

四个脚本全跑通，真实看板一个字节没动。

## 教训

看板本身是对的（`task remove --force` 走事件路径、`rebuild` 自证通过），
**但它挡不住有人绕过 API 直接 `init --force`**。所以「代码没写错」不等于「数据没丢」。

# 三个本轮新发现（不在原清单里）

## A. 流程事故：我全程没 claim 任何卡

审查进行到一半才发现：**19 张卡的活全是在「无主」状态下干的**，而且做完 5 张也没标 done。

后果不是「不好看」，而是两个具体损失：
- 整套 lease 机制一次都没被触发。如果那个会话中途崩了，看板上看不出任何人在任何卡上。
- **看板在撒谎**：它显示「13 todo / 0 doing」，而实际上有 6 张正在做、5 张已经做完。
  而「让看板如实反映真实状态」正是这个产品存在的理由。

同一天里我已经因为验收脚本污染（另一节）犯过一次同类错误：**代码写对了不等于数据对了**。
看板本身能挡住误操作，挡不住绕过它。

## B. 设计缺口：长时间不调 kanban 命令就会被回收

上面那张卡后来还是被回收了——机制在正常工作：

```
claim 完 6 张 → 去跑 bun test（44s）+ 一串 verify 脚本（数分钟）
→ 期间没有任何 kanban 命令 → 超过 10 分钟宽限 → 判失联 → 收回卡片（进度保留）
```

`last_seen_at` 只由 **kanban 命令**刷新。所以一个 agent 在一段长的**非 kanban** 工作
（跑测试、跑构建、改代码）里待超过 `grace`，就会在干活过程中被当成失联者。

这与 #0 是**两个不同的问题**：#0 是「从不刷新」（每个会话都会中招），
而这里是「只在 kanban 命令时刷新」（只有长时间不调命令的会话会中招）。
#0 的修复让每次调命令都能续命，但没有、也不应该让**非 kanban 的活动**去续命——
否则一个挂死的进程只要还在跑任何东西就永远收不回来。

**缓解办法**（当前）：长于 `grace` 的非 kanban 工作前后各调一次 `task progress`。
**真正的解法**（未做）：把 grace 与「agent 声明的预计时长」挂钩，
或让 `serve` 侧提供一种「我在忙」的显式声明。这是 #0 之后的下一个待办。

## C. 流程事故：两张卡标了 done，checklist 却一项没勾
关掉 T-0006 / T-0007 时我用一个硬编码的检查项列表去循环 `--check`，而且
**把输出 `*> $null` 吞了**。结果是 `checklist_item_not_found` 报错完全看不见，
而 `pct 100` → `review` → `done` 照样一路绿灯。T-0007 的 0/4 有确切原因
（我用的是 T-0006 的项列表，两张卡清单不同）；T-0006 的具体原因没能复原，
但两者是同一个错误：**批量循环 + 吞输出**。

更值得记的是：**它对整套工具链完全隐形**。

| 检查 | 结果 | 为什么 |
| --- | --- | --- |
| `bun test` | 绿 | 测试不检查看板内容 |
| `rebuild --check` | 绿 | 投影与事件流确实一致——库里就真是「done 且未勾」 |
| `verify:*` 全套 | 绿 | 没有一条覆盖「断言与证据是否一致」 |
| 人眼扫看板 | 看不出 | 几个空框混在十几张卡里 |

也就是说：**看板的自证机制覆盖不了「断言与证据不一致」**。这是本项目的一个
结构性盲点，补法是给 `doctor` 加一条显式检查（`done_with_unchecked_checklist`，
只报不修——勾选是人的判断，doctor 替你勾上就把「有意放弃」与「忘了做」混成一样）。

**教训与 A 同源**：两次都是「代码/命令全绿」掩盖了「看板在说谎」。
区别在于 A 是我绕过看板，B 是我**通过**了看板但内容是假的。
看板能挡住误操作，挡不住一个不看输出的人。

## D. 用户发现的真 bug：卡片完成后，交接仍挂在「待接手」里

界面上挂着 6 条红色告警：

> the previous holder s-niz0mr went silent (10 min without a heartbeat, the process may have crashed)

而那 6 张卡**全部已经 done、progress 100%**。也就是说 `context` 一直在叫 agent 去接手
**已完成的活**，而且交接正文里的「progress 0%」与库里的 100% **直接矛盾**——
两条都是假信息，而且假得很具体，比「没有提示」更坏。

成因链：

1. 一次回收为 6 张卡合成了 crash 交接（那时它们确实是 todo，语义**正确**）；
2. 随后那 6 张卡被正常做完并标 done；
3. **没有任何东西在卡片到达终态时作废它的交接。**

修法是**读侧**过滤（`pendingHandoffs` / `countPendingHandoffs` 都加
「卡片未到终态」），**不在完成时自动消费**：

- 自动消费会销毁一个事实——「这张卡曾经被丢下过」，而那正是审计价值；
- 读侧过滤**顺带修好存量**：库里已有的 6 条陈旧交接不需要迁移，界面立刻干净；
- 判据用**当前状态**而不是「完成时打个标记」，所以被 reopen 的卡（done → todo）
  它的旧交接会重新变得相关——这正是想要的语义。

守卫 `test/handoff-pending-scope.test.ts`（7 条），含一条接线守卫：两条读路径
必须用**同一条**过滤，否则角标会说「2 条待接手」而侧栏一条不列。
逐条回退 2/2。

> 这条 bug 与 B 是同一条链的两端：B 让我的会话被回收，C 是 B 的**可见后果**。
> 而真正让它变成「假信息」的，是第 3 步那个缺失的不变量。

### 1. 16 条写路径漏掉 `project_key` → 跨 project 静默损坏数据（已修）

`tasks` 的唯一约束是 `UNIQUE(project_key, id)`，**T 编号是 per-project 的**（ADR-9 的核心设计：
agent 口语里的 "T-0007" 必须只指向本 project 的卡）。但 `tasks.ts` 里几乎所有
`UPDATE tasks` 只按 `id` 匹配，而 `id` 在全库范围内不唯一。

**实证 A**：在 `pa` 里对 T-0001 依次 claim → progress → release → edit → done，
`pb` 的 T-0001 被同步改掉（状态、进度、标题一起变）：

```
--- 1) 在 pa 里 claim 之后 ---
  {"project_key":"pa","id":"T-0001","status":"doing","assignee_session_id":"s-A", ...}
  {"project_key":"pb","id":"T-0001","status":"doing","assignee_session_id":"s-A", ...}   ← 被误改
```

**实证 B（连锁）**：污染会反过来打掉 claim 判定。`pa` 抢了 T-0002 之后，在 `pb` 里
**根本抢不到自己的 T-0002**，直接 CONFLICT「being worked on by sA」——
错误信息指向一个根本不存在的持有者。

**实证 C（最恶劣的一处）**：`sessions.ts` 的 `reapZombies` 会把**别的 project 里由健康会话持有的卡**
释放掉：

```
初始：pa/T-0002 → sA（心跳停在 30 分钟前）,  pb/T-0002 → sB（30 分钟前刚心跳，完全健康）
reap crashed = ["sA"]
--- 回收之后 ---
  {"project_key":"pa","id":"T-0002","status":"todo","assignee_session_id":null}
  {"project_key":"pb","id":"T-0002","status":"todo","assignee_session_id":null}   ← sB 正在做的卡被抢走
```

这正好摧毁整套租约机制存在的理由：防两个 agent 重复劳动。

### 2. 计划 ID 跨 project 撞主键 → `plan save` 在多 project server 上不可用（已修）

```
pa → plan id = PL-0001
pb → ❌ unique constraint failed (usually a normal race under concurrency), safe to retry once
pa 任务级 plan id = PL-T-0001-01
pb 任务级 → ❌ unique constraint failed ...
```

两重问题：

1. **功能**：第二个 project 存不了任何计划，而 ADR-9 声称支持「一个 server 管多个 project」。
2. **错误分类**：`src/core/errors.ts` 把 UNIQUE 冲突一律映射成

### 3. `rebuild` 自证与投影互相矛盾（已修；实际有 5 处不一致）

`src/core/rebuild.ts` 的 `task_review` 处理器把 `assignee_session_id` 与 `lease_expires_at`

`t.status = t.assignee_session_id ? "doing" : "todo"` 区分「评审打回」与「终态重开」——

#### 已完成（2026-09-27）

## 二、安全问题

### 4. `tokens.id` 存的就是明文 token —— 整套哈希设计形同虚设

`src/core/tokens.ts`：

```ts
const plaintext = generateToken();
const id = plaintext; // token 的 id 就是 key 本身（便于用 key 直接查）
```

而文件头注释与 `src/core/schema.sql` 都写着「**库里只存 key_hash（SHA-256）**，
明文只在创建/轮换时显示一次」。实际效果是：任何能读到 `kanban.db` 的人
（备份、`export` 产物、误提交、截图、只读挂载的运维脚本）都拿到全部**在用**的 token。
`key_hash` 列纯属摆设，鉴权走的是 `WHERE id = ?` 的明文直查。

修法：`id` 改成独立的随机 uuid（`t_` + 16 hex），加 `UNIQUE` 索引到 `key_hash`，
鉴权改为 `WHERE key_hash = ?`。**这是破坏性变更**——存量库里所有 token 会失效，
需要一次迁移 + 明确的升级说明（v2→v3 的 token 迁移已经处理过一次"旧 key 无法恢复"，
可以复用那套沟通方式）。

### 5. admin 页的「吊销」与「移除授权」按钮完全失效（已修，随 #4 一并解决）

`tokenToJson` 返回的是 `maskToken(token.id)`（形如 `k_1a2b…cdef`），
而 `/api/admin/tokens/:id/*` 要的是完整 id。admin 页把掩码当 id 发出去 → 必然 404：

- `src/server/admin-page.ts` 的 `revokeToken(tk.id)`（吊销按钮）
- 同文件 `revokeProjectGrant(tk.id, ...)`（移除单个授权的 × 按钮）

**签发之后页面永远拿不到完整 id**（只有创建那一次响应里带 `plaintext`），
所以这两个按钮从来没成功过。`test/` 下**零覆盖**——这正是它能活到现在的原因。

**根因就是 #4**：`token.id` 当时就是明文密钥，所以只能掩码。一改成独立的
`token_ref`（不承担鉴权职责），`tokenToJson` 就可以直接给全，admin 页自然通了。
守卫在 #4 那批里一并补上（`dual-mode.test.ts` 的 HTTP 层两条 + `token-storage.test.ts` 一条）。

### 6. 契约与实现不符

### 7. 其他安全项（已修，三项都做完了）

#### (1) SSE 的 token 走 URL query

`web/src/lib/api.ts` 的 `subscribeEvents` 把 token 放进 `/api/stream?...&key=k_xxx`
（`EventSource` 不能设自定义 header，所以「只能」这么干）。而 URL 会进浏览器历史、
反代 access log、容器日志与 `Referer`——项目自己的 `consumeUrlLogin` 注释就很担心
token 泄漏，但 SSE 每条连接都在这么干。

**改成两条路径，URL 里不再出现 token**：

| 客户端 | 方式 |
| --- | --- |
| 浏览器 `EventSource`（不能设 header） | `POST /api/stream-ticket`（header 鉴权）换一张 **60 秒一次性**票 → `?ticket=` |
| 能设 header 的客户端（`core/backend-remote.ts` 的 `streamEvents`、验收脚本） | 直接 `X-Kanban-Key` header，不必换票 |

关键决定：
- **服务端彻底删除 `?key=`**，不留后门（否则漏洞原封不动）。
- 票据存在**内存**里、**只能用一次**、与 project 绑定。放数据库的话等于给免鉴权面
  开一个「读表即可拿到凭据」的新口子。
- 旧的 `subscribeEvents` 直接删除，不留一个「参数收下但不用」的死函数。

#### (2) SSE 长连接不重新鉴权

token 中途被吊销，已建立的连接会继续推事件直到客户端重连。pump 里现在**每 30s 重验一次**，
失效就推 `event: auth_expired` 再关流——客户端据此清掉登录态。
不推这个事件的话，界面会一直显示「在线」却收不到任何事件，而重连也一样被拒。

用**墙钟**而不是 tick 计数判到期：机器卡顿时也不至于把复验窗口拉长。

#### (3) `/api/health` 泄漏全局水位

免鉴权端点曾返回 `{ok, version, projects, head_seq}`。`projects` 是全库 project 数、
`head_seq` 是全局事件水位——那是**信息**不是健康检查，而任何能碰到端口的人都能免费拿到。
现在只回 `{ok, version}`（消费方 compose healthcheck / verify-auth / verify-binary
都只读 `ok`；契约文档与两份 README 同步）。

#### 守卫

`test/sse-security.test.ts`（11 条）
- health：只回 liveness（行为 + 源码两层）。
- URL：裸 `?key=` → 401；header 能连；票能用一次、重放必 401；票与 project 绑定；
  换票需要有效 token；**源码里不再有把 token 拼进 URL 的地方**（Web / backend / 服务端三处）。
- 复验：源码里有 `reauthIfDue` + `authenticate` + `auth_expired`；Web 收到后清登录态。
- **真实闭环**（30s）：签一个项目级 token → 用票连上 → 吊销 → 断言收到 `auth_expired`。
  这条是真起了 server、真跑了 30 秒复验周期，不是静态扫描。
- 逐条回退验证 5/5。

扫描类断言一律**先剥注释**（`code()` 辅助函数去掉块注释与行注释后再匹配）。

## 三、实现与设计/文档不符

### 8. `blocked` 不释放租约，但 MCP 工具描述说它释放（已修）

`transition()` 只在 `isTerminal` 和 `to === "todo"` 时清 `assignee_session_id` /
`lease_expires_at`；转 `blocked` 两项都留着。实测：

```
status = blocked / assignee_session_id = s-dead / lease_expires_at = 1700000900000
```

10 小时后（持有者会话行根本不存在了）：`reapZombies` 只回收 `status='doing'`，
`doctor` 的孤儿检查也只筛 `doing` → **这个幽灵持卡人永远挂着**，
UI 上 blocked 卡永远显示一个死掉的 assignee。

而 `src/mcp/tools.ts` 的 `kanban_task_block` 描述写着
*"Mark a task blocked. **Releases the lease** so someone else can pick it up."*
——描述与行为直接矛盾。而 **agent 读不到源码，它只能读描述**，
于是会基于错误的预期行动（「阻塞了，别人应该能接」）。

#### 已完成（2026-09-27）

语义定为「**阻塞 = 放手**」，理由三条：

1. `claimTask` 不接受 `blocked`，所以留着租约**毫无用处**；
2. `reapZombies` 与 doctor 都只管 `doing`，留着就等于**永久残留**一个死掉的持卡人；
3. 与本项目另一条已定规则一致：「回到待认领池 = 清 assignee + lease」
   （自动解阻与手动 unblock 早就这么做了）。

- `transition()` 的 `to === "blocked"` 分支补上清 assignee + lease。
- `rebuild` 的 `task_blocked` 同步（否则 `claim → blocked` 会报漂移——
  这条由 `rebuild-state-paths.test.ts` 自动盯住）。
- MCP 工具描述改成与行为一致的英文，并注明「以前描述就是这么写的、但实现没跟上」。
- 守卫 `test/mcp-tool-contracts.test.ts`（3 条）+ `state-machine.test.ts` 两条：
  把**「描述里承诺的副作用」变成可执行断言**——描述说释放租约，实现就必须释放。
  另有一条粗筛：任何工具描述里出现 “releases the lease” 时，
  `transition` 的 blocked 分支里必须真的有清租约的代码。
- 逐条回退验证 4/4（含「描述与行为一起失守」这个方向）。


### 9. `describeEvent(plan_superseded)` 渲染出字面量 `undefined`（已修；实际缺 17 个 case）

`src/core/events.ts` 读 `d.old_plan_id`，但 `savePlan` 发的事件 `data` 里是 `id`：

这直接违反仓库自己在 `test/cli-output.test.ts` 立的「输出里不许出现 undefined」规矩。
测试没抓到只是因为那套 fixture 从不建计划——**事件根本没产生过**。

**但真正的规模比这大**：静态扫描后才发现两个渲染函数加起来**缺 17 个 case**
（`context.describeEventBrief` 缺 11 个）。缺 case 有两种后果：
- 读错字段层级 → 字面量 `undefined`（最刺眼）
- 根本没 case → `default: return event.type`，把 `plan_superseded` 这种内部名字

#### 已完成（2026-09-27）

- **补齐两个渲染函数缺的 17 个 case**。

- 逐条回退验证 4/4。


### 10. `buildContext` 的 `tail` 与 `consumeHandoffs` 两个入参是死的（已修）

`src/core/context.ts` 里 `const { scope, now, graceMs, tail = 20 } = input;`——
**`tail` 和 `consumeHandoffs` 都没被用过**。`tail` 传什么都不影响（内部硬编码 3）；
`agent-kanban context --tail N` 因此一直是个**空转的 flag**。

更实质的问题：`consumeHandoffs` 由 `ops.ts` 在**读完 context 之后**另开一个事务去消费，
而且它**又查了一次** `pendingHandoffs`。两次查询之间新到的交接会被
「**消费掉但 agent 从没看到过**」——既没人读过，也不再挂着，等于凭空丢一条。

#### 已完成（2026-09-27）

- **两个死参数都删掉**（`ContextInput` 只剩 4 个字段；`context.get` 的 Op 只剩 `consume`；
  CLI 的 `context --tail` 一并删掉）。选择删而不是「接线」的理由：
  给已有 Op 参数**发明新语义**会影响所有调用方，比删掉更糟。
  `resume --tail` 是另一个活参数（时间线条数），保留。
- 消费改为**只消费 `result.pending_handoffs` 里那几条**。
- **不把读+消费塞进同一事务**，理由写进代码注释：真正的互斥靠租约，不靠
  `consumed_by`。`consumeHandoff` 对已消费的交接是 no-op，所以两个 session 同时
  `context --consume` 最多是「都以为自己消费了」；真要动手时 `resume` 走 `claimTask`，
  租约有效时后到的那位拿到 CONFLICT。为它引入事务嵌套反而会让「读」变成写路径。
- 守卫 `test/context-consume.test.ts`（8 条），其中最关键一条是**结构守卫**：
  行为用例抓不住这个 bug——无竞态时「按返回值消费」与「再查一次消费」拿到的是
  **同一批**（同样的查询 / limit / 排序），两者只在竞态时分岔，而竞态无法确定性复现。
  （第一版探针就因为这个报「没抓住」，差点让我以为修复无效。）
  所以改成钉住不变量本身：`context.get` 分支**不得自己再调 `pendingHandoffs`**，
  且必须从 `result.pending_handoffs` 推导 id。
  另有一条反向守卫：`ContextInput` 的每个字段都必须在 `buildContext` 函数体里被读过
  （防止再出现「声明了却从不使用」的开关）。
- 逐条回退验证 3/3。

### 13. `validateOp` 名不副实

`src/core/ops.ts` 的注释写「server 端会对每个字段做类型/范围校验」，

### 14. 看板静默截断到 500 张卡（已修）

`src/core/board.ts` 的 `buildBoard` 硬编码 `limit: 500`，而 `counts` 来自全量
`countByStatus`。所以一个 620 张卡的 project：计数显示 620，界面只渲染 500，
**没有任何"还有更多"的提示**。`ListTaskParams` 也**没有 offset 字段**（底层 `ListFilter` 有），
所以前端无法分页。

#### 已完成（2026-09-27）

选了「**先让截断可见，再让它可恢复**」两条都做：静默截断是 bug，无分页是能力缺口。

**后端**
- `BoardSnapshot` 新增 `truncated: { total, showing, limit, offset, truncated }`。
  `truncated` 只在首页（`offset === 0`）为真——翻页时调用方是「主动在翻」，
  不该被报成「看板不完整」。
- `buildBoard` 接 `limit` / `offset`；默认页大小提成 `BOARD_PAGE_SIZE = 500`。
- `board.get` Op 与 `/api/board` 都接受并**钳制** `limit` / `offset`。

  一个 `?limit=1e9` 就是把整库塞进一个 HTTP 响应。

**Web**
- 泳道下方一条提示条（「共 N 张卡，当前只列出前 M 张」+「显示更多」）。
- 「显示更多」**合并**而不是整页重建：直接改 `limit` 重拉会把用户已经看到的 500 张
  全部重建（滚动位置、展开的卡片、拖拽状态全丢）。泳道是按优先级全局排序后切页的，
  同一张卡不会跨页出现，所以按 id 去重合并就够。
- `mergeBoardPages` 里**必须重算** `truncated`：新一页的 `offset > 0` 所以它的
  `truncated` 恒为 false，直接透传会让提示条在翻页后消失，而后面可能还有页。
- 三条文案进 zh / en 词典（走 `t()`，界面无中文字面量）。

**回归链**（改 Web 必须走完）：`bun run web:build` → `web:typecheck` → `verify:web:ui`
（真浏览器）全通过。

**守卫** `test/board-truncation.test.ts`（11 条）
- 行为：造 501+ 张卡断言 `truncated` 为真、`showing`/`total` 正确；
  翻页 `offset` 生效且**两页不重叠**。
- 上限保护：`limit=-1` 不变成「不限长」、`limit=1e9` 被钳到 2000、非数字退回默认。
- **接线守卫**：Web 侧必须真的用了 `truncated`（否则就是「后端报出来了但界面还是不说」，
  等于没修）；`/api/board` 必须有上界而不是直接 `Number()` 透传。
- 逐条回退验证 5/5。其中「「显示更多」改成整页重建」这条**第一版没抓住**——
  因为守卫只判 `mergeBoardPages` 出现过，而 import 里就有这个名字。
  改成判**实际的状态更新那一行**才抓住。

### 15. 每条只读命令都要抢写锁

`src/commands/context.ts` 的 `openLocalCtx` 在**任何**命令（包括 `task list`、`board`、
`context`）开头无条件调 `reapZombies`，而它内部是 `withTx` → `BEGIN IMMEDIATE`。
即使一个僵尸都没有，也要拿一次写锁。多 agent 并发读会全部串行化在写锁上。
`busy_timeout=5000` 会把压力转成退出码 4 而不是报错，所以表现是"变慢"不是"坏掉"，
但规模上去后读性能会被写锁拖住。先跑一条只读 `SELECT` 判断有没有僵尸再进事务就能解决。

**已随 #0 一并修掉主因**：`reapZombies` 现在先做一次只读探测，确认真有僵尸才开写事务
（事务内用同一判据重查，所以只是优化、不引入竞态）。剩下的开销是 `touchSession`
的节流写（≤ 1 次/分钟/会话），量级已经可以忽略。

仍然值得考虑的：`task list` / `board` 这类纯读命令其实**根本不需要**跑回收，
但把它们与身份相关命令区分开需要额外一层「这次调用是不是只读」的判定，
当前靠节流已把成本压到可接受，先不动。

### 16. token / project 管理完全绕开了事件流

ADR-1 说「每一次状态变化都必须在同一事务里完成改投影 + 写事件」。但：

- `ops.ts` 的 `project.rename` / `project.rotate_key`
- `tokens.ts` 的 `issueToken` / `revokeToken` / `updateTokenProjects` / `updateTokenMeta`

全是裸 `db.query`，**没有事务、没有事件**。安全相关的状态变更没有审计链
（`tokens` 表有 `created_by` / `revoked_at` 列，但那是就地字段，`rebuild` 恢复不了）。
另外 `project.create` 借 `board_exported` 事件类型来记 `action: "project_created"`，
是一种事件类型复用，读事件的人会困惑。

### 17. MCP 面覆盖不全

Op 有 40+ 个，MCP 只暴露 20 个。缺 `task.cancel` / `task.reopen` / `task.release` /
`task.remove` / 全部 `task.dep.*` / `plan.list|history|at|attach` / `events.*` /
`rebuild.check` / `project.*`。

只靠 MCP 的 agent **无法取消任务、无法删除任务、无法管理依赖**（只能靠 `session_end`
间接释放）。ADR-6 / ADR-10 宣称的"三端一致"在能力覆盖上并不成立。
要么补齐，要么在 MCP 工具描述里诚实说明"这些操作请用 CLI"。

**已修**：全局提取去掉 query 分支；判据改成「整个 `http.ts` 里没有从 query 取凭据」
（不再按函数体切）；新增行为层用例（四个端点带 `?key=` 全部 401）+ 一条反向用例
（header 仍然能进 `/api/board`，防「把门焊死」这种修法）。分享链接不受影响：
`?key=` 的合法用途只在**根路径**的 SPA（读完就 `history.replaceState`），之后的 API 调用都走 header。
契约 §4.1 的措辞也从「SSE 不接受」改成「任何端点都不接受」。

### R2. 远程模式的 `sessions.cwd` 记的仍然是 **server** 的目录

04802cc 把 `ops.ts` 里那句 `cwd: ctx.db ? process.cwd() : process.cwd()` 换成了
`op.params.cwd || ctx.cwd || undefined`，注释写着「没带就存 null 而不是猜一个——
猜出来的值比没有更坏」。但**下一层又猜回来了**：`createSession` 里
`input.cwd ?? process.cwd()`。而 `X-Kanban-Cwd` 这条通道**没有任何客户端发送**
（`RemoteBackend` 只发 `X-Kanban-Key` / `X-Kanban-Session`，MCP 的 `kanban_session_start`
也不带），而契约 §4.1 却把它写成正式通道。

探针实测（server 跑在临时目录，客户端不带该头）：

```
server 进程目录 = C:\...\Temp\ak-probe
session s-sg8r2r cwd = "C:\\Users\\...\\Temp\\ak-probe"     ← 库里记的是 server 的目录
```

连响应 JSON 里回显的也是它。一条比空值更坏的信息：**它看起来像真的**。

**已修**：两头都补上。`createSession` 不再退回 `process.cwd()`，缺省存**空串**
（列是 `NOT NULL`，空串是这里唯一诚实的“未知”）；`RemoteBackend` 新增 `cwd` 选项
（缺省 `process.cwd()`）并在每个请求上带 `X-Kanban-Cwd`，`withSession` 重建时也带着。
守卫：原来的那条只查了 `ops.ts` 与 `http.ts`，正好漏掉真正写库的 `sessions.ts`——
补了「`createSession` 不得出现 `input.cwd ?? process.cwd()`」+「远程 backend 必须发头」
+ 一条行为用例（带客户端目录 → 记客户端目录；不带 → 空串，且**绝不是** `process.cwd()`）。

### R3. `clampInt` 让 `?limit=`（空串）从「默认 500」变成「只给 1 张卡」

dbd8bf4 把 `/api/board` 的分页钳制从自写一套 `Number`/`Math.min` 换成共用的 `clampInt`
（这个复用是对的：上界与默认值当时有两个真相）。但旧代码里
`Number.isFinite(raw) && raw > 0 ? … : 500` 会把**非正数**当「没给」，而 `clampInt` 只处理
`undefined`/`null`/`NaN`：`Number("")` 是 **0 而不是 NaN**，于是 `?limit=` 被
`Math.max(0, 1)` 抬成 1，`?limit=0`、`?limit=-1` 同理。探针实测（3 张卡的库）：

```
?limit=     -> 200  showing=1  truncated=true
?limit=0    -> 200  showing=1  truncated=true
?limit=-1   -> 200  showing=1  truncated=true
```

「只给 1 张」不是任何调用方的意思，而它**看起来像个合法请求**：响应里
`truncated.truncated` 变 true，界面于是显示「共 3 张，当前只列出前 1 张」，像分页坏了。

**已修**：`clampInt` 现在把「不像是想清楚的输入」一律当没给——空串/纯空白、非正数
（仅当 `min > 0`；`offset` 的下界是 0，0 正是它的默认值，必须放行）。两条钉住旧行为的
用例相应改成钉住新契约；`task.list` 那条（原来断言「-1 钳到 1」）改成造 250 张卡、
断言 200，这样它能同时区分「退回默认」与「不限长」。

### R4. token 事件的 `token_ref` 仍能把明文密钥写进事件流

零迁移意味着老库的 `tokens.id` 里就是明文密钥。dbd8bf4 的 `describeTokenRef` 堵住了
`tokenToJson`（实测：老行在 admin 列表里显示 `k_aaaa…aaaa`，仍能鉴权 ✓），
但 `token_revoked` / `token_updated` 拿的是**调用方传入的 id**，
CLI 上手敲 `admin token revoke k_xxx` 完全合法——密钥就顺着 `token_ref` 进了事件表，
而事件表会被 `export`、备份、`rebuild` 重放。

**已修**：四个 `token_*` 事件的 `token_ref` 都过 `describeTokenRef`；渲染侧
（`events.describeEvent` / `context.describeEventBrief`）同样过一遍，兜住「旧库里已经
写进去的明文」。依赖方向 `events → tokens` 是单向的（`tokens.ts` 只 import
errors/tx/projects/rows/types，那几个都不 import events），不成环。

### 教训（与本文件前面三处事故同源）

**「已修」是一个需要证据的断言，而注释是最弱的证据。** 这四条里有三条的根因是同一句话：
上一轮把「我打算修」写成了「我已经修」，而守卫恰好只覆盖了它能看见的那一层——
`handleSse` 函数体、`ops.ts` 与 `http.ts`、已经掩过码的 `tokenToJson`。
探针是唯一把它们叫醒的东西：**每条都是先起真 server 打真请求**，不是读代码推的。

| 症状 | 藏在哪一层 |
| --- | --- |
| `?key=` 只删了 SSE | 函数体 vs 整个 `http.ts` |
| `sessions.cwd` 记成 server 目录 | 传参那一层 vs 真正写库的 `createSession` |
| 事件流里的明文 token | 列表出口 vs 事件写入点 |

守卫的判据要落在**不变量所在的那一层**，而不是改动最容易改的那一层。
