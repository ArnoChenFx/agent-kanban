# CLI 文案英文化实施笔记（2026-09-27）

> 目标：`agent-kanban` 面向用户的输出一律英文，中文只留在注释、用户数据与文档叙述里。
> 方案见 `docs/plan/006-CLI文案英文化.md`（术语表与文风规则），这篇记实施过程与踩到的坑。
> 最终规模：**73 个文件 / +4396 −1267**，19 个命令文件 + core + MCP + Web 词典 + 测试 + 文档。

## 一、怎么做的：5 个并行 agent + 1 个定调

跨 19 个文件、约 650 处文案，单会话串行改必然耗尽上下文，所以拆成文件互不重叠的 5 组并行：

| 组 | 文件 | 产出 |
| --- | --- | --- |
| A | `commands/{task,plan,admin}.ts` | 176 处 |
| B | `commands/{recovery,context,board,handoff,session,project}.ts` | 189 处 |
| C | `commands/{config,backup,init,rebuild,args,protocol}.ts` | 178 处 |
| D | `core/**` + `server/http.ts` | 错误文案 + 61 个 reason slug |
| E | `mcp/{tools,server}.ts` | 工具描述与报错 |

**先做的是文风定调，不是并行**：`src/cli.ts` 的 `HELP`、`commands/output.ts` 的四个错误模板、
`core/format.ts` 的状态标签与相对时间，我先亲手改完当参照样例，术语表也只此一份。
子代理回报了 20+ 条措辞疑问，我逐条裁定后写回 006——**没裁定的代价是同一句话两种拼法**。

## 二、必须先写进指令的一条：本机 `Get-Content` 会毁掉中文

并行改文案时最大的风险不是译错，是**把乱码当原文**。本机 PowerShell 5.1 的
`Get-Content` 默认按 GBK 解码，把仓库里正确的 UTF-8 中文显示成 `瑙ｆ瀽绉熺害鏃堕暱`
（`解析租约时长`）。照着这个翻译 = 把乱码写进文件，而且**语法合法、测试照过**。

同一条指令里还有第二个坑：`rg PATTERN` 不带路径在非交互环境下会去**读 stdin**，
于是永久挂住——有个 agent 就这么卡了 4 分钟，只能中断再恢复。
教训已写进 `AGENTS.md`，因为它对**任何人**（包括不用并行的未来会话）都成立。

## 三、方案中途被现实推翻两次

### 1. "`next_actions` 是纯命令" —— 错

方案里写"`next_actions` 是给 agent 的数据，不翻译"。实际它带中文前缀：
`认领：agent-kanban task claim T-0001`。不译则终端仍然中英混排。

**为什么译了不会污染中文界面**（这是能放心译的前提）：后端同时给
`next_action_items`（`{code, args}` 结构化数组），Web 走
`web/src/lib/next-actions.ts` 按 `code` 查自己的词典渲染，**根本不读 `next_actions` 文本**；
只有降级路径才回退到文本。`code` 与 `args` 键名一个字没动。

### 2. "交接正文是数据" —— 机器生成的那部分不是

崩溃后自动合成的交接（`synthesizeCrashHandoff`）也是数据吗？问过用户，定为**英文化**：
它不是人手写的，是机器生成的，而 `agent-kanban resume` 遇崩溃时正好把它打给 agent 看。
用户手写的交接仍然原样回显（可能是中文，那是数据）。

## 四、顺手抓到的四个真 bug（都不是文案问题）

### 1. `context` 输出里漏 `undefined`

```
Last: handoff written (undefined)
```

`describeEventBrief` 读 `d.kind`，而 `handoff_created` 事件的 payload 是**嵌套**的
`{ handoff: { kind } }`（因为 rebuild 靠它重建 handoffs 表）。字段取错层级。
中文版本同样有这个 bug（`写了交接（undefined）`），是既有缺陷被英文输出照搬。

**为什么一直没被发现**：仓库只给 `task show` 钉了「输出里不许出现 undefined」
（`test/cli-output.test.ts`），`context` 不在覆盖范围内。已补 `context` 的守卫。

同一个断言还暴露了一个陷阱：断言不能笼统地查整段。中文正文里的"无心跳"英文化后
变成 `without a heartbeat`，`not.toContain("heartbeat")` 会**误伤**。所以把断言收窄到
它真正守护的段落：`summary.split("Last actions:")[1]`。这比原来的写法更严。

### 2. `verify:web:ui` 门禁在我动手前就是坏的

13 项失败，根因是脚本用 `KANBAN_SERVER` 远程模式跑 CLI，却依赖 `session start`
写默认会话文件——而 `session start` **只在本地模式写**（`ctx.backend.mode === "local"`）。
于是 `task claim` / `plan save` / `handoff` 全报 `missing session id`，
后面十几个断言（检查项计数、交接角标、计划页签、进度条内缩）连锁失败。

门禁坏了就得修，否则以后每次都只能靠"反正它一直红"来忽略。改成显式取回
`session_id` 并用 `KANBAN_SESSION` 传下去 → **64 项全绿**。

### 3. `verify:deploy` 与 `docker-compose.yml` 脱节

`3387e19`（改名那轮）把 compose 服务名改成了 `agent-kanban`，但门禁还在断言 `kanban`。
**和本次会话一开始修的 release.yml 是同一类漏改**：改名时只改了主文件，忘了改断言它的脚本。

### 4. 陈旧的 asset manifest 让所有 CLI 命令起不来

`src/server/assets.generated.ts` 引用 `index-CAHjF4FO.js`，而 `web/dist` 里已经是
`index-B8EKyMeR.js` → 每条 CLI 命令都抛 `Cannot find module`。`gen:assets` 可解。

顺带记住这条规则：**仓库提交的是空表占位 manifest**，因为 `http.ts` 静态 import 它，
干净 checkout（CI、新机器）还没有 `web/dist`。跑 `web:build` 会把它覆盖成真实清单——
本地跑完构建**必须 `git checkout HEAD -- src/server/assets.generated.ts` 恢复占位**，
否则会把带本机 hash 的生成物提交进去（`verify:deploy` 会当场报「manifest 是空表占位」）。

## 五、Web 侧：让中文界面继续说中文

CLI 英文化后 `KanbanError.message` 变英文，而看板是双语的。做法：

```
details.reason（稳定 slug）→ 词典 error.<reason> → 命中则中文，未命中回退英文原文
```

- 61 个 slug，`zh` 写中文，`en` **一律留空串**。
- **en 留空是刻意的**：后端那句已经是英文，词典里再抄一份就多一处会漂移的第二真相
  （`next-actions.ts` 的注释里写过这个教训：前端给后端的中文串配英文译法，迟早会显示过时旧句）。
- 占位符必须用 `details` 里真实存在的键名（`{task_id}` 不是 `{taskId}`），否则界面渲染出字面量。
  守卫在 `test/web-i18n.test.ts`——它当场抓到了我第一版正则的缺陷
  （`details` 常写在单行对象字面量里，行首锚定抓不到键），**也抓到了词典本身**。

## 七、留给下一个人的三条

1. **别用 `Get-Content` 看中文源码**（GBK 乱码），别跑不带路径的 `rg`（读 stdin 永久挂住）。
2. **改 CLI 文案后跑一遍真实输出**再改断言：直译会破列宽。已踩两例——
   `relativeTime` 从"刚刚"变 `"just now"` 后 8 格的时间列被占满，
   拼出 `just now created task (p2)`（已加宽到 10）；
   中文宽度对齐的表格（`session list` / `config show` / `project list`）标签长度全变。
3. **改名时把所有引用它的地方找出来**，别只改你正在看的那一处。同一轮 `3387e19` 里
   漏了三处：`Collect assets` 的 `find -name`（→ 发布直接失败）、
   `verify:deploy` 的服务名断言、compose 的 volume 引用。
