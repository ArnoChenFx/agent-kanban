# M2 崩溃恢复实施笔记（2026-02-19）

> 主题：把"agent 崩了怎么接上"从概念变成代码。
> 结果：新增 4 个 core 模块、4 个 Op、4 个 CLI 命令、17 个测试；测试总数 60 → 77。

## 一、做了什么

| 模块 | 职责 |
| --- | --- |
| `src/core/handoff.ts` | 交接的写入/查询/消费，以及**崩溃自动合成** |
| `src/core/context.ts` | 恢复现场组装（`buildContext`）与接管（`resumeTask`） |
| `src/core/doctor.ts` | 一致性自检与修复（租约/阻塞/进度/投影） |
| `src/core/sessions.ts` | 僵尸回收时在同一事务内**自动生成 crash 交接** |

对应 CLI：`kanban context` / `kanban resume` / `kanban handoff` / `kanban doctor`。
对应 Op：`context.get` / `handoff.create` / `resume.task` / `doctor.check`（本地远程一致）。

## 二、过程中发现并修掉的真实缺陷

这一节的每一条都是**先有 bug、后有测试**的，写下来是为了以后别再踩。

### 1. `listTasks` 的 `sessionId` 过滤是哑的

```ts
if (filter.mine && filter.sessionId) {   // ← 必须同时给 mine
  where.push("assignee_session_id = ?");
}
```

`buildContext` 写的是 `listTasks(scope, { status: "doing", sessionId })`，**忘了 `mine: true`**，
于是过滤被跳过，`my_tasks` 把**所有**会话的卡都算成"你正在做的"。

一个 agent 打开 `kanban context` 看到自己名下挂着别人的 5 张卡——这直接摧毁了"上下文恢复"的价值。

**为什么没被现有测试发现**：M1 的测试只验证 list 的 status/ready/label 过滤，没验证 sessionId 过滤。
**修法**：代码里加了警示注释，`buildContext` 显式传 `mine: true`，并补测试锁住行为。

> 教训：`filter` 里两个字段互为前提时，要么合成一个字段，要么让其中一个独立生效。
> 哑条件（传了也不生效）比报错更危险。

### 2. 交接写得越认真，越接不了手

`resume` 接管走 `claimTask`，而 `claimTask` 只在**租约过期**时允许抢占。
但典型场景是：A 干完写了交接（进程还活着，租约还剩 15 分钟）→ B 来接管 → **CONFLICT**。

这是语义矛盾：交接就是"我把这张卡交出去了"的明确信号，租约应当让位。

**修法**：`claimTask` 的前置校验与条件 UPDATE 都加入
"存在持有者未消费的 `voluntary` 交接"这一分支（`HANDOVER_PREDICATE`）。
只认 `voluntary`：crash 交接是系统在自己回收时合成的，那时任务已无租约，不该参与抢占判断。

### 3. `resume` 拿到了信息量最少的交接

原实现取 `handoffs[handoffs.length - 1]`（最后一条）。
时间顺序上，崩溃合成的 crash 交接总是**晚于** agent 自己写的 voluntary 交接，
于是 agent 明明认真写了交接，接手方看到的却是系统自动合成的粗糙版本
（"进度 60%，持有者失联……"）。

**修法**：`[...handoffs].reverse().find(h => h.kind === "voluntary") ?? 最后一条`。
原则：**人写的优先于机器合成的**。

### 4. crash 交接的 blockers 是空的

原实现只在 `task.blockReason` 存在时填 blockers。而崩溃回收后任务已回到 `todo`，
`blockReason` 自然为空——于是"为什么会到我手上"这个最该被看到的信息被丢了。

**修法**：无条件写入 `原持有者 X 失联（30 分钟无心跳，进程可能已崩溃）`。

### 5. `kanban init --force` 根本不删库

`--force` 之前只是**跳过幂等分支**，然后 `migrate` —— 而 migrate 不清表。
结果是"名为重建、实则旧数据全留"，任务号一路涨到 T-0004。

**修法**：`--force` 时显式删除 `kanban.db` / `-wal` / `-shm` 三个文件。
`-wal` / `-shm` 也要删，否则残留 WAL 可能让删除后的库"复活"。

### 6. crash 交接的时间线里混进了自己的回收事件

`reapZombies` 在合成交接时，`task_reclaimed` 事件已经写入了同批事件，
于是交接的"最后动作"会包含"被回收"——对接手方是废话（他当然知道是被回收后才拿到的）。
**修法**：合成时排除 `task_reclaimed` 本身。

### 7. `kanban handoff --task T-0007` 不认 `--task`

只读位置参数，导致 `--task` 形式的调用直接报"缺少参数 <任务号>"。
**修法**：`--task` 优先，位置参数作为宽容回退。

### 8. `consumed_count` 混进了 `next_actions`

`next_actions` 是**写给 agent 的建议**；把"已标记 N 条交接为已读"这种系统反馈塞进去，
agent 会把一条反馈当成待办去执行。**修法**：改为独立的 `consumed_count` 字段。

## 三、测试策略

`test/recovery.test.ts`，17 个用例，**全部使用可注入逻辑时钟**（`TestDb.advance`），零真实 sleep。

分组：

1. `handoff —— 主动交接`：写入/查询/消费/project 隔离/不自己提醒自己
2. `崩溃自动合成`：回收时自动合成、含进度与未完成项、重复回收不刷屏
3. `context —— 恢复现场`：组装、只读不消费、失联标 stale
4. `resume —— 接管`：进度与 checklist 保留、租约有效时被拒、force、已完成卡拒绝、崩溃识别
5. `doctor —— 一致性自检`：健康库、发现并修复失联租约、进度/checklist 不一致、心跳刷新

写测试时踩的坑：

- **`ProgressInput` 的字段是 `pct` 不是 `progress`**。写成 `progress: 40` 会被忽略，
  然后走"按 checklist 比例重算"分支，得到 33%。差点误判成 bug。
- **`reapZombies(db, opts)` 自己开事务**，不要再包一层 `withTx`。
  包了之后 `ctx` 被当成 `db` 传进去，报错信息极具误导性（`db.exec is not a function`）。

## 四、端到端验证

`scripts/verify-recovery.ts`：起真实 CLI 子进程，完整走一遍
干活 → 写交接 → 改库模拟崩溃（心跳推到 30 分钟前）→ 新会话 `context` → `resume` → 校验 → `doctor`。

真实进程验证能抓到单测抓不到的东西：CLI 参数解析、跨进程 session 传递、终端渲染。

```bash
# agent 收工

  --summary "完成 WAL 事务层" \
  --next "实现崩溃自动合成" \
  --blockers "依赖还没装" \
  --open "WAL 文件要不要纳入 git？"

# 运维

```
