# Release 资产重复上传导致发布失败（2026-09-26）

> v0.1.1 发布在最后一步失败：`Error: Not Found - .../rest/releases/assets#update-a-release-asset`。
> 根因是 `files:` 里两个 glob 重叠，导致 4 个 `.sha256` 各被并发上传两次。

## 一、故障现象

`softprops/action-gh-release@v2` 这一步挂了，但**大部分资产其实已经传完**：

```
⬆️ Uploading agent-kanban-windows-x64.exe.sha256...
⬆️ Uploading agent-kanban-linux-x64.sha256...
⬆️ Uploading agent-kanban-darwin-x64.sha256...
⬆️ Uploading agent-kanban-darwin-arm64.sha256...
⬆️ Uploading agent-kanban-windows-x64.exe.sha256...     ← 同名，第二次
⬆️ Uploading agent-kanban-linux-x64.sha256...          ← 同名，第二次
⬆️ Uploading agent-kanban-darwin-x64.sha256...         ← 同名，第二次
⬆️ Uploading agent-kanban-darwin-arm64.sha256...       ← 同名，第二次
✅ Uploaded release-notes.md
✅ Uploaded agent-kanban-windows-x64.exe.sha256
error updating release asset metadata for agent-kanban-darwin-x64.sha256: HttpError: Not Found ...
  Matching asset is present after refresh; continuing...
error updating release asset metadata for agent-kanban-windows-x64.exe.sha256: HttpError: Not Found ...
  Matching asset is present after refresh; continuing...
error updating release asset metadata for agent-kanban-linux-x64.sha256: HttpError: Not Found ...
  Matching asset is present after refresh; continuing...
Error: Not Found - .../update-a-release-asset
```

**指纹很明确**：4 个二进制 + `release-notes.md`（8 个唯一文件）全部 `✅ Uploaded`，
只有 `.sha256` 报错，而 `.sha256` 恰好就是被传了两遍的那批。

## 二、根因：glob 的 `*` 会匹配点号

原来的 `files:`（`.github/workflows/release.yml`）：

```yaml
files: |
  release-assets/kanban-*
  release-assets/*.sha256      # ← 以为是"补充校验和"，实际是"再传一遍"
  release-notes.md
```

glob 语法里 `*` 匹配**任意数量的、除了 `/` 以外的字符**，点号只是普通字符。
所以 `release-assets/kanban-*` 已经把 4 个 `kanban-*.sha256` 全收进来了，
第二行不是"补充"，而是让每个校验和文件在待传列表里出现两次。

action 侧的行为（`src/util.ts` + `src/main.ts`，v2 分支）：

```ts
// util.ts: paths() —— 每个模式各自 glob，然后直接 concat，不去重
return acc.concat(resolved);

// main.ts: 默认并发上传
results = await Promise.all(files.map(uploadFile));
```

于是同名资产的两次 POST **并发**打向 GitHub。这是竞态：GitHub 拒掉其中一个
（404 或 422 already_exists），action 只能靠"重新列举资产、找到同名的那一个"来兜底
（`findReleaseAsset`，3 次、每次间隔 1s）。兜底成功就打 warn 继续，
兜不中就走到 `throw error`，整个 step 失败——也就是最后那行裸的
`Error: Not Found - .../update-a-release-asset`。

### 两个容易误判的地方

1. **报错信息里的 `update-a-release-asset` 是误导的。** 出错的是上传 POST，不是 PATCH。
   action 判断"是不是资产相关的 404"用的是 URL 匹配，而上传地址本身就长这样：
   `https://uploads.github.com/repos/<o>/<r>/releases/<id>/assets?name=...`
   → 命中了它的 `/releases/\d+/assets` 分支，于是被当成"更新资产元数据失败"来兜底。
   排查时别顺着 `updateReleaseAsset` 找，找不到根因。

2. **同一个配置 v0.1.0 发布成功了。** 竞态就是时好时坏：
   `git diff v0.1.0 HEAD -- .github/workflows/release.yml` 显示这期间**只改了
   release notes 里的 docker run 那一行**，`files:` 一个字没动。
   所以"上次能发成功"不能证明配置没问题，只能证明这次运气好。

## 三、修法

### 1. 只留一个 glob（`.github/workflows/release.yml`）

```yaml
files: |
  release-assets/kanban-*      # 二进制 + 校验和都在这里
  release-notes.md
# 重跑失败发布是常规修复手段；上次失败总会留下资产（action 是全部传完才 publish），
# 能覆盖才能让重跑收敛而不是死在 already_exists
overwrite_files: true
```

### 2. 顺带把校验和数量也卡住

`Collect assets` 步骤原来只数二进制（`grep -vc '\.sha256$'`）。校验和跟二进制在同一个
artifact 里，一起丢；少了校验和的下载链接和少了二进制一样是坏的发布，所以单独数一次：

```bash
SUMS=$(ls -1 release-assets/*.sha256 2>/dev/null | wc -l || true)
SUMS="${SUMS:-0}"
if [ "$SUMS" -ne "$EXPECTED" ]; then
  echo "::error::expected ${EXPECTED} .sha256 files, found ${SUMS}:"
  exit 1
fi
```

### 3. 把不变量写进 CI（`scripts/verify-workflows.ts`）

静态检查挡不住"下次又手滑加一行"，所以反过来做：**用矩阵里的 `asset:` 名去展开
`files:` 的每个模式，要求每个资产（含 `.sha256`）恰好被一个模式命中**。

```ts
const expectedAssets = assetNames.flatMap((a) => [`release-assets/${a}`, `release-assets/${a}.sha256`]);
const badMatches = expectedAssets.filter(
  (name) => filePatterns.filter((p) => globRe(p).test(name)).length !== 1,
);
```

注意模式带目录前缀，比对时文件名也要带 `release-assets/`，否则命中数全是 0。
回归验证（把重叠那行加回去）：

```
✗ 每个平台资产（含 .sha256）恰好被一个 glob 命中
  命中数不为 1：release-assets/agent-kanban-linux-x64.sha256, ... 共 4 个
```

正好点名那 4 个文件，和 CI 日志里的报错集合一致。

## 四、结论 / 教训

- **glob 的 `*` 匹配点号**。写 `foo-*` 时它已经包含 `foo-*.sha256`、`foo-*.txt`；
  想只要一层扩展名就写 `foo-*.exe` 这类精确后缀，别指望"再加一行更窄的 pattern"来收窄。
- **一个 `files:` 列表里不要出现互相覆盖的模式。** action 不去重 + 并发上传 =
  同名竞态，失败还是概率性的，最难查。
- **CI 报错信息要怀疑，但要核对**。`update-a-release-asset` 这个 endpoint 名字来自
  action 自己的启发式判断，不是真的调用了那个 API。
- **"上次发布成功"不是配置正确的证据**，尤其在有并发、有网络、有 GitHub 侧最终一致性的地方。
