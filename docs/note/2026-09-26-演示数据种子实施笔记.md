# 2026-09-26 演示数据种子脚本实施笔记

对应计划：`docs/plan/005-演示数据种子脚本.md`
产物：`scripts/seed-demo.ts` + `bun run seed:demo`

## 一、为什么不用 spawn CLI

第一版想过沿用 `snapshot-web.ts` 的做法（每步 `spawn bun run src/cli.ts ...`），
写到一半发现两个死结：

- **时间戳全是 now**。CLI 不接受时间注入，十八张卡会共享同一个 `created_at`，
  界面上全是"刚刚"。看板截图最吃的就是"这件事是上周做的"。
- **慢**。40 多次 spawn，每次 ~200ms，冷启动就 8 秒。

改成直接 import core：`createTask(ctx, input)` / `claimTask(ctx, id, actor)` / …
`runTaskCommand` 内部照样是 `withTx` + 完整状态机守卫，非法流转照样抛错，
只是 `Actor.now` 可以随便填。`snapshot-web.ts` 里那种"用 CLI 一步步造数"的写法
在需要精确时间轴时就完全不够用了。

## 二、踩到的坑

### 1. `Cannot access 'GRACE_MS' before initialization`

`const` 有 TDZ。我把 `GRACE_MIN` 声明在"时间轴"那一节，却在建库那节就用它写 meta，
Bun 报的是 `INTERNAL`（被 `toKanbanError` 包了一层），堆栈里才看到真正原因。
**教训：脚本报错被 core 的错误包装盖住时，先看 `details.stack`，别急着改 core。**

### 2. 跑一次 `doctor`，看板自己变了

第一版灌完数据，`doctor` 说"1/5 活跃"——我明明建了 5 个会话、其中 4 个心跳在
一小时之内。查事件才发现：**`doctor` 开头调了僵尸回收**，把 4 个会话判成 crashed，
把它们持有的卡退回 todo，还给一张卡合成了**中文**崩溃交接。

这不是 bug，是 core 的设计（心跳超时就该回收），但对"演示数据"是致命的：
放半小时再看一次，看板已经是另一个样子了。见笔记第三节的修法。

### 3. `updated_at` 被更早时间戳的写入拉回去

`doctor` 提示 `T-0007 超过 4 小时没有更新进度`，可它的最后一次 progress 是 2 小时前。
原因是我把"保存计划"那段代码放在"剧情"之后执行，而计划的时间戳是 6 天前——
`savePlan` → `attachPlan` 会 `UPDATE tasks SET updated_at = <计划的时间>`，
把卡片的时间戳**倒着**改回 6 天前。

修法不是给数据打补丁，而是**按真实时间顺序排列代码**：先存计划，再干活。
core 的所有写函数都会把 `updated_at` 设成当前逻辑时钟，所以"最后写的那一步"
必须是时间上最晚的那一步。

### 4. 进行中的卡显示"租约已过期"

租约 = 认领时间 + 15 分钟。剧情里的认领发生在 1~2 天前，界面直接显示过期。
真实运行时靠 agent 每隔几分钟的 `progress` / `note` 隐式续租，脚本里没有这些调用，
所以最后对每张 doing 的卡显式 `renewLease` 一次。续租按设计不写事件，
所以 `rebuild` 的结果不受影响（`lease_expires_at` 本来就不参与比较）。

### 5. core 生成的 checklist 备注是中文

`updateProgress` 勾选后自动追加 `task_note`：`"检查项更新（2/4 完成）"`，
Web 时间线直接渲染 `data.text`（`web/src/lib/status.ts` 的 `describeEvent`
对 `task_note` 是 `String(data.text)` 原样输出，不查词典）。
脚本最后跑一条 `UPDATE events SET data = replace(replace(data, ...))` 换成英文。
只改事件里的展示文本，投影一个字段没动，所以 `rebuild` 重放结果不变——
**判断依据是：note 的 text 不参与任何投影计算**。

两个切分点踩了一次：原文是 `"检查项更新（2/4 完成）"`，第一段换掉 `检查项更新（`、
第二段如果只换 `完成）`，就会拼出 `"(2/4  done)"` 的双空格（`（` 是全角、
自带一个视觉空格）。第二段要连前导空格一起换：`" 完成）"` → `" done)"`。

另外在脚本末尾加了 **CJK 自检**：扫事件 `data`、卡标题/描述/阻塞理由、交接、计划正文，
出现任何中文就 `die`。目的是让"core 以后又新增了硬编码中文的自动文案"这种事
在灌数据时就炸，而不是等到截图拍完才发现看板里有一行中文。

### 6. `doctor` 的 progress / checklist 一致性告警

`|checklist 完成比例 - progress| > 10%` 就告警。剧本里随手写的
"进度 40%、checklist 1/4" 会被判成不一致。改数据比关检查便宜：
`T-0007` 勾两项到 50%、`T-0009` 提到 50%。这条检查挺有用的，
它抓的正是"进度条和清单对不上"这种最容易被用户质疑的状态。

### 7. 建卡顺序必须让依赖在前面

`createTask` 的 `blockedBy` 需要真实任务号，而任务号是按创建顺序分配的。
`MCP package` 依赖 `isolation`，但我最初把 `MCP package` 写在前面，
跑起来直接 `taskNotFound`。现在每个 `add(...)` 的第 5 个参数就是依赖 key 列表，
key 会在调用时解析成当时的真实 id——但**顺序约束还在**，靠注释盯着。

## 三、两个刻意的"非默认"

### 失联宽限 30 分钟（core 默认 10）

不是拍脑袋：`reapZombies` 在每条命令开头跑，宽限 10 分钟意味着演示数据
只有 10 分钟的"保质期"。脚本 `--grace` 可调，写回 `meta.grace_ms`。
**最稳的做法还是截图前重跑一次** `--reset`。

### 会话分三种下场

真实看板里不会有"5 个会话都活跃"的场景，因为干完活的人会 `session end`。
脚本照做：`codex-tests` 走 `closeSession`（因此不出现在 `board` 的会话列表），
`gpt-nightly` 显式 crashed，其余三个心跳新鲜。
副作用是 `context` 的会话列表只有 4 条——这才是真实看板的样子。

## 四、顺带发现：rebuild 在 `review` 状态上报假漂移

`rebuild` 对种子数据报 2 处漂移，都是 `tasks.T-00xx 字段 assignee_session_id`。
去掉种子脚本、纯用 CLI 复现：

```bash
bun run src/cli.ts init --db /tmp/bug/kanban.db --project bugcheck
bun run src/cli.ts session start --agent t1 --harness pi
bun run src/cli.ts task add "probe"
bun run src/cli.ts task claim T-0001
bun run src/cli.ts task review T-0001
bun run src/cli.ts rebuild        # ✗ assignee_session_id 漂移
```

原因：`transition(..., "review")`（`src/core/tasks.ts`）只把 `progress` 提到 100，
**保留** `assignee_session_id`（评审者需要知道是谁交的）；而 `rebuild.ts` 的
`case "task_review"` 把 `assignee_session_id` 和 `lease_expires_at` 都置空。
两者对"待评审的卡归谁"的理解不一致。

**应该改 rebuild（保留 assignee），而不是改 transition**：`review → doing`（打回）
这条转移不设置持有者，如果 `review` 阶段就把 assignee 清了，
打回后的卡会变成"进行中但没人持有"的坏数据。

一行修法（本次未实施，等确认）：

```ts
case "task_review": {
  const t = get(p, event.taskId);
  if (!t) return;
  t.status = "review";
  // 保留 assignee：与 transition() 一致，评审者要知道是谁交的
  // lease_expires_at 照旧不参与比较（见文件头"不参与比较的字段"）
  t.updated_at = ts;
  return;
}
```

影响面：任何停在"待评审"的真实看板都会让 `rebuild` 报漂移，
`verify-rebuild.ts` 没覆盖到 review 状态所以 CI 是绿的。
