# 容器化 + 发布（2026-02-19）

> 用 `bun build --compile` 出跨平台自包含二进制，打 tag 时由 GitHub Actions 自动发布，
> 另提供多架构 Docker 镜像运行 server。

## 一、`bun build --compile` 的关键前提：内嵌文件

编译成单文件二进制后，**只有模块图里的东西会被打进去**。本项目踩到了两个：

### 1. `schema.sql` —— 编译期无感，运行期 ENOENT

原来的写法是运行时读路径：

```ts
const sql = readFileSync(join(import.meta.dir, "schema.sql"), "utf8")
```

`bun build --compile` 出来的产物里 `import.meta.dir` 指向一个临时虚拟根目录
（`B:\~BUN\root\`），那里没有 `schema.sql`，于是：

```
错误[INTERNAL]：ENOENT: no such file or directory, open 'B:\~BUN\root\schema.sql'
```

**编译完全成功，只有运行才炸。** 修法是 Bun 的 embedded files：

```ts
import SCHEMA_FILE from "./schema.sql" with { type: "file" }
// 编译后：SCHEMA_FILE 指向二进制内嵌的虚拟路径，readFileSync 读到内存副本
// 开发模式：指向真实文件，行为一致
```

配套补了 `src/types/assets.d.ts`（TS 不认识这个导入属性）。

### 2. `package.json` —— 同理

`--version` 要读版本号。`import.meta.dir` 在编译产物里同样不可靠，
所以也用 `with { type: "file" }` 引入。

> 顺带加了 `kanban --version` / `-V` 命令（之前没有，CI 和用户都用得上）。

**结论**：只要代码里有"运行时按路径读文件"的地方，编译成单二进制前都必须改成 embedded file。
这类问题编译期完全发现不了，**只能在目标平台上跑一次才算验证过**——
所以 workflow 里每个平台都有 smoke test，arm64 因为 x64 runner 跑不了，走 qemu。

## 二、CI 结构

| workflow | 触发 | 内容 |
| --- | --- | --- |
| `ci.yml` | push / PR | 三平台类型检查 + 单测；前端构建 + 二进制冒烟 + Docker 构建；5 套端到端验证 |
| `release.yml` | `v*.*.*` tag | 版本一致性校验 → 全量验证 → 5 平台二进制 → 多架构镜像 → GitHub Release |

### 版本号只能有一个来源

打 tag 时校验 `tag 去掉 v == package.json.version`，不一致直接失败。
否则会出现"这个二进制到底是哪版"查不到的情况——版本号一旦有第二个来源就必然漂移。

### 二进制矩阵

| target | runner | 冒烟方式 |
| --- | --- | --- |
| `bun-linux-x64` | ubuntu | 直接跑 |
| `bun-linux-arm64` | ubuntu | **qemu**（`docker run --platform linux/arm64`） |
| `bun-darwin-x64` | macos | 直接跑 |
| `bun-darwin-arm64` | macos | 直接跑（arm64 runner） |
| `bun-windows-x64` | windows | 直接跑 |

每个平台跑 `init` → `task add` → `task list`，验证 schema 内嵌与 SQLite 可用。

### Docker 镜像

- **多阶段**：`deps`（利用层缓存）→ `build`（前端 + 编译）→ `runtime`（alpine + 二进制 + dist）
- **架构**：`linux/amd64` + `linux/arm64`
- **推送**：GHCR（必）+ Docker Hub（secrets 存在时）
- **不用 bun 运行镜像**：二进制已内嵌 bun 运行时，运行镜像零依赖、攻击面小；
  代价是体积约 100MB，换来与下载产物**完全一致**的行为

## 三、Dockerfile 里踩的坑

### `/data` 的属主

```dockerfile
VOLUME ["/data"]
USER kanban
```

`VOLUME` 声明的目录在**运行时**由 Docker 创建，属主是 root。
非 root 用户第一次写库就会失败，而且报错很含糊（"初始化看板失败"之类），很难联想到权限。

修法是构建期显式准备：

```dockerfile
RUN mkdir -p /data && chown -R kanban:kanban /data /opt/kanban
```

### `dpkg --print-architecture` 做 target 推导

```dockerfile
RUN bun build --compile --target=bun-linux-$(dpkg --print-architecture | sed 's/amd64/x64/;s/arm64/arm64/') ...
```

buildx 为每个目标平台构建时，基础镜像也会拉对应架构，
所以这个命令在 arm64 构建阶段自然返回 `arm64` → `bun-linux-arm64`。不用写死。

## 四、容器使用

```bash
# 启动 server
docker run -d --name kanban \
  -p 7788:7788 \
  -v kanban-data:/data \
  ghcr.io/<owner>/agent-kanban:v0.1.0

# 首次启动会打印管理员 token
docker logs kanban

# 建 project + 签发 token
docker exec kanban agent-kanban admin project add my-app
docker exec kanban agent-kanban admin token create --project my-app --name ci
```

数据卷 `/data` 存 project、token、任务、交接——换机器时备份这个目录即可迁移。

环境变量：

| 变量 | 默认 | 说明 |
| --- | --- | --- |
| `KANBAN_PORT` | 7788 | 监听端口（优先于 CMD 里的 `--port`） |
| `KANBAN_HOST` | 127.0.0.1 | 监听地址；容器里设 `0.0.0.0` |
| `KANBAN_WEB_DIR` | 自动探测 | 前端静态资源目录 |

> `KANBAN_PORT` / `KANBAN_HOST` 是这次为容器化加的：原先只能靠改镜像 CMD 里的参数。

## 五、本地验证

```bash
# 编译单个平台
bun build --compile --target=bun-linux-x64 src/cli.ts --outfile dist/agent-kanban
./dist/agent-kanban --version
./dist/agent-kanban init && ./dist/agent-kanban task add "冒烟"

# Docker（本机无 docker 时用 CI 验证）
docker build -t agent-kanban:local .
docker run --rm -p 7788:7788 -v "$PWD/data:/data" agent-kanban:local
```
