# 2026-02-19 双模式架构改造笔记（D1-D7）

> 对应 ADR-9 ~ ADR-12，见 [001-总体设计 §2.1](../plan/001-总体设计.md)。
> 需求：支持「云端 server + 远程 CLI」与「本地目录」两种形态，且要按 project 组织。

## 一、改造范围

在 M1 基础上引入 project 层级与双后端，涉及：

- schema v1 → v2（`projects` 表、`project_key` 列、`project_counters` 表、tasks 表重建）
- core 全面引入 `Scope = {db, projectKey}`，所有读函数强制带 project 过滤
- 新增 Op 执行层（`core/ops.ts`），命令层从"直接调 core"改为"构造 Op 交给 Backend"
- 新增 `LocalBackend` / `RemoteBackend`、HTTP + SSE server、project/remote/serve 命令

## 二、关键设计决策

### 1. 任务号必须 per-project 唯一（不是全局）

最初想把 `tasks.id` 保持全局 UNIQUE。**这是错的**：

一个 server 管 10 个项目时，如果 ID 全局递增，agent 说"我改完了 T-0042"时，
听者无法判断是哪个项目的卡。任务号失去指代能力是 agent 场景的严重问题。

因此：
- `UNIQUE(project_key, id)` 而非 `UNIQUE(id)`
- 新增 `project_counters` 表做 per-project 分配
- **不用 `MAX(id)+1`**：删除任务后 MAX 回退 → 已删除的 ID 被重新分配，
  而历史事件/交接里仍引用它 → 审计链断裂。计数器保证 ID 永不复用。

代价：SQLite 不支持 `DROP CONSTRAINT`，v1→v2 迁移必须**重建 tasks 表**（见 `rebuildTasksTableForProject`）。

### 2. sessions 故意不带 project_key

会话是 agent **进程**的身份，一个会话完全可以跨项目工作（agent 在 A 项目干活、顺手看 B 项目）。
所以 `tasks.assignee_session_id` 不限定 project，**租约回收（reapZombies）也是全局的**：
进程死了，它在所有 project 下的卡都要回收。

推论：`reapZombies` 写 `task_reclaimed` 事件时，project_key 必须取**任务自己的** project，
否则远程客户端按 project 过滤 SSE 时会漏掉回收事件（已实现并测试）。

### 3. Op 是跨进程的稳定协议（ADR-10）

原本设想：命令层直接调 core，远程模式再写一套 HTTP 映射。
**那样必然出现"本地能用、远程报错"的漂移**（改了一处忘了另一处）。

改成：命令层只构造纯 JSON 的 `Op{kind, params}`，交给 Backend：

```
LocalBackend  ──────────────► executeOp()   同进程
RemoteBackend ──HTTP /api/op──► server ──► executeOp()
```

两端走同一个 switch，行为一致性变成**结构保证**而不是人工纪律。
`test/dual-mode.test.ts` 会逐字段比对两侧产出，一旦漂移立刻失败。

### 4. per-project key 认证（ADR-11）

- key 只在创建时明文显示一次，库里只存 SHA-256
- 错误信息**故意不区分"key 错"与"project 不存在"**：区分开等于给 key 猜解提供 oracle
- body 的 project 必须与 URL 的一致（防"用 A 的 key 操作 B"）
- 本地 project（`api_key_hash` 为空）不鉴权：已有文件系统权限，再要 key 只是摩擦

## 三、踩到的坑

### 坑 1：`{ create: false }` 之外又碰到 `PRAGMA` 的类型参数

`.query<T, [string]>(...).all()` 在 `PRAGMA table_info(...)` 上报
`Expected 1 arguments, but got 0`——PRAGMA 不接受参数，Params 类型应是 `[]`。

### 坑 2：迁移里 project_key 填成字面量 `'default'`

`rebuildTasksTableForProject` 重建表时把 project_key 填成 `'default'` 占位，
而后续回填语句是 `WHERE project_key IS NULL OR project_key = ''`——**匹配不到 `'default'`**，
于是 tasks 的 project_key 永远停在 `'default'`，与 events/plans 的真实 key 不一致。

连带后果：`project_counters` 按真实 key 查 MAX 查不到 → 计数器回填成 1
→ 下一张卡拿到已存在的 `T-0001`。

**修法**：把 defaultKey 的计算**提前到重建之前**，重建时直接填最终值。
教训：占位符 + 后续回填的组合，只有在占位符等于"会被回填命中的值"时才安全；
最稳的是一开始就用最终值。

### 坑 3：`code in ExitCode` 永远为 false

远程错误还原时写了 `(body.error.code in ExitCode ? ... : INTERNAL)`。
`ExitCode` 是 `{OK:0, USAGE:1, ...}`，它的 **key 是名字**，不是数字。
`3 in ExitCode` 检查的是"有没有名为 '3' 的键" → 永远 false
→ **所有远程错误都被降级成 INTERNAL(6)**。

agent 会因此认为"这是 bug，别重试"，而实际是冲突(3)／该换任务。

**修法**：改为 `VALID_CODES.includes(code)` 校验数字范围。
教训：JS 的 `in` 操作符对"值"无效，只对"键"有效——这类错误编译器不会报，
只能靠"断言错误码"的测试抓出来。

### 坑 4：`agent-kanban serve` 启动完立刻自杀

`main()` 末尾统一 `process.exit(code)`，而 `serve` 的 server 跑在**当前进程**的事件循环上。
于是 server 刚启动就被 exit 杀掉，外部连接全部 refused。

**修法**：`case "serve"` 直接 `return`，不走 process.exit。
教训：长驻进程不能走"执行完就退出"的统一收尾逻辑，需要显式豁免。

### 坑 5：server 端硬编码 `Date.now()` 破坏测试的固定时钟

测试用固定时钟（2026-01-01）创建任务，server 用真实时间（2026-02）
判定 `lease_expires_at <= now` → 认为租约已过期 → 允许接管 → 冲突测试失败。

**修法**：`ServeOptions` 加 `now?: () => number`（生产 `Date.now`，测试注入固定值）。
这不只是为了测试——**任何"多进程共享同一时间基准"的场景都需要它**。

### 坑 6：RemoteBackend 没在 URL 上带 project

server 从 URL query 读 `project` 做鉴权路由，而客户端只把它放在 body 里
→ 远程请求全部 401。

契约（§4.0/§4.1）里两边都提到了 project，但实现只做了一半。
**修法**：RemoteBackend 自动在 URL 上附加 `?project=`，body 仍保留（用于交叉校验）。
