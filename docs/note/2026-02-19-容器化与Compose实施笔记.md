# 容器化与一键部署实施笔记

> 日期：2026-02-19
> 范围：Dockerfile、docker-compose.yml、.env.example、部署配置校验脚本
> 状态：已完成（Docker 实际构建待有 Docker 的环境验证）

## 1. 最终形态：一个服务，三条命令

```bash
cp .env.example .env      # 填 KANBAN_ADMIN_TOKEN
docker compose up -d

docker compose exec kanban agent-kanban admin project add my-app
docker compose exec kanban agent-kanban admin token create --project my-app --name ci
```

`docker-compose.yml` 里**只有 kanban 一个服务**。没有反向代理，没有初始化容器。

## 2. 三个被砍掉的东西，以及为什么

砍掉它们不是因为功能做不到，而是因为每个都在用"多一层"换"少敲几条命令"。

### 2.1 Caddy（反向代理 + 自动 TLS）

**砍掉的理由**：这个 server 的部署场景大多在已有基础设施后面——公司网关、nginx、K8s Ingress、或者干脆是带 VPN 的内网。这些环境里 HTTPS 已经有了，为一个看板再维护一套证书体系：

- 多一个容器要升级、监控、备份
- 多一份证书会过期，续期失败时服务直接不可用
- 多一层网络跳，`X-Kanban-Key` 头的排查链路变长

**留下的**：`KANBAN_BIND` 默认 `127.0.0.1`。要放开改成 `0.0.0.0`，但文档里明确写了裸 HTTP 下 token 是明文传输的。

### 2.2 `bootstrap` profile（初始化容器）

原本的设计是：compose 里加一个一次性的 `bootstrap` 服务，脚本负责「读管理员 token → 判断 project 是否存在 → 签发 token → 写客户端配置样例」。

**砍掉的理由**：这件事本来就是三条命令：

```bash
agent-kanban admin project add my-app
agent-kanban admin token create --project my-app --name ci
```

为它付出的代价却不少：

- 一次性的容器要有自己的 `restart: "no"`、健康检查依赖、退出码处理
- 脚本要处理"幂等重跑"——用户改了参数再跑一次时，是覆盖还是跳过？
- 生成的 `config.toml` 样例如果和实际 server 配置漂移了，排查方向会被带偏
- BusyBox shell 的语法差异（`${VAR:0:10}` 在 `sh` 下不成立）只能在真容器里发现

**留下的**：`KANBAN_ADMIN_TOKEN` 环境变量。用户自己填一个 `openssl rand -hex 16` 生成的 token，比任何脚本都直接。

### 2.3 Docker 里编译二进制

最初的三阶段 Dockerfile 是 `bun build --compile` 出单文件二进制，运行镜像用 `alpine` 裸底。

**砍掉的理由**：`--compile` 会把 bun 运行时**链进**产物（约 90MB）。如果运行镜像基于 `oven/bun:alpine`，那镜像里本来就有一个 bun 运行时——等于同一份运行时装了两遍。

直接跑源码的账：

| 方案 | 运行时 | 体积构成 |
|---|---|---|
| compile + alpine | 二进制内嵌一份 bun | alpine 7MB + bun ~85MB + 应用 ~3MB ≈ **95MB** |
| bun 跑源码 | 镜像自带 bun 一份 | oven/bun ~95MB + 源码 0.5MB + web/dist 0.7MB ≈ **96MB** |

实际差别不大，但**直接跑源码多两个实在的好处**：

1. 镜像里就是你在本地跑的那份代码，中间没有编译这一步可以出错
2. 改一行前端不用重新 `bun build --compile`，Docker 层的缓存失效范围小得多

**留下的**：单文件二进制这条路没取消——它服务的是另一个场景（下载即用、不需要装 bun），走 CI 的 release 流程。两条路互不影响。

## 3. 管理员 token 的三条来源

优先级：`KANBAN_ADMIN_TOKEN` 环境变量 > `config.toml` > 自动生成。

| 来源 | 写 config.toml | 打印明文 | 适用场景 |
|---|---|---|---|
| 环境变量 | 否 | 否 | 容器 / CI / K8s Secret |
| config.toml | — | 否 | 手工 `agent-kanban serve` 后从文件读 |
| 自动生成 | 是 | **是，仅一次** | 首次本地试用 |

环境变量路径额外做了**格式强校验**（必须 `k_` + 32 位小写十六进制），不合法直接启动失败。理由很直接：token 只在初始化时用一次，格式错了不会立刻暴露，而是等到"以为配好了结果 401"的时候才难查。

启动日志对应地分两种措辞：

```
管理员 token：来自环境变量 KANBAN_ADMIN_TOKEN（不写入配置文件、不打印明文）
```

```
已生成管理员 token（只显示这一次，已存入 /data/.kanban/config.toml）
  k_9f2a...
```

## 4. 前端内嵌（发布二进制路径）

`bun build --compile` 出来的二进制要能独立提供前端。有两个障碍：

### 4.1 静态资源必须是静态字面量

Bun 的 embedded files（`with { type: "file" }`）要求 import 路径是字面量，不能是变量、也不能是 glob（写成 glob 在 `bun run` 下不展开，直接语法报错）。

而 Vite 产出的文件名带内容哈希（`assets/index-CnzJ-tBv.js`），构建前根本不知道叫什么。

**解法**：`scripts/gen-assets.ts` 在前端构建后扫一遍 `web/dist`，生成 `src/server/assets.generated.ts`：

```ts
import a5_assets_index_CnzJ_tBv_js from "../../web/dist/assets/index-CnzJ-tBv.js" with { type: "file" }
export const EMBEDDED_ASSETS: EmbeddedAssetMap = {
  "assets/index-CnzJ-tBv.js": () => Bun.file(a5_assets_index_CnzJ_tBv_js as unknown as string),
}
```

`as unknown as string` 不是笔误：Bun 内置类型会把 `.html` 导入声明成 `HTMLBundle`（SSR 用），直接传给 `Bun.file()` 匹配不到重载。运行时它们都是路径字符串。

### 4.2 顺序错了不会报错

**少跑 `gen-assets` 的话，`bun build --compile` 依然成功**，只是二进制里没有前端，`/` 静默退回占位页。这种失败方式很难在流水线里被发现。

所以构建顺序被写死成三步，`package.json` 里封装成 `build:binary`：

```
web:build  →  gen:assets  →  bun build --compile
```

`src/server/assets.generated.ts` 仓库里存的是**空占位**版本，保证新 clone 就能 import。

## 5. 资源查找优先级

```
内嵌资源  →  磁盘目录（KANBAN_WEB_DIR / 包根 web/dist）  →  占位页
```

这个顺序让三种开发形态都成立：

| 场景 | 命中 | 说明 |
|---|---|---|
| 装了 npm 包 | 磁盘 | `web/dist` 在 `files` 里 |
| 跑编译好的二进制 | 内嵌 | 唯一可用的来源 |
| 只 clone 了仓库 | 占位页 | 提示去构建前端 |

启动日志会明确说当前是哪种：

```
Web 看板：已内置于二进制 (10 个文件，729 KB)
Web 看板：从磁盘读取 /opt/kanban/web
Web 看板：未启用 （构建前端后重新编译二进制）
```

## 6. 验证：`scripts/verify-binary.ts`

跑这个脚本需要先产出二进制。它做的事是把 exe 复制到系统临时目录（**那个目录里没有源码、没有 `web/dist`、没有 `node_modules`），在那里起 server，然后：

- `GET /` 返回真实前端（`id="root"`），不是占位页
- HTML 里引用的 hashed JS / CSS 能从二进制里读出来，内容正确
- 556 KB 的 JS、81 KB 的 CSS 都完整——说明嵌入的不是占位
- SPA 回退正常，`/deep/route` 也返回 index.html
- 路径穿越（`%2e%2e%2f%2e%2e%2fpackage.json`）没泄露 `package.json`
- `KANBAN_ADMIN_TOKEN` 注入的 token 直接可用，且**启动日志里没有明文**
- 建 project、签发项目级 token、越权访问被拒

关键在隔离目录：如果不这么做，server 可能只是"恰好能找到磁盘上的 `web/dist`"，而内嵌其实根本没生效。

## 7. 踩过的坑

### 7.1 注释里的 `*/` 截断了块注释

```ts
 *      （`import * as x from "./dist/**/*" with {type:"file"}` 在 bun run 下不工作）
```

`dist/**/*` 里的 `*/` 被解析成块注释结束符，后面的 `" with ...` 就成了真代码，报 `error: Unexpected *`。

**教训**：在 TS/JS 注释里举例涉及 glob 时，别写 `/*` 后面跟 `*/` 的组合。改用文字描述「glob 通配」即可。

### 7.2 生成器把占位模板和新内容拼在了一起

第一版 `gen-assets.ts` 的 HEADER 里带了 `export const EMBEDDED_ASSETS: EmbeddedAssetMap = `，而"有资源"分支又在后面拼了完整声明，于是生成出两个 `export const EMBEDDED_ASSETS`、中间夹着 import 语句。

**修法**：把注释头和类型定义留在 HEADER（两种产物共用），占位内容单独一个常量，新内容由 source 自己完整拼。

### 7.3 检查 Dockerfile 时误命中注释

`check("无 bun build --compile", !/bun build --compile/.test(df))` 一直是失败的，因为 Dockerfile 头部注释里就写着「这里**不编译二进制**」并给出了 `bun build --compile` 的字样。

**修法**：`df.split("\n").filter(l => !l.trim().startsWith("#")).join("\n")` 先剥注释再检查。凡是"断言某命令不存在"的检查，都要先剥注释。

## 8. 安全姿态

| 项 | 做法 | 理由 |
|---|---|---|
| 默认暴露 | `127.0.0.1` | 默认只有本机能连 |
| 容器内 | `0.0.0.0` | 否则收不到 Docker 网络流量；对外面由 `ports` 宿主侧绑定决定 |
| 进程用户 | 非 root `kanban`(10001) | `/data` 显式 chown |
| 提权 | `no-new-privileges:true` | 挡住 setuid 类提权 |
| 凭据 | `.env`（已 gitignore） | 不进镜像（`.dockerignore` 排了 `.kanban`） |
| 日志 | 10MB × 3 轮转 | 避免撑爆磁盘 |
| 备份 | 见 compose 注释里的 `tar` 一行 | 单文件、单卷，备份不需要工具 |

**一个必须说清的前提**：不内置 TLS 意味着**直接对外暴露时 token 是明文传输的**。这一点写在 `.env.example`、compose 注释和本笔记里，因为它是这套架构唯一的真实风险点。
